# 缓存机制说明

## 目的

本篇说明 AD-Agent 当前缓存什么、缓存 key 如何构造、Redis 不可用时如何降级，以及哪些路径会主动刷新缓存。

## 当前代码真源

- `ad-direction-agent/app/persistence/redis_cache.py`
- `ad-direction-agent/app/persistence/redis_client.py`
- `ad-direction-agent/app/core/workflow_orchestrator.py`
- `ad-direction-agent/app/config/settings.py`

## 缓存对象

当前核心缓存对象是 `ASINData`。

缓存用于减少重复 MCP 拉取，尤其是前置策略工作流和 Campaign 分析中共同需要的父 ASIN 基础数据。

Campaign 级细粒度分析结果主要通过 ERP 批次快照/viewmodel 承载，不应被简单混入 ASINData 缓存。

当前还有两类容易混淆的非 ASINData 缓存/状态：

| 类型 | 存放位置 | 说明 |
| --- | --- | --- |
| CampaignData Redis 缓存 | `campaign.py` 内 `_campaign_cache_key()`、`_load_cached_campaigns()`、`_save_cached_campaigns()` | 只缓存活动事实数据，不缓存最终建议 |
| workflow state 缓存型推荐 | State 库 `workflow_meta` / `keyword_analysis` / `target_scores` / `p3_recommendation` | 是用户流程状态或推荐缓存，不是 Redis ASINData |

## Redis 配置

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| `redis_url` | `redis://127.0.0.1:6379/0` | Redis 地址 |
| `redis_enabled` | `True` | Redis 开关 |
| `redis_short_ttl` | `7200` | 完整 ASINData TTL |
| `redis_partial_ttl` | `900` | 部分数据 TTL |
| `redis_lru_ttl` | `30` | 本地 LRU TTL |

Redis 不可用时，缓存层降级到本地 LRU。LRU 只适合作为短期兜底，不应被当作跨进程一致缓存。

Redis 降级语义：

- `redis_cache.py` 的 ASINData 缓存降级为进程内 LRU，默认 30 秒。
- `redis_client.py` 的 lock 降级为进程内 dict，只能保护当前 worker。
- 多 worker 部署时，Redis 不可用会削弱跨进程互斥和缓存共享，但不应让请求直接崩溃。

## Key 结构

完整数据：

```text
asin_data:{asin}:{days}
```

带 `meta_filter` 的轻量数据：

```text
asin_data:{asin}:{days}:f{hash}
```

部分数据：

```text
asin_data_partial:{asin}:{days}
asin_data_partial:{asin}:{days}:f{hash}
```

`meta_filter` hash 由排序去重后的 filter 列表生成，取 md5 前 10 位。这样不同轻量数据域不会互相污染。

## meta_filter 与缓存完整度

`meta_filter` 用于控制本次需要哪些数据域。

典型分组来自 `settings.py`：

- `meta_filter_tactics`
- `meta_filter_diagnosis`
- `meta_filter_execution`
- `meta_filter_p3`
- `meta_filter_dashboard_light`

有 meta_filter 的缓存不等同于完整 ASINData。读取时应优先匹配同 filter 的缓存；需要完整分析时不能误用轻量缓存。

## WorkflowOrchestrator 的缓存策略

`WorkflowOrchestrator` 使用 `_cache_lock` 降低同一进程内重复构建的竞争。

典型逻辑：

1. 先按 ASIN、days、meta_filter 查缓存。
2. 命中则直接返回。
3. 未命中则拉取数据并写入对应缓存。
4. 某些刷新路径会删除指定 filter 缓存，也可能删除完整缓存。
5. 如果请求轻量数据但完整缓存存在，可以从完整缓存派生或复用。

## 失效与刷新

缓存 TTL 是主要失效机制。

主动失效点包括：

- 强制刷新 ASINData。
- 某些 meta_filter 数据重建失败后的清理。
- 需要从完整数据切换到轻量数据或反向修正时的删除/重写。

修改 MCP 字段、normalizer 或 ASINData schema 后，旧 Redis 内容可能结构不兼容。开发环境可直接清理相关 key；生产环境应安排灰度或兼容读取。

## 读写优先级和刷新路径

`WorkflowOrchestrator._ensure_data()` 的核心优先级：

1. `refresh=true`：删除指定 meta_filter 缓存；必要时也删除完整缓存，然后重新拉取。
2. 有 meta_filter：先读同 filter 缓存。
3. 有 meta_filter 且完整缓存存在：复用完整缓存，避免重复 MCP。
4. 无 meta_filter：读完整缓存。
5. 未命中：调用 `DataAggregator.aggregate()` 拉 MCP 并写缓存。

CampaignData 缓存的边界：

- `refresh=true` 时跳过缓存。
- `total_campaigns == 0` 或 `errors` 非空时不写缓存，避免上游临时失败污染后续分析。
- 该缓存只用于节省 discovery/report 成本；LLM 输出、护栏结果和 ERP 批次仍以本次分析为准。

## 常见误区

- 不要把 `asin_data:{asin}:{days}:fxxx` 当成完整缓存。
- Redis 降级到 LRU 后，多 worker 之间不会共享缓存。
- 缓存命中不代表 MCP 当前一定可用。
- Campaign 结果落 ERP，不应通过 ASINData 缓存向前端展示旧 Campaign 结论。
