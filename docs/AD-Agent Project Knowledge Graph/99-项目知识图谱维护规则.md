# 项目知识图谱维护规则

## 目的

本篇规定本目录文档的写法、更新时机和审查方式，确保它长期作为项目知识体系，而不是变成一次性交接材料。

## 文档定位

本目录只记录 AD-Agent 项目自身：

- 架构
- 数据对象
- 调用链
- 数据库边界
- 运行时设置
- 缓存机制
- 前端设计
- 测试地图
- 项目内复核组件

不记录：

- 流水式任务记录
- 个人交接记录
- 业务知识库正文
- 临时排障流水
- 未验证的猜测

## 每篇文档的固定结构

建议保留：

```markdown
# 标题

## 目的
## 当前代码真源
## 核心说明
## 常见误区
## 更新检查清单
```

复杂专题可增加：

- 主流程
- 数据模型
- API 入口
- 表结构
- 时序图
- 配置表
- 验证方式

## 详细度最低标准

长期说明文档不能只写“模块做什么”，还应尽量回答这些问题：

| 问题 | 文档里应给出的信息 |
| --- | --- |
| 数据从哪来 | MCP 工具、上游 API、State/ERP 表、前端入参或缓存 key |
| 入参如何构造 | 代码文件、函数、关键字段和默认值 |
| Prompt 如何组装 | reasoner/kb_loader/preset 位置，哪些运行时事实会进入 prompt |
| 本环节产出什么 | Python 对象、ERP 表、viewmodel 字段、前端状态或 MCP payload |
| 谁消费产物 | 下游 step、前端、执行链路、定时任务、Codex 复核 |
| 是否有多来源/兜底 | 优先级、fail-open/fail-closed、缓存/实时差异 |
| 边界条件是什么 | blocked/degraded、空数据、partial failure、重复执行、过期缓存 |
| 如何验证 | 对应测试文件、手工 smoke 或外部依赖缺口 |

如果某篇文档只有宏观说明，后续修改时应优先补“代码锚点地图”和“数据/状态流表”。

## 真源原则

代码是真源，文档是索引和解释。

当文档和代码冲突：

1. 先读代码。
2. 用测试或运行结果确认。
3. 更新文档。
4. 如果代码行为不符合设计，再另开实现任务修改代码。

行号可以作为导航锚点，但不能当成长期真源。写行号时应同时写函数名或类名，便于后续用 `rg` 复核。

## 开发 Agent 使用规则

开发 Agent 修改项目时应：

1. 先读对应专题文档的“当前代码真源”。
2. 再读真实代码。
3. 不把文档当成唯一事实来源。
4. 修改代码后同步更新相关文档。
5. 运行 `14-测试与验证地图.md` 中对应测试。

## 更新触发器

必须更新文档的情况：

- 新增或废弃 API。
- 新增或废弃 MCP 工具。
- 修改 MCP 参数或返回消费。
- 修改 `ASINData`、`CampaignData` 或前置层模型。
- 修改 ERP/State 表。
- 修改 Campaign viewmodel。
- 修改缓存 key、TTL、meta_filter。
- 修改 timeout、semaphore、连接池。
- 修改定时任务请求体或退出码。
- 修改 Advert MCP 执行链路。
- 修改 Codex 复核接入方式。

## 禁止写法

避免以下内容：

- “今天修了……”
- “临时这样处理……”
- “后面再补……”
- “详见群聊……”
- 没有代码真源的断言。
- 只描述现象但不说明入口和边界。

如果确实存在不确定性，应写成：

```text
当前代码只能确认 A；B 需要从外部系统 schema 或部署配置验证。
```

## 审查命令

在仓库根目录执行：

```powershell
Get-ChildItem "docs/AD-Agent Project Knowledge Graph" | Select-Object Name,Length
rg -n "<占位词或流水式记录关键词>" "docs/AD-Agent Project Knowledge Graph"
rg -n "当前代码真源" "docs/AD-Agent Project Knowledge Graph"
```

如果新增文档没有“当前代码真源”，通常不应合入。

## 文件命名

使用两位数字前缀和中文主题：

```text
00-项目知识图谱总览.md
01-核心数据对象与领域模型.md
```

新增文档应先判断是否能并入既有专题。只有当主题有独立读者、独立真源和独立维护节奏时，才新建文件。

## 常见误区

- 不要把旧交接文档复制进来。应该提炼稳定架构和当前代码真源。
- 不要把业务知识库规则复制进来。这里只解释加载机制和调用关系。
- 不要为了“完整”记录所有历史方案。
- 不要让文档只有人类能读；开发 Agent 需要明确路径、入口和验证命令。

## 更新检查清单

- 每次修改本目录后，跑审查命令。
- 每次大功能合入后，检查 README 阅读路线是否仍然合理。
- 每次新增测试后，更新测试地图。
- 每次发现旧交接文档比本目录更准时，优先更新本目录。
