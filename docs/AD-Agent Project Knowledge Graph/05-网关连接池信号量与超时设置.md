## 目的

本篇集中记录 AD-Agent 的关键运行时限制：MCP 网关、连接池、信号量、LLM、Campaign 总超时、ERP 写入和广告执行 MCP。

## MCP 数据网关

主要配置：

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| `mcp_transport` | `none` | MCP transport 开关，生产通常需要 http |
| `mcp_server_name` | `user-starrocks-data-server` | MCP server 名 |
| `mcp_gateway_url` | 空 | MCP 网关地址 |
| `mcp_gateway_token` | 空 | 网关鉴权 token |
| `mcp_gateway_header_name` | `Authorization` | token header |
| `mcp_timeout` | `1200` | 单次底层调用默认超时 |
| `mcp_retries` | `1` | 失败重试次数 |
| `mcp_max_concurrency` | `115` | MCP 并发信号量 |
| `mcp_max_connections` | `120` | httpx 连接池上限 |
| `mcp_tool_timeout` | `1200` | 报表工具超时 |
| `mcp_bootstrap_timeout` | `180` | bootstrap 工具超时 |
| `mcp_context_timeout` | `30` | 父 ASIN 上下文解析超时 |

`mcp_max_connections` 应大于或等于 `mcp_max_concurrency` 并保留余量，否则会在连接池层排队，抵消信号量配置。

MCP 调用有三层超时：

| 层 | 配置/代码 | 说明 |
| --- | --- | --- |
| httpx 内层 | `mcp_timeout` / `mcp_client.py:109` | 单个 HTTP client 请求的底层上限 |
| adapter 单工具 | `call_tool_timed_with_args(timeout)` | 业务传入的单工具 timeout，Campaign 通常用 `campaign_mcp_tool_timeout` |
| 阶段/总流程 | `run_planned_mcp_tools()`、Campaign `_do_analyze()` | 批量阶段和请求整体保护 |

排查超时时，应先看是哪一层触发。只增大内层 `mcp_timeout`，不能解决 semaphore 等待、连接池排队或 Campaign 总超时。

## MCP 调用层限流

`McpAdapter` 内部有全局信号量：

```python
asyncio.Semaphore(max(1, settings.mcp_max_concurrency))
```

分阶段工具运行 `run_planned_mcp_tools()` 也会按 `max_concurrency` 控制并发，并区分 bootstrap timeout 和 reports timeout。

Campaign 级工具调用还有 `campaign_mcp_tool_timeout`，通过 `call_tool_timed_with_args()` 包装 `asyncio.wait_for()`。

信号量和连接池关系：

- `McpAdapter._sem` 控制应用层并发。
- `StreamableHttpMcpInvoker` 的 httpx limits 控制连接池。
- `campaign_fetcher.py` 内还有 `_mcp_sem` 用于 placement/search term 等 Campaign 级批量调用。
- 如果 worker 数增加，实际系统并发约等于每 worker 并发配置的叠加，配置时要把 `num_workers` 纳入容量估算。

## Campaign 分析超时

主要配置：

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| `campaign_discovery_timeout` | `90` | Campaign discovery 墙钟上限 |
| `campaign_mcp_tool_timeout` | `300` | Campaign 单工具超时 |
| `campaign_rank_timeout` | `45` | 自然排名旁路拉取上限 |
| `campaign_total_timeout` | `900` | Campaign 总分析超时 |
| `campaign_sem_acquire_timeout` | `120` | 等待 Campaign semaphore 槽位上限 |
| `campaign_llm_concurrency` | `50` | Campaign LLM 并发 |
| `campaign_global_llm_concurrency` | `24` | 全局 Campaign LLM 并发 |
| `campaign_batch_size` | `10` | Campaign 批处理大小 |

API 层 `_do_analyze` 对 ASINData 准备和 Campaign 主分析都使用 `asyncio.wait_for()`。总超时应理解为“保护请求不永久挂死”的上限。

Campaign 分析互斥：

- 同一父 ASIN 使用 `campaign:running:{asin}` running key。
- Redis 可用时跨 worker 生效；Redis 不可用时只能进程内兜底。
- TTL 通常基于 `campaign_total_timeout + 60`，防止异常退出后永久占锁。
- 前端看到 in-progress 时，应切到只读或等待，不应重复触发同 ASIN 分析。

## LLM 客户端

主要配置：

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| `llm_timeout` | `75` | LLM read timeout |
| `llm_global_concurrency` | `420` | 全局 LLM 并发预算 |
| `num_workers` | `1` | 用于折算每 worker 并发 |

HTTP timeout 拆分：

- connect：8 秒
- read：`llm_timeout`
- write：10 秒
- pool：5 秒

Key pool 会记录成功、失败、延迟和状态码，用于多 key 轮转。

LLM 并发要同时看：

- 全局 LLM 客户端并发。
- Campaign 流内 `campaign_llm_concurrency`。
- Campaign 全局 `campaign_global_llm_concurrency`。
- 每批 batch size 和 R1 单轮 + 护栏 R2/R3/R4 重判次数。

Campaign LLM 卡顿时，不一定是 MCP 问题；先看 LLM label 延迟、timeout 和全局信号量等待。

## ERP 写入

主要配置：

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| `erp_auto_write` | `False` | 是否自动写 ERP |
| `erp_write_timeout` | `30` | ERP 写入超时 |
| `erp_use_tls` | 配置项 | ERP MySQL TLS |

ERP 写入失败应与分析失败区分。分析可以成功但写入失败，前端展示和定时任务需要分别判断。

## Advert MCP 执行

主要配置：

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| `advert_mcp_url` | 空 | Advert MCP 网关地址 |
| `advert_mcp_token` | 空 | Advert MCP token |
| `advert_mcp_timeout` | `120` | 单次执行工具超时 |
| `advert_mcp_enabled` | `False` | 执行总开关 |
| `advert_exec_dry_run` | `True` | 默认空跑，不动真实广告 |

执行路径在 `advert_mcp_enabled=false` 时拒绝真实执行，在 `advert_exec_dry_run=true` 时构造计划但不下发真实 MCP。

## 配置关系建议

- `mcp_max_connections >= mcp_max_concurrency`。
- `campaign_total_timeout` 应大于单轮 discovery、报表、LLM、护栏和 ERP 写入的合理总和。
- `campaign_sem_acquire_timeout` 不宜过长，否则用户会感觉请求挂起；也不宜过短，否则高峰期大量误失败。
- Advert MCP timeout 不应直接沿用数据 MCP 的长超时，因为执行接口语义更敏感。

## 常见误区

- 单纯增大 `mcp_timeout` 不能解决连接池排队。
- Campaign 总超时不是每个 MCP 工具的超时。
- LLM timeout 和 Campaign total timeout 是两层不同保护。
- `advert_exec_dry_run=true` 时返回 ok 不代表真实广告已经执行。
