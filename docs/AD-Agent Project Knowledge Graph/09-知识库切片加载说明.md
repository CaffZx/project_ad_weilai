## 核心机制

`kb_loader.py` 用 preset 描述“某个任务需要哪些知识库文件的哪些章节”。

加载流程：

1. 调用方指定 preset。
2. preset 展开为若干 `fid:sectionlist`。
3. loader 只读取被引用的文件。
4. 按章节切片提取内容。
5. 枚举值通过 `ENUM_MAP` 翻译成业务文本。
6. 缺失章节记录 warning。
7. 拼装成 LLM prompt 可消费文本。

Preset 的粒度原则：

- 一个 preset 对应一个 LLM 任务，不对应一个页面或一个后端模块。
- Campaign exact/broad/new/overview/budget 被拆成不同 preset，是为了减少 token、降低互相干扰。
- synthesis prompt 当前刻意不直接塞入完整 Campaign adjustment KB，避免 26K 级规则重复进入后处理阶段。

## 章节引用格式

典型格式是：

```text
fid:section1,section2,section3
```

其中：

- `fid` 指知识库文件标识。
- section list 指需要加载的章节。
- loader 根据章节标题或内部索引提取内容。

## 与 Prompt 的关系

知识库切片是 prompt 的证据和规则输入。

它不应包含：

- 当前运行时数据。
- MCP 工具返回原始 JSON。
- ERP 表结构。
- 项目架构说明。

这些内容应由代码、数据层或本项目知识图谱提供。

## Ontology Card 注入机制

除了按 preset 注入知识库切片，`kb_loader.py:232` 的 `build_ontology_card(task_type)` 还会从 `runtime_contract.yaml` 拼装一份精简的「Ontology Card」注入 prompt。它与知识库切片是互补关系：

- **知识库切片**：提供业务规则（阈值、流程、策略）
- **Ontology Card**：提供运行时结构约束（哪些动作合法、组合如何路由、硬规则是什么）

### 注入内容

从 `runtime_contract.yaml` 提取以下字段：

| 字段 | 内容 | 用途 |
|------|------|------|
| `mode_policies` | 6 种经营模式的允许/禁止动作清单 | LLM 感知当前模式的行为边界 |
| `portfolio_groups` | 4 组及其 match_type 约束 | LLM 理解组合语义 |
| `portfolio_routing` | ROUTE-001 ~ ROUTE-999 路由规则 | LLM 不产出违反路由的动作 |
| `hard_rules` | ONT-RUNTIME-001 ~ 009 | 硬约束注入 LLM prompt |
| `action_bundle` | 动作生命周期状态机 | LLM 理解动作流转 |

### 分流注入

`build_ontology_card(task_type)` 按 `task_type` 分流：

- **精准流（exact）**：注入 `ontology_card_injection.always_inject` 的全部 hard_rules，但**不注入** ONT-RUNTIME-001（广泛禁广告位——精准广告允许广告位调整，这条规则对其是噪声）
- **广泛流（broad）**：注入全部 hard_rules，含 ONT-RUNTIME-001
- `always_inject` 当前清单：ONT-RUNTIME-002 ~ 009（8 条）

### 拼装位置

`build_campaign_adjustment()` 是 campaign 流的主要入口。它在末尾将知识库切片和 Ontology Card 拼装：`KB 切片文本 + "\n\n---\n\n" + Ontology Card YAML`。调用方（`reasoner.py`）不感知这一拼装逻辑。

## KB v3.4.8 四条结构性约束

知识库 `00-知识库总纲与切片覆盖矩阵.md` 规定了四条结构性约束，对 `kb_loader.py` 和知识库维护有直接影响：

### 约束 1：单一数值来源

任何阈值只在**一个**文件里定义一次，其他文件只能引用编号。这消除了 v3.3.0 中「同一数值在多个文件各自表述后漂移」的问题。对 loader 的影响：切片可以安全地只注入规则文件，阈值已在唯一源文件中。

### 约束 2：单一动作词表

`30-动作词表与映射.md` 是 action_code 的唯一权威表。`12-输出规范.md`、`ontology/actions.yaml`、ERP 映射、`app/domain/advertising.py` 的 `ActionType` 必须从它派生。`campaign_adjustment_exact` 和 `campaign_adjustment_broad` 两 preset 均已包含 30号。

### 约束 3：切片全覆盖

每个知识库文件必须满足：①已纳入至少一个 prompt 切片，或 ②显式标注 `reference_only`。`tests/test_kb_slicing.py` 的 `test_every_kb_file_is_covered_or_reference_only` 机械校验此约束。若 loader 新增 preset 或修改切片后该测试失败，说明有知识库文件悬空。

### 约束 4：无死资产

代码侧的新增模块必须满足：①在生产链路可达（从 `app.main` 出发的 import 图能到达），或 ②在断链清单显式登记为「待接线」。`tests/test_no_dead_assets.py` 机械校验此约束。`acos_constraints.py` 和 `campaign_exact_transition.py` 均从 `campaign.py` 的生产路径可达，无需登记。

## 缺失章节处理

如果 preset 引用的章节不存在，loader 会记录 warning。

开发时不要忽略 warning。缺失业务规则可能导致 LLM 输出看似正常但依据不完整。

## 失败和降级边界

| 情况 | 行为 | 维护要求 |
| --- | --- | --- |
| preset 名不存在 | `build()` 返回空或记录异常风险 | 调用方应使用固定枚举式 preset，不要由前端传入 |
| 文件不存在 | preload warning | 新增/改名知识库文件后同步 PRESETS |
| 章节不存在 | build warning，缺少该片段 | 修改章节标题/编号后必须跑 `tests/test_kb_slicing.py` |
| enum 未翻译 | prompt 中保留原枚举或语义变弱 | 修改 `layers.py` 枚举后检查 `ENUM_MAP` |
| preset 过大 | LLM token 和延迟上升 | 优先按任务拆分，不要把全量 KB 塞给所有任务 |

## 常见误区

- 不要把本目录的项目知识图谱加入业务知识库切片。
- preset 越大不一定越好；过多无关业务规则会稀释 prompt。
- enum 翻译是 prompt 语义的一部分，修改枚举值时要检查 `ENUM_MAP`。
- 缺失章节 warning 不是纯日志噪音。
- 不要把 Ontology Card 当成知识库切片的替代品。两者互补：KB 切片提供业务规则，Ontology Card 提供运行时结构约束。
- 不要在精准流 prompt 中注入 ONT-RUNTIME-001（广泛禁广告位）。`build_ontology_card(task_type="exact")` 已自动排除。
- 不要绕过 `build_campaign_adjustment()` 直接调 `build(preset)` 来做 campaign 分析——后者不含 Ontology Card 和方向收窄。

## 更新检查清单

- 新增业务知识库文件后，检查是否需要新增 fid 和 `_FILE_PATHS` 映射。
- 新增 LLM 任务类型后，优先新增或复用 preset。
- 修改章节标题后，运行知识库切片测试（`test_kb_slicing.py`）。
- 修改 enum 后，检查 `ENUM_MAP` 和所有相关 prompt。
- 修改 `runtime_contract.yaml` 的 mode_policies / portfolio_routing / hard_rules 后，检查 `build_ontology_card()` 的注入逻辑和 always_inject 清单是否需要同步更新。
- 新增 KB 文件但未纳入任何 preset 时，`test_every_kb_file_is_covered_or_reference_only` 会失败——要么补切片，要么标注 `reference_only`。
