## 统一状态机（三张 pending 表共用）

`confirm_status` 和 `execute_status` 是独立维度。

| 阶段 | `confirm_status` | `execute_status` | `task_id` | `execute_time` |
| --- | --- | --- | --- | --- |
| 分析落库 | `PENDING` | `PENDING` | `NULL` | `NULL` |
| 人工确认/自动确认后未提交 | `CONFIRMED` | `PENDING` | `NULL` | `NULL` |
| 容量满拒绝提交（scheduler.reserve 失败） | `CONFIRMED` | `PENDING` | `NULL` | `NULL` |
| 已原子抢占、正在提交或等待 taskId | `CONFIRMED` | `IN_PROGRESS` | `NULL` | `NULL` |
| 已收到 taskId、等待轮询终态 | `CONFIRMED` | `IN_PROGRESS` | 返回的 taskId | `NULL` |
| 异步任务确认成功 | `CONFIRMED` | `SUCCESS` | 返回的 taskId | 终态确认时间 |
| 异步任务明确失败 | `CONFIRMED` | `FAIL` | 返回的 taskId（若有） | 终态确认时间 |
| 四次查询均未确认成功（轮询耗尽） | `CONFIRMED` | `FAIL` | 返回的 taskId | 第四次查询时间 |
| 提交阶段未拿到 taskId（超时/异常/空） | `CONFIRMED` | `FAIL` | `NULL`（`` or None → NULL） | 提交失败时间 |
| 同步 MCP（新建/否词）明确成功 | `CONFIRMED` | `SUCCESS` | `NULL` | 接口返回时间 |
| 同步 MCP 明确失败 | `CONFIRMED` | `FAIL` | `NULL` | 接口返回时间 |
| 演练 | `CONFIRMED` 或 `PENDING` | `DRY_RUN` | `NULL` | `NULL` |

关键语义：

- **提交成功 ≠ 广告生效**：`task_id` 只代表异步任务被受理；终态由后台轮询器确认。
- **taskId 拿到即落库**：异步 MCP 返回有效 taskId 后立即写入精确 pending 行（保持 `IN_PROGRESS`、`execute_time=NULL`），既是轮询依据，也是服务重启后的人工审计信息。
- **三次失败文案必须区分**：提交结果未知（`提交结果未知，未获得 taskId，禁止自动重提，需人工核对`）、轮询耗尽（`异步任务在 4 次轮询…内未返回成功终态；需人工复核 taskId=<id>`）、平台明确失败（平台返回的 errorMsg）。不得混用。
- **`confirm_status` 不属于轮询器写入范围**：提交、轮询、终态回写均不得修改它。

## 执行入口（2026-08-03 起统一；v3.28 核实）

历史存在两条独立路径；spec §6.1/§6.2 已收敛为**唯一提交服务 `submit_and_poll()`**。

```
POST /campaign/confirm (approve，前端"同意所选")                     ← 正常模式 & 清货优先共用
  → submit_execution_direct(decision_id, card_ids)
    → 先对选中卡原子确认（confirm_decisions）
    → 重载该范围内 CONFIRMED + execute_status=PENDING 的 pending（confirmed_only=True）
    → build_exec_plan() → submit_and_poll()                          ← 统一提交/轮询服务

POST /decision/immediate-exit（立即退出，系统自动确认）              ← 仅立即退出模式
  → _run_immediate_exit()
    → [新批次] 确定性动作分类 → write_immediate_exit → finalize_batch → confirm_decisions(全量自动)
    → submit_execution(decision_id)
      → load_confirmed_pending(全部 CONFIRMED) → build_exec_plan() → submit_and_poll()
```

> **"清货优先"不是独立执行入口**（v3.28 澄清）：`CONTROLLED_CLEARANCE` 只是 `operating_mode` 枚举值，仅影响 LLM 分析阶段的策略上下文，执行时与正常模式走完全相同的 `/campaign/confirm` → `submit_execution_direct` 路径。前端人工确认/勾选后同样经 `submit_and_poll` 统一管线（原子抢占 + taskId 落库 + 轮询终态）。交接文档 §13.4 表把清货优先列为独立链路且标注"taskId 终态轮询=无"已是 v3.24 之前的状态，现已过时。

已删除：

- `POST /campaign/execute`（历史端点，2026-07-26 至 08-03 生产日志 0 次访问，campaign.py:644 仅剩注释）
- `POST /decision/immediate-exit/status`（前端 5s×12 轮询入口）
- `poll_execution_result()` / `list_execution_task_ids()` / `update_campaign_terminal_status()`（旧 taskId 反查与泛更新）

新增：

- `GET /decision/execution-status?decision_id=...`：只读聚合三张 pending 表的 `task_id / execute_status / execute_msg / execute_time`，不调用 MCP、不写数据库；前端刷新展示用。

## 统一提交/轮询服务 `submit_and_poll()`

`app/workflow/steps/advert_execution.py`。调用方必须已确认或先完成确认。

流程（spec §5.1，v3.28 代码核实）：

```
1. insert_advert_record（主记录，含 request_params_json）
2. dry-run 分流：只写 DRY_RUN 结果；不抢占、不调 MCP、不写 task_id、不入队
3. 容量预检：scheduler.reserve()；容量满 → 拒绝提交，pending 保持 PENDING
4. 原子抢占：claim_pending_for_execution（PENDING→IN_PROGRESS，WHERE confirm_status='CONFIRMED'）
   全部唯一目标成功才继续；失败 → release 名额 + 返回 already_claimed
5. _resolve_modify_portfolios（挪组）
6. 三路 MCP 并行：agent_async_batch_update_advert ∥ agent_create_portfolio_campaign ∥ agent_create_negative_keywords
   （同一 try 块内依次调用，异常隔离；新建/否词为同步 MCP，结果在该 try 块内直接落 SUCCESS/FAIL）
7. 同步路径回写：sync_ops（新建/否词）→ update_pending_execute_status（终态写 execute_time，非终态不写）
8. 无 async_ops 提前返回（仅同步操作时跳过轮询）
9. 未拿到有效 taskId → write_pending_submit_failed（精确行写 FAIL + _SUBMIT_UNKNOWN_MSG）
10. 拿到 taskId → write_pending_task_id（只写 task_id + update_time，保持 IN_PROGRESS → execute_time 不写）
    → 池表同步 → 闭包 _terminal_write_fn（write_pending_terminal + 终态池表同步）
    → scheduler.enqueue(PollTask) 入队轮询
```

### 计数口径统一

抢占、taskId 落库、终态回写全部使用**同一套唯一 `(record_kind, pending_id)` 目标**：

- `_unique_pending_target_count(ops)`：唯一目标数（含无效身份，repository 无法抢占它们时 fail-closed）
- `claim_pending_for_execution`：内部按唯一目标去重抢占
- `write_pending_task_id`：按唯一目标写 task_id，行数不足即抛错（整笔回滚）
- `write_pending_terminal` / `write_pending_submit_failed`：按唯一目标精确回写

重复 `ExecPlan.ops` 只抢占、提交、绑定一次，不会误报 `already_claimed`。

## taskId 轮询调度器

`app/workflow/steps/task_poll_scheduler.py` — 进程内有界队列 + 固定协程消费者。

| 配置 | 默认 | 说明 |
|------|------|------|
| `advert_task_poll_workers` | `2` | 每 Web 进程的轮询协程消费者数（**不是** Uvicorn 进程数） |
| `advert_task_poll_queue_capacity` | `20` | 每进程轮询队列容量 |

- 单进程已受理上限 = 协程数 + 队列容量 = **22**；多进程部署时全局上限 = 进程数 × 单进程值（8012 当前 4 进程 → 最多 8 并发结果查询、80 个已受理任务）。
- 对每个 taskId 按 **3m/6m/12m/24m** 最多查询四次 `agent_batch_update_advert_result`。
- **部分终态不停止轮询**：每次查询只回写已终态（SUCCESS/FAIL）的行，未终态行保持 `IN_PROGRESS` 继续轮询；全部关联 campaign 终态或四次耗尽才结束。
- 四次耗尽 → 未终态行写 `FAIL` + 轮询耗尽文案。
- 不持久化调度状态：进程重启丢失内存队列，但已落库的 `pending.task_id` 供人工核对；**不自动重提**（避免重复修改广告）。
- 仍存在极窄崩溃窗口（外部已受理、本地 task_id 写入前进程退出）；无持久化提交账本时无法严格零丢失，需高优先级告警 + 外部执行记录人工核对。

| `campaign_portfolio_enabled` | `bool` | — | 组合分类/挪组总开关 |

**生产执行必须同时满足**：

- `advert_mcp_enabled = True`
- `advert_exec_dry_run = False`
- `advert_mcp_url` 和 `advert_mcp_token` 已配置

### 本地开发机 vs 生产服务器（v3.28）

本地仓库 `settings.py` 默认 `advert_mcp_enabled=False` + `advert_exec_dry_run=True`：所有执行请求走 dry-run 分支，构造计划但不调 MCP、不抢占、不入队。生产服务器（chenv31）通过环境变量或 `.env` 覆盖为生产值，走真实提交→轮询链路。

### dry-run 语义（spec §5.1 第1条，v3.28 核实）

- 只构造计划 + 写入既有 `DRY_RUN` 结果（`execute_status='DRY_RUN'`，`task_id=NULL`、`execute_time=NULL`）
- **不**原子抢占、**不**调用异步 MCP、**不**写 taskId、**不**创建后台轮询任务
- `/campaign/confirm` approve 路径：`submit_execution_direct` 检测 `advert_exec_dry_run` 后直接按选中 card_ids 构造计划返回（advert_execution.py:791-801），**跳过 `confirm_decisions` 步骤**
- `/decision/immediate-exit`：`submit_execution` → `submit_and_poll` 内部 dry-run 分流（advert_execution.py:401-422）

## 执行计划 `ExecPlan`

定义于 `advert_exec_mapper.py`，是 `build_exec_plan()` 的返回值，承载全部 MCP 调用参数和追踪元数据。

### 字段

| 字段 | 类型 | 用途 |
|------|------|------|
| `params_vo_list` | `list[dict]` | `agent_async_batch_update_advert` 入参。经 `_resolve_modify_portfolios` 按 portfolioId 拆分 |
| `create_calls` | `list[dict]` | `agent_create_portfolio_campaign` 逐 card 调用 |
| `negative_calls` | `list[dict]` | `agent_create_negative_keywords` 调用 |
| `ops` | `list[dict]` | 逐 pending 行的操作记录（`record_kind/pending_id/campaign_id` 是精确回写的唯一目标） |
| `warnings` | `list[str]` | 非致命告警（缺字段、跳过等），返回前端 |
| `move_errors` | `list[dict]` | 挪组失败详情，结构 `{campaign_id, campaign_name, group, reason}`，去重后前端弹 toast |

### `build_exec_plan()` 内部逻辑

1. 从 `pending["decision"]` 提取 `shop_id / parent_asin / parent_seller_sku`
2. 将 cards 按 `suggest_category == "CREATE"` 分为新建和修改两类
3. **新建活动**：逐 card 构造 `create_calls`（`agent_create_portfolio_campaign` 入参）
4. **否定词**：`keyword_pending` 中 negative 行聚合为 `negative_calls`
5. **修改已有活动**：按 `campaign_id` 聚合 campaign/keyword/placement pending 行为 `campaignVo`，汇入一个 `paramsVo` 条目。`campaignGroupType` 来自 card 的 `campaign_group_type` 字段（ERP 码），暂存于 campaignVo 内部，**不传给 MCP**——后续由 `_resolve_modify_portfolios` 解析为 `portfolioId`

## Portfolio 解析（挪组核心）

挪组逻辑集中在 `_resolve_modify_portfolios()`（`advert_execution.py`）。

### 完整解析链

```
t_advert_agent_modify_suggest_card.campaign_group_type
  → "exact_core_group"  (ERP 码)
    → unmap_campaign_group_type()
      → "精准主力组"  (中文组名)
        → agent_query_portfolio_list  (查 MCP)
          → _normalize_portfolio_list(res)  (返回 list[dict]，非 list 直接 raise ValueError)
            → match_unique_portfolio("精准主力组", portfolios)
              → 命中 1 个: _pf_field(pf, "portfolioId")  ← 仅取此字段
                → 注入 paramsVo 顶层 "portfolioId"
```

### `match_unique_portfolio()` 匹配规则

- **单向子串匹配**：`g in nm`（组名必须是 portfolio 名的子串），不再反向匹配（`nm in g` 已删除）
- **必须唯一**：0 个匹配或 ≥2 个匹配均返回 `(None, match_count)`
- **取 portfolioId**：`_pf_field(pf, "portfolioId")`，**仅此一个字段**，不 fallback 到 `id`（内部 hash）或 `portfolio_id`

### 按 portfolioId 拆分 paramsVo

`build_exec_plan()` 构造时所有活动在**一个** `paramsVo` 条目中。`_resolve_modify_portfolios()` 按 `portfolioId` 拆成多个条目：

```
改前: paramsVoList[0]: { ..., campaignVoList: [活动A→主力组, 活动B→测试组, 活动C→主力组] }

改后: paramsVoList[0]: { ..., portfolioId: "169...", campaignVoList: [活动A, 活动C] }
       paramsVoList[1]: { ..., portfolioId: "145...", campaignVoList: [活动B] }
       paramsVoList[2]: { ..., campaignVoList: [活动D] }   ← 未匹配到任何组合，无 portfolioId
```

拆分时拷贝原条目的所有顶层字段（`shopId`/`parentAsin`/`currentUserId`/`adjustReason`/`decisionId` 等）。

### 三种结果

| 场景 | `campaignGroupType` | `portfolioId` | 其他调整字段 | `move_errors` |
|------|---------------------|---------------|-------------|---------------|
| 匹配成功 | **移除**（冗余） | 注入 paramsVo 顶层 | 原样保留 | 不写入 |
| 匹配失败（0/≥2/ID缺失） | **移除** | 不注入 | 原样保留继续下发 | 写入结构化错误 |
| `agent_query_portfolio_list` 查询失败 | **移除**（全部） | 不注入（全部） | 原样保留继续下发 | 不写入（仅一条 warning） |

核心原则：**挪组失败不阻塞预算/Bid/状态/广告位等其他调整**。

### `move_errors` 结构

```python
plan.move_errors.append({
    "campaign_id": "123456789",
    "campaign_name": "活动A",     # 从 plan.ops 按 campaign_id 反查
    "group": "精准测试组",         # 中文组名
    "reason": "存在多个",          # "不存在" | "存在多个" | "ID缺失"
})
```

活动名从 `plan.ops` 建立 `campaign_id → campaign_name` 映射获取，**不污染 campaignVo**（campaignVo 内不塞 `_name` 等内部字段）。

### 前端展示

`campaign_confirm()` 将 `move_errors` 扁平透传前端。`state.js` 按 `group + reason` 去重：

```js
const byGroup = {};
for (const e of moveErrors) {
  const key = `${e.group}\x00${e.reason}`;
  if (!byGroup[key]) byGroup[key] = { group: e.group, reason: e.reason, count: 0 };
  byGroup[key].count++;
}
// → sticky toast: "精准测试组存在多个，已跳过 8 个活动，不阻塞预算和bid修改。"
```

## 结果解析

### `parse_result_envelope(res)` → `(bool, str)`

判断 MCP 返回是否成功。当前实现遍历 dict key 查找 `*state`/`*msg`，**未识别格式时默认返回 `(True, "")` 即成功**——此项的风险已在 audit 中标记，尚未修复。

### `extract_task_ids(res)` → `list[str]`

从 MCP 返回提取异步 taskId。尝试多个 key 名并递归进 `data` 子对象。

**提交成功 = 拿到有效 taskId**：未拿到（MCP 错误/网络异常/超时/无法解析/空 taskId）一律视为提交阶段终态失败，写 `FAIL` + `提交结果未知，未获得 taskId，禁止自动重提，需人工核对` 文案。

### `parse_batch_update_terminal(raw, message_by_campaign)` → `dict[str, str]`

轮询器解析 `agent_batch_update_advert_result` 的逐活动终态（`SUCCESS`/`FAIL`/`IN_PROGRESS`）。未达终态的行保持 `IN_PROGRESS` 等待下次查询。

## 幂等边界

### 统一服务（`submit_and_poll`）

- 原子抢占 `PENDING → IN_PROGRESS` 成功才允许提交 MCP（WHERE `confirm_status='CONFIRMED'`）
- 抢占失败/重复点击/旧前端请求只能读取当前状态，绝不创建第二个轮询器或再次下发
- taskId 落库行数不足（按唯一目标计数）→ 视为失败，重试一次仍失败则禁止入队 + 释放名额
- 轮询入队失败 → taskId 已落库但无轮询器，报错并转人工，不得静默

### `/campaign/confirm` approve 时序

1. 先对选中卡原子确认（`confirm_decisions`，`ok=False` 不得下发）
2. **重载**该范围内 `CONFIRMED + execute_status=PENDING` 的 pending（`confirmed_only=True`）
3. 用重载结果构建计划提交

已拒绝/已完成等跳过项不会混入计划，也不会阻塞同次其他有效项。重复点击的卡被 `confirm_decisions` 记为 skipped，但重载后其**未执行的** pending 仍可执行（幂等且不阻塞）。

### 状态回写语义

| 场景 | execute_status | 说明 |
|------|---------------|------|
| dry-run | `DRY_RUN` | 计划构造成功，未真实下发；task_id/execute_time 均为 NULL |
| 提交成功拿到 taskId | `IN_PROGRESS` + task_id | 等待后台轮询终态 |
| 提交未拿到 taskId | `FAIL` | 提交结果未知文案，禁止自动重提 |
| 轮询终态 SUCCESS/FAIL | `SUCCESS`/`FAIL` + task_id + execute_time | 按 `(record_kind, pending_id)` 精确回写 |
| 四次轮询未确认 | `FAIL` | 轮询耗尽文案，区别于平台明确失败 |
| 同步新建/否词 | `SUCCESS`/`FAIL` | task_id 保持 NULL |

`update_pending_execute_status` 只对 `SUCCESS/FAIL` 等终态写 `execute_time`；`IN_PROGRESS`/`PENDING`/`DRY_RUN` 不写。

## Fallback 禁令

广告执行 MCP 链路严禁 fallback。凡涉及 MCP 工具入参/返回处理，取不到正确值就报错/跳过，不允许：

- 多个字段名逐个试取（如 `"portfolioId"` → `"id"` → `"portfolio_id"`）→ 已修复，仅取 `portfolioId`
- 信封 key 猜测（如 `"data"/"list"/"portfolioList"...`）→ 已修复，非 list 直接 `raise ValueError`
- `campaignGroupType` 兜底传给 MCP 自行解析 → 已删除
- 未知 group_code 原样透传 → 已修复，`unmap_campaign_group_type` 返回 None 时跳过
- 提交结果未知时自动重提 → 禁止；只能人工核对
- 服务重启后自动恢复轮询 → 禁止；靠 `pending.task_id` 人工核对

## 常见误区

- **写入 pending ≠ 执行**：pending 是 LLM 分析结果落库，执行是另一条独立链路
- **confirm_status 已确认 ≠ 一定会执行**：还需 execute_status=PENDING + 安全开关全开
- **提交成功 ≠ 广告生效**：taskId 只代表受理；终态必须由后台轮询器确认
- **dry-run 返回 ok**：只说明计划构造成功，MCP 未调用；不写 task_id
- **新建和修改是不同 MCP 工具**：`agent_create_portfolio_campaign` vs `agent_async_batch_update_advert`
- **挪组失败不阻断其他调整**：匹配不到 portfolio 的活动仍会下发预算/Bid/状态/广告位修改
- **portfolioId 在 paramsVo 顶层**：不在 campaignVo 内层。按目标组拆分成多个 paramsVo 条目
- **`id` 不是 `portfolioId`**：`agent_query_portfolio_list` 返回同时有 `id`（内部 hash）和 `portfolioId`（Amazon Ads ID），只取后者
- **"10 worker" 是 Uvicorn 进程数不是轮询协程数**：轮询调度器是每进程 2 协程 + 20 队列；多进程全局上限 = 进程数 × 单进程值
- **清货优先不是独立执行路径**：`CONTROLLED_CLEARANCE` 只影响 LLM 分析阶段的策略上下文，执行时与正常模式走相同 `/campaign/confirm` → `submit_and_poll` 链路 — 交接文档 §13.4 中"清货优先无 taskId 轮询"已是 v3.24 以前的状态
