## 两种执行路径（关键区分）

项目存在两条独立的执行路径，对应不同 API 和不同调用方。

### 路径 A：`submit_execution()` — `/campaign/execute` 接口

```
调用方 → POST /campaign/execute   (前端"同意执行"不走此接口)
  → submit_execution(decision_id)
    → load_confirmed_pending(decision_id)   ← CONFIRMED + execute_status=PENDING
      → build_exec_plan()
        → _resolve_modify_portfolios()
          → agent_async_batch_update_advert
            → 回写 execute_status (IN_PROGRESS / FAIL / DRY_RUN)
```

- **入参**：`decision_id`（批次 ID）
- **数据源**：`confirm_status='CONFIRMED'`（需调用方先通过 `confirm_decisions` 标 CONFIRMED，当前无前端触发此路径）
- **DB 写入**：回写 `execute_status` + 写 `t_advert_agent_modify_advert_record`
- **当前状态**：接口存在但非前端主路径

### 路径 B：`submit_execution_direct()` — 新"同意即执行"（主路径）

```
前端"同意执行所选"按钮
  → codex_ux_patch.js 拦截 → 确认弹窗 → 二次点击
    → POST /campaign/confirm  (decision='approve')
      → submit_execution_direct(decision_id, card_ids)
        → load_pending_by_card_ids(decision_id, card_ids)  ← 不检查 confirm_status
          → build_exec_plan()
            → _resolve_modify_portfolios()
              → agent_async_batch_update_advert
                → _sync_pool_entries_from_exec 回写 execute_status='SUCCESS'
                  → 返回 { ok, ops, task_ids, errors, move_errors }
```

- **入参**：`decision_id` + `card_ids[]`（前端勾选的卡片 ID 列表）
- **数据源**：直接从 `t_advert_agent_modify_suggest_card` 按 `id IN (card_ids)` 拉取，**不检查 `confirm_status`**
- **DB 写入**：不写 confirm_status / record；`_sync_pool_entries_from_exec` 内回写 `execute_status='SUCCESS'`（仅 MCP 提交成功时）
- **特点**：合并"审核确认 + 执行"为一步，前端选了就下发

### 路径 B 的请求体

```json
POST /api/v1/agent/ad-direction/campaign/confirm
{
  "asin": "B0C58N3MWJ",
  "days": 7,
  "run_id": "dec_20260719_001",
  "decisions": [
    {"campaign_key": "card_001", "decision": "approve"},
    {"campaign_key": "card_002", "decision": "approve"}
  ],
  "operator": "tab5"
}
```

后端 `campaign_confirm()` 将 `decision='approve'` 的 card 收集为 `approve_ids`，调用 `submit_execution_direct(decision_id, approve_ids)`。

## 安全开关

| 配置项 | 类型 | 默认值 | 作用 |
|--------|------|--------|------|
| `advert_mcp_enabled` | `bool` | `False` | 执行总开关。为 `False` 时两条路径均在入口返回 `{"ok": false, "error": "..."}` |
| `advert_exec_dry_run` | `bool` | `True` | 空跑开关。为 `True` 时只构造计划并返回，不调 MCP |
| `advert_mcp_url` | `str` | `""` | Advert MCP 网关地址（`whpadvertapi.91cyerp.com/mcp`） |
| `advert_mcp_token` | `str` | `""` | Bearer token |
| `advert_mcp_timeout` | `float` | `120.0` | 单次 MCP 调用超时（秒） |
| `campaign_portfolio_enabled` | `bool` | — | 组合分类/挪组总开关。关闭时分析阶段不分类、执行阶段不挪组 |

**生产执行必须同时满足**：
- `advert_mcp_enabled = True`
- `advert_exec_dry_run = False`
- `advert_mcp_url` 和 `advert_mcp_token` 已配置

### 开关检查位置

- `advert_mcp_enabled`：`submit_execution()` / `submit_execution_direct()` / `execute_portfolio_budget()` 各自在入口第一行检查
- `advert_exec_dry_run`：`build_exec_plan()` 之后、MCP 调用之前检查；dry_run 模式返回 `{"ok": true, "dry_run": true}`
- `campaign_portfolio_enabled`：在 `_analyze_campaigns_impl` 中控制 `_classify_portfolio` 调用和 `_run_realloc` 执行

## 执行计划 `ExecPlan`

定义于 `advert_exec_mapper.py`，是 `build_exec_plan()` 的返回值，承载全部 MCP 调用参数和追踪元数据。

### 字段

| 字段 | 类型 | 用途 |
|------|------|------|
| `params_vo_list` | `list[dict]` | `agent_async_batch_update_advert` 入参。经 `_resolve_modify_portfolios` 按 portfolioId 拆分 |
| `create_calls` | `list[dict]` | `agent_create_portfolio_campaign` 逐 card 调用 |
| `negative_calls` | `list[dict]` | `agent_create_negative_keywords` 调用 |
| `ops` | `list[dict]` | 逐 pending 行的操作记录（用于回写 execute_status） |
| `warnings` | `list[str]` | 非致命告警（缺字段、跳过等），返回前端 |
| `move_errors` | `list[dict]` | 挪组失败详情，结构 `{campaign_id, campaign_name, group, reason}`，去重后前端弹 toast |

### `build_exec_plan()` 内部逻辑

1. 从 `pending["decision"]` 提取 `shop_id / parent_asin / parent_seller_sku`
2. 将 cards 按 `suggest_category == "CREATE"` 分为新建和修改两类
3. **新建活动**：逐 card 构造 `create_calls`（`agent_create_portfolio_campaign` 入参）
4. **否定词**：`keyword_pending` 中 negative 行聚合为 `negative_calls`
5. **修改已有活动**：按 `campaign_id` 聚合 campaign/keyword/placement pending 行为 `campaignVo`，汇入一个 `paramsVo` 条目。此时 `campaignGroupType` 来自 card 的 `campaign_group_type` 字段（ERP 码），暂存于 campaignVo 内部，**不传给 MCP**——后续由 `_resolve_modify_portfolios` 解析为 `portfolioId`

## Portfolio 解析（挪组核心）

挪组逻辑集中在 `_resolve_modify_portfolios()`（`advert_execution.py`）。

### 完整解析链

```
t_advert_agent_modify_suggest_card.campaign_group_type
  → "exact_core_group"  (ERP 码)
    → unmap_campaign_group_type()
      → "精准主力组"  (中文组名)
        → agent_query_portfolio_list  (查 MCP)
          → _normalize_portfolio_list(res)  (返回 list[dict]，非 list 直接 raise ValueError)
            → _match_portfolio("精准主力组", portfolios)
              → 命中 1 个: _pf_field(pf, "portfolioId")  ← 仅取此字段
                → 注入 paramsVo 顶层 "portfolioId"
```

### `_match_portfolio()` 匹配规则

- **单向子串匹配**：`g in nm`（组名必须是 portfolio 名的子串），不再反向匹配（`nm in g` 已删除）
- **必须唯一**：0 个匹配或 ≥2 个匹配均返回 `(None, match_count)`
- **取 portfolioId**：`_pf_field(pf, "portfolioId")`，**仅此一个字段**，不 fallback 到 `id`（内部 hash）或 `portfolio_id`

### 按 portfolioId 拆分 paramsVo

`build_exec_plan()` 构造时所有活动在**一个** `paramsVo` 条目中。`_resolve_modify_portfolios()` 按 `portfolioId` 拆成多个条目：

```
改前: paramsVoList[0]: { ..., campaignVoList: [活动A→主力组, 活动B→测试组, 活动C→主力组] }

改后: paramsVoList[0]: { ..., portfolioId: "169...", campaignVoList: [活动A, 活动C] }
       paramsVoList[1]: { ..., portfolioId: "145...", campaignVoList: [活动B] }
       paramsVoList[2]: { ..., campaignVoList: [活动D] }   ← 未匹配到任何组合，无 portfolioId
```

拆分时拷贝原条目的所有顶层字段（`shopId`/`parentAsin`/`currentUserId`/`adjustReason`/`decisionId` 等）。

### 三种结果

| 场景 | `campaignGroupType` | `portfolioId` | 其他调整字段 | `move_errors` |
|------|---------------------|---------------|-------------|---------------|
| 匹配成功 | **移除**（冗余） | 注入 paramsVo 顶层 | 原样保留 | 不写入 |
| 匹配失败（0/≥2/ID缺失） | **移除** | 不注入 | 原样保留继续下发 | 写入结构化错误 |
| `agent_query_portfolio_list` 查询失败 | **移除**（全部） | 不注入（全部） | 原样保留继续下发 | 不写入（仅一条 warning） |

核心原则：**挪组失败不阻塞预算/Bid/状态/广告位等其他调整**。

### `move_errors` 结构

```python
plan.move_errors.append({
    "campaign_id": "123456789",
    "campaign_name": "活动A",     # 从 plan.ops 按 campaign_id 反查
    "group": "精准测试组",         # 中文组名
    "reason": "存在多个",          # "不存在" | "存在多个" | "ID缺失"
})
```

活动名从 `plan.ops` 建立 `campaign_id → campaign_name` 映射获取，**不污染 campaignVo**（campaignVo 内不塞 `_name` 等内部字段）。

### 前端展示

`campaign_confirm()` 将 `move_errors` 扁平透传前端。`state.js` 按 `group + reason` 去重：

```js
const byGroup = {};
for (const e of moveErrors) {
  const key = `${e.group}\x00${e.reason}`;
  if (!byGroup[key]) byGroup[key] = { group: e.group, reason: e.reason, count: 0 };
  byGroup[key].count++;
}
// → sticky toast: "精准测试组存在多个，已跳过 8 个活动，不阻塞预算和bid修改。"
```

## 调用的 MCP 工具

全部指向广告执行网关 `whpadvertapi.91cyerp.com/mcp`（独立于 StarRocks 数据 MCP）。

| 工具 | 调用位置 | 类型 | 用途 |
|------|---------|------|------|
| `agent_query_portfolio_list` | `_resolve_modify_portfolios` / `_resolve_create_portfolios` / `execute_portfolio_budget` | 读 | 查 ASIN 下所有组合列表 |
| `agent_async_batch_update_advert` | `submit_execution` / `submit_execution_direct` / `execute_portfolio_budget` | 写 | 异步批量修改已有活动 |
| `agent_create_portfolio_campaign` | `submit_execution` / `submit_execution_direct` | 写 | 新建活动（可选含组合） |
| `agent_create_negative_keywords` | `submit_execution` / `submit_execution_direct` | 写 | 否定词/关键词 |
| `agent_batch_update_advert_result` | `advert_mcp_client.batch_update_result()` | 读 | 按 taskIds 查异步结果（已封装，主流程未 poll） |
| `agent_query_keyword_suggest_bid` | `advert_mcp_client.query_keyword_suggest_bid()` | 读 | 查建议竞价 |

**调用顺序**（`submit_execution_direct`）：
1. `agent_query_portfolio_list`（串行）→ 解析 portfolioId → 拆分 paramsVoList
2. `agent_async_batch_update_advert`（并行）∥ `agent_create_portfolio_campaign` × K（并行）∥ `agent_create_negative_keywords`（并行）

## 结果解析

### `parse_result_envelope(res)` → `(bool, str)`

判断 MCP 返回是否成功。当前实现遍历 dict key 查找 `*state`/`*msg`，**未识别格式时默认返回 `(True, "")` 即成功**——此项的风险已在 audit 中标记，尚未修复。

### `extract_task_ids(res)` → `list[str]`

从 MCP 返回提取异步 taskId。尝试多个 key 名并递归进 `data` 子对象。当前提交后不 poll 结果，`execute_status` 保持 `IN_PROGRESS`。

## 幂等边界

### 路径 A (`submit_execution`)

- `load_confirmed_pending()` 只取 `confirm_status='CONFIRMED'` AND `execute_status='PENDING'`
- 执行后回写 `execute_status`
- 已执行行不会被重复拉取

### 路径 B (`submit_execution_direct`)

- `load_pending_by_card_ids()` 不检查 `confirm_status`（card 和 pending 查询均无此条件）
- pending 查询有 `execute_status='PENDING'` 过滤——已执行过的不会被重复拉取
- MCP 提交成功后，`_sync_pool_entries_from_exec()` 回写 `execute_status='SUCCESS'`（`advert_execution.py:101-104`）
- 若上次执行时 MCP 提交成功但回写失败（DB 异常），`execute_status` 仍为 `PENDING`，**存在重复执行风险**

### 状态回写语义

| 路径 | 场景 | execute_status | 说明 |
|------|------|---------------|------|
| A + B | dry-run | `DRY_RUN` | 计划构造成功，未真实下发 |
| A | MCP 真跑提交成功 | `IN_PROGRESS` | `submit_execution` 异步 task 已提交 |
| A | MCP 真跑提交失败 | `FAIL` | `submit_execution` |
| B | MCP 提交成功 | `SUCCESS` | `_sync_pool_entries_from_exec` 异步补写（`advert_execution.py:101-104`） |
| B | MCP 提交成功但 DB 回写失败 | 残留 `PENDING` | `update_pending_execute_status` 异常被吞 |
| 通用 | mapper 跳过 | 不写 | 缺字段等情况不伪造成功 |

## Fallback 禁令

广告执行 MCP 链路严禁 fallback。凡涉及 MCP 工具入参/返回处理，取不到正确值就报错/跳过，不允许：
- 多个字段名逐个试取（如 `"portfolioId"` → `"id"` → `"portfolio_id"`）→ 已修复，仅取 `portfolioId`
- 信封 key 猜测（如 `"data"/"list"/"portfolioList"...`）→ 已修复，非 list 直接 `raise ValueError`
- `campaignGroupType` 兜底传给 MCP 自行解析 → 已删除
- 未知 group_code 原样透传 → 已修复，`unmap_campaign_group_type` 返回 None 时跳过

## 常见误区

- **写入 pending ≠ 执行**：pending 是 LLM 分析结果落库，执行是另一条独立链路
- **confirm_status 已确认 ≠ 一定会执行**：路径 B 完全不看 confirm_status；路径 A 还需 execute_status=PENDING + 安全开关全开
- **dry-run 返回 ok**：只说明计划构造成功，MCP 未调用
- **新建和修改是不同 MCP 工具**：`agent_create_portfolio_campaign` vs `agent_async_batch_update_advert`
- **挪组失败不阻断其他调整**：匹配不到 portfolio 的活动仍会下发预算/Bid/状态/广告位修改
- **portfolioId 在 paramsVo 顶层**：不在 campaignVo 内层。按目标组拆分成多个 paramsVo 条目
- **`id` 不是 `portfolioId`**：`agent_query_portfolio_list` 返回同时有 `id`（内部 hash）和 `portfolioId`（Amazon Ads ID），只取后者
