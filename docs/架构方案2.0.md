## 三、图编排：按广告运营工作流设计

### 3.1 核心原则

**节点按业务决策流程编排，不是按技术职能编排。** 运营做广告调整的真实顺序是：先看有没有特殊场景→定战略层参数→定广告目的→选关键词→定目标ACOS→定预算→选方向→出执行清单→校验→审核。图的节点就是这个顺序，一步一节点，层层递进。

**只有需要 LLM 推理的节点才进入 ReAct 循环。** 其余节点是确定性操作，不叫 Agent，直接执行。

### 3.3 节点详解

| # | 节点 | 类型 | 核心逻辑 | 是否有 LLM |
|---|------|------|---------|-----------|
| 1 | `load_data` | Service | 并行调 MCP 工具加载 ASIN 全量数据 + 4h 缓存 | 否 |
| 2 | `detect_scenario` | Service ★分支 | 8 种场景判定(acos_crisis/clearance/cold_start/rapid_growth/push_ranking/profit_harvest/stable_conversion/default) | 否 |
| 3 | `special_strategy` | Service | 特殊场景快速通道: 清货期→激进出价/acos_crisis→优先止血/cold_start→低预算测试 | 否 |
| 4 | `strategy_layer` | Service | 从 long_term_config 读战略层选择 → 从 YAML KB 匹配参数(ACOS上限/bid系数/允许方向) | 否 |
| 5 | `ad_purpose` | Service+LLM | 调 purpose-agent → 推荐广告目的(5选1-2) + 理由 | 是(单次) |
| 6 | `keyword_recommend` | Service+LLM | 调 purpose-agent → 推荐关键词类型 + 关键词列表 + 分类理由 | 是(单次) |
| 7 | `target_acos` | Service+规则 | TargetAcosRecommender 7步规则: 阶段范围→趋势修正→竞品修正→库存修正→相对变化限制→精度到1% | 否 |
| 8 | `budget_recommend` | Service+规则 | BudgetBidRecommender 6步规则: 当前消耗率→库存天数→阶段系数→趋势修正→竞品修正→相对变化限制 | 否 |
| 9 | `direction_recommend` | ★ReAct 子图 | 四方向评分+LLM推理+按需工具调用+方案生成 | 是(ReAct) |
| 10 | `decision_package` | Service | 组装: 选中方向→具体建议(否定词/bid调整/拓词)→优先级排序→执行步骤 | 否 |
| 11 | `validate` | Service | 18 条规则逐项校验 + 护栏检查 + 风险标记 | 否 |
| 12 | `human_review` | Interrupt | 展示完整方案+校验明细, 等运营 approve/modify/reject | 否 |

### 3.4 节点间的数据契约（层层递进）

```
load_data:
  产出 → asin_data {acos, cpc, cvr, keywords[...], competitors[...], inventory, ...}

detect_scenario:
  消费 ← asin_data + long_term_config
  产出 → scenario {id, north_star, alerts}

strategy_layer:
  消费 ← scenario + long_term_config + YAML KB
  产出 → strategy {product_stage, product_level, season_stage,
                   acos_tolerance, bid_coefficient, budget_coefficient,
                   allowed_purposes, disallowed_purposes}

ad_purpose:
  消费 ← strategy + asin_data + scenario
  产出 → ad_purposes [{purpose, confidence, reasoning}]

keyword_recommend:
  消费 ← ad_purposes + strategy + asin_data.keywords
  产出 → keyword_plan {keyword_types, recommended_kws[...], category_map}

target_acos:
  消费 ← strategy + asin_data + keyword_plan
  产出 → acos_target {value, reasoning_steps, manual_override}

budget_recommend:
  消费 ← strategy + asin_data + acos_target
  产出 → budget_plan {daily_budget, bid_suggestions, manual_override}

direction_recommend (ReAct):
  消费 ← 前方全部产出 + RAG检索
  产出 → direction_analysis {
            scores {push_natural/expand_keywords/optimize_acos/balance_maintain},
            priority_directions,
            per_direction_detail {reason, proposals, attention},
            overall_analysis,
            risk_warnings
          }

decision_package:
  消费 ← direction_analysis
  产出 → tasks [{priority, action, keyword, current_value, suggested_value, reason}]

validate:
  消费 ← tasks + direction_analysis + strategy
  产出 → validation {items[{rule_id, passed, message}], self_check_result}

human_review:
  消费 ← 全部产出
  产出 → decision {approved|modified|rejected, modifications?}
```

### 3.7 Agent vs Service 的定位变化

**旧方案**: 4 个 Agent（Data / Strategy / Analyst / Guardian）
**新方案**: 1 个 Agent（direction_recommend 的 ReAct 子图）+ 11 个 Service 节点

```
Service = 确定性操作 + 无 LLM + 无 checkpoint + 纯函数
Agent  = LLM 推理 + 工具调用 + ReAct 循环 + checkpoint
```

只在 direction_recommend 需要 ReAct——因为四方向分析天然是"拿到数据→发现异常→深入调查→修正判断"的迭代过程。前面的节点（查数、场景检测、战略层、关键词、ACOS、预算）都是确定性的，调一次就出结果，用 Service 足够。

### 3.9 图的编译

```python
# agents/graphs/asin_workflow.py

from langgraph.graph import StateGraph, END
from langgraph.checkpoint.sqlite import SqliteSaver

def build_asin_workflow() -> StateGraph:
    builder = StateGraph(AsinState)

    # 节点
    builder.add_node("load_data", load_data_node)
    builder.add_node("detect_scenario", detect_scenario_node)
    builder.add_node("special_strategy", special_strategy_node)
    builder.add_node("strategy_layer", strategy_layer_node)
    builder.add_node("ad_purpose", ad_purpose_node)
    builder.add_node("keyword_recommend", keyword_recommend_node)
    builder.add_node("target_acos", target_acos_node)
    builder.add_node("budget_recommend", budget_recommend_node)
    builder.add_node("direction_recommend", build_direction_recommend_subgraph())
    builder.add_node("decision_package", decision_package_node)
    builder.add_node("validate", validate_node)
    builder.add_node("human_review", human_review_node)

    # 边
    builder.add_edge(START, "load_data")
    builder.add_edge("load_data", "detect_scenario")

    # 场景分支
    builder.add_conditional_edges(
        "detect_scenario",
        route_scenario,
        {
            "special": "special_strategy",
            "normal": "strategy_layer",
            "end": END,
        }
    )

    builder.add_edge("special_strategy", "direction_recommend")  # 特殊场景跳过中间步骤

    # 正常流: 层层递进
    builder.add_edge("strategy_layer", "ad_purpose")
    builder.add_edge("ad_purpose", "keyword_recommend")
    builder.add_edge("keyword_recommend", "target_acos")
    builder.add_edge("target_acos", "budget_recommend")
    builder.add_edge("budget_recommend", "direction_recommend")

    # 后期: 执行清单 → 校验 → 审核
    builder.add_edge("direction_recommend", "decision_package")
    builder.add_edge("decision_package", "validate")

    builder.add_conditional_edges(
        "validate",
        lambda s: "human" if s["validation"]["self_check_result"] != "FAIL" else "direction_recommend",
        {"human": "human_review", "direction_recommend": "direction_recommend"}
    )

    builder.add_conditional_edges(
        "human_review",
        lambda s: s["human_decision"],
        {"approved": END, "rejected": END, "modified": "direction_recommend"}
    )

    return builder.compile(
        checkpointer=SqliteSaver.from_conn_string("ad-direction-agent/config/_langgraph/checkpoint.sqlite")
    )

def route_scenario(state: AsinState) -> str:
    sid = state["scenario"]["id"]
    if sid in ("acos_crisis", "clearance", "cold_start", "rapid_growth"):
        return "special"
    if sid == "no_action":
        return "end"
    return "normal"
```

## 四、特殊场景快速通道

### 4.1 为什么需要特殊通道

4 个特殊场景（acos_crisis / clearance / cold_start / rapid_growth）的决策逻辑和正常流程不同：

| 场景 | 正常流程的问题 | 特殊通道做什么 |
|------|-------------|-------------|
| `acos_crisis` | 逐层推荐太慢，ACOS>40% 必须立即止血 | 跳过中间步骤，direct_recommend 聚焦"哪些词在烧钱、怎么快速降ACOS" |
| `clearance` | 清货期不需要关注 ACOS/排名 | ACOS 容忍拉到 80%，方向聚焦"快速出清"，出价激进度按库存天数计算 |
| `cold_start` | 新品数据不足，大部份推荐无意义 | 聚焦"低预算测试→看数据→再决定"，Recommend 用默认参数不调 LLM |
| `rapid_growth` | 推进期需要快速决策 | 跳过 ACOS/预算的细粒度推荐，方向聚焦"加价+扩词"，批量处理 |

### 4.2 special_strategy 节点逻辑

```python
def special_strategy_node(state: AsinState) -> dict:
    sid = state["scenario"]["id"]
    data = state["asin_data"]

    if sid == "clearance":
        return {
            "strategy": {
                "acos_tolerance": 80,
                "bid_coefficient": max(0.6, 1.0 - (data.get("inventory_days", 30) / 60)),
                "allowed_purposes": ["清货型"],
            },
            "skip_nodes": ["ad_purpose", "keyword_recommend", "target_acos", "budget_recommend"]
        }

    if sid == "acos_crisis":
        return {
            "strategy": {
                "acos_tolerance": 40,
                "priority": "止血优先: 否定零转化词 + 降高出价",
            },
            "skip_nodes": ["ad_purpose", "keyword_recommend", "target_acos", "budget_recommend"]
        }

    # cold_start / rapid_growth 类似...
```

### 4.3 跳过机制

`special_strategy` 产出的 `skip_nodes` 字段告诉后续 Service 节点"我被跳过了，请用默认值"。`direction_recommend` 节点看到 `skip_nodes` 后调整 prompt：对于跳过节点，使用策略默认值而不是推荐值。

## 五、MCP 工具接入

### 5.1 现状与问题

StarRocks MCP Server 提供 **14 个原始工具**（见 .mcp.json），问题是：
- 参数锅炉板(parent_asin, parent_seller_sku, shop_account 每次都要传)
- 返回数据不可控(ad_keyword_report 一把返回 200 个关键词)
- 工具名与分析意图不匹配("查烧钱词" vs `ad_keyword_report(match_type=EXACT)`)

### 5.2 解决方案：11 个意图适配工具

不拆分 MCP 工具(14→30+)，也不直接用原始工具。中间加一层 **意图适配器**：

```
Analyst LLM 看到的 11 个工具          底层调用的 MCP 工具(不改)
(按分析师意图命名, 参数少, 返回精)    (按数据源, 不变)
─────────────────────────────        ──────────────────────────

get_ad_snapshot()                    → ad_product_report + product_sales
  → {acos, tacos, cpc, cvr, margin, spend}

get_keyword_heatmap()                → ad_keyword_report
  → TOP5高ACOS + TOP5高花费 + 零转化词计数

get_kw_detail(keyword)               → ad_keyword_report + keyword_child_asins
  → 单个词完整画像: bid/acos/cvr/rank/trend

list_wasteful_kw(min_spend)          → ad_keyword_report
  → 零转化词(limit 10)

check_placement()                    → ad_placement_report
  → TOS vs ROS 各 ACOS/CPC/花费占比

check_ranking_health(filter)         → keyword_child_asins × N
  → 排名变化>3位的词(limit 10)

get_trend(metric)                    → ad_product_report (daily)
  → 指定指标的日趋势点

list_expansion_candidates()          → flow_keywords + ad_search_term_report
  → 高转化未覆盖词(limit 10)

check_competitors()                  → direct_competitors + product_competitors_basic_info
  → 竞品价格/评分/BSR对比

search_term_report(keyword)          → ad_search_term_report
  → 指定搜索词明细(limit 10)

check_inventory()                    → product_sales
  → {可售库存, 可售天数, 断货风险}
```

### 5.3 实现方式

```python
# agents/tools/analysis_tools.py (~300行)

class AnalysisTools:
    """意图适配工具集。参数从 AsinContext 自动注入，LLM 只传业务参数。"""

    def __init__(self, ctx: AsinContext):
        self.ctx = ctx  # asin, seller_sku, shop, days 自动补全

    async def get_ad_snapshot(self) -> dict:
        product = await mcp_call("ad_product_report", **self.ctx.base_params())
        sales = await mcp_call("product_sales", **self.ctx.base_params())
        return {
            "acos": product.get("acos"), "tacos": sales.get("tacos"),
            "cpc": product.get("cpc"), "cvr": product.get("cvr"),
            "margin": sales.get("margin"), "daily_spend": product.get("spend") / self.ctx.days,
        }

    async def list_wasteful_kw(self, min_spend: float = 15) -> list[dict]:
        raw = await mcp_call("ad_keyword_report", **self.ctx.base_params(), match_type="EXACT")
        return [
            {"keyword": k["keyword"], "spend": k["spend"], "acos": k.get("acos", 0)}
            for k in raw.get("keywords", [])[:200]
            if k.get("spend", 0) >= min_spend and k.get("orders", 0) == 0
        ][:10]  # 硬限制 10 条

    # ... 其余 9 个工具同理
```

def build_kb():
    """将 unstructured/ 下的 Markdown 分块嵌入 ChromaDB"""
    chroma_client = chromadb.PersistentClient(path="kb/vector_store")
    collection = chroma_client.get_or_create_collection("ad_knowledge")

                embeddings=[embedding],
                metadatas=[{"source": str(md_file), "chunk": i, "title": chunk_title(chunk)}],
                ids=[f"{md_file.stem}:{i}"]
            )

### 7.2 各层实现

**短期记忆** — 零额外开发。LangGraph 的 SqliteSaver 已在图中启用，LLM messages 通过 `Annotated[list, add_messages]` 自动累积。

**中期记忆** — 见第八章数据库设计(`analysis_history`, `adjustment_logs`, `feedback` 表)。每次 `asin_workflow` 完成后，`finalize` 节点写入。

**长期记忆** — 两个组件：

1. **ASIN 画像**(JSON): `config/{ASIN}/profile.json`，聚合历史分析的关键指标趋势、典型场景、有效策略
2. **趋势向量嵌入**(ChromaDB): 将每个历史分析的场景+结果摘要嵌入向量库，新 ASIN 分析时检索 Top-3 相似历史案例，作为 RAG 上下文的一部分

```python
# memory/long_term.py

class LongTermMemory:
    def __init__(self, chroma_client, state_manager):
        self.chroma = chroma_client
        self.state = state_manager

    async def retrieve_similar_cases(self, asin: str, scenario: str, acos: float) -> str:
        """检索相似历史案例，注入 Analyst 的 Think prompt"""
        query = f"场景:{scenario} ACOS:{acos:.0f}% ASIN:{asin}"
        results = self.chroma.query(query_texts=[query], n_results=3)
        return format_case_context(results)

    async def update_profile(self, asin: str, analysis_result: dict):
        """分析完成后更新 ASIN 画像和趋势向量"""
        profile = self.state.get_profile(asin)
        profile["analysis_count"] = profile.get("analysis_count", 0) + 1
        profile["last_acos"] = analysis_result.get("acos")
        profile["typical_scenario"] = most_common_scenario(asin)
        self.state.save_profile(asin, profile)

        # 嵌入分析摘要
        case_summary = f"ASIN:{asin} 场景:{analysis_result['scenario']} ACOS:{analysis_result['acos']:.0f}% 方向:{analysis_result['priority_directions']} 效果:{analysis_result.get('outcome', 'unknown')}"
        embedding = await deepseek_embed(case_summary)
        self.chroma.add(documents=[case_summary], embeddings=[embedding], ids=[f"case:{asin}:{timestamp}"])
```

## 九、批量 ASIN 分析

### 9.1 执行模型

```
POST /api/v2/batch/jobs  {asins: ["A","B","C","D","E"], auto_confirm: true}
  → 202 Accepted {batch_id: "uuid"}
  → batch_supervisor.ainvoke()
  → init_batch Node
  → fan_out_to_asins() 返回 5 个 Send("asin_workflow", {asin: "A"}, ...)
  → LangGraph 引擎并行执行 5 个子图
  → 工具层 Semaphore 控制并发(Database:5, LLM:3)
  → 每个子图完成后返回结果到 aggregate
  → aggregate 汇总 → batch_jobs 状态更新 → Webhook 通知
```

### 9.2 并发控制

```python
# agents/tools/concurrency.py
db_semaphore = asyncio.Semaphore(5)      # 最多 5 个并行 DB 查询
llm_semaphore = asyncio.Semaphore(3)     # 最多 3 个并行 LLM 调用

# 工具函数内使用
async def get_ad_snapshot(self) -> dict:
    async with db_semaphore:
        return await self._do_query()
```

### 9.3 隔离保证(重申)

| 维度 | 隔离方式 |
|------|---------|
| State | 每个 Send 独立 AsinState 实例 |
| Checkpoint | thread_id = batch_id:asin, SqliteSaver 分区 |
| LLM messages | 每个子图独立累积(Annotated[list, add_messages]) |

## 十、组件解耦

### 10.1 分层依赖方向

```
API 层 ──→ 编排层 ──→ 核心域
                       ↑
                     工具层(一侧)
                     KB 层(一侧)
                     记忆层(一侧)
```

**依赖规则**：上层可以依赖下层，下层绝不依赖上层。核心域内部各组件只依赖协议(Protocol)，不依赖具体实现。

### 10.2 协议定义

```python
# core/protocols.py

class DataProvider(Protocol):
    """数据获取协议 — Data Agent 实现"""
    async def fetch(self, asin: str, days: int) -> ASINData: ...

class StrategyProvider(Protocol):
    """策略参数协议 — Strategy Agent 实现"""
    def match_params(self, tags: dict) -> dict: ...
    def detect_scenario(self, data: ASINData, params: dict) -> dict: ...

class AnalystProvider(Protocol):
    """分析协议 — Analyst Agent 实现"""
    async def analyze(self, data: ASINData, params: dict, scenario: dict) -> AnalystOutput: ...

class GuardianProvider(Protocol):
    """校验协议 — Guardian Agent 实现"""
    def validate(self, proposals: list[dict], context: dict) -> ValidationResult: ...

class ToolProvider(Protocol):
    """工具协议 — AnalysisTools 实现"""
    async def execute(self, tool_name: str, params: dict) -> dict: ...

class KnowledgeBase(Protocol):
    """知识库协议"""
    def structured_query(self, key: str) -> dict: ...       # YAML 查表
    def semantic_search(self, query: str, n: int) -> list[str]: ...  # RAG 检索

class MemoryStore(Protocol):
    """记忆存储协议"""
    async def save_analysis(self, result: dict) -> int: ...
    async def get_history(self, asin: str, limit: int) -> list[dict]: ...
    async def get_similar_cases(self, query: str, n: int) -> list[dict]: ...
    async def update_profile(self, asin: str, updates: dict): ...
```

### 10.3 依赖注入

```python
# agents/graphs/asin_workflow.py

def build_asin_workflow(
    data_agent: DataProvider | None = None,
    strategy_agent: StrategyProvider | None = None,
    analyst_agent: AnalystProvider | None = None,
    guardian_agent: GuardianProvider | None = None,
    tools: ToolProvider | None = None,
    kb: KnowledgeBase | None = None,
    memory: MemoryStore | None = None,
) -> StateGraph:
    """所有依赖通过参数注入，不硬编码 import。默认使用生产实现。"""
    data_agent = data_agent or DataAgent(DbAdapter())
    strategy_agent = strategy_agent or StrategyAgent(YamlKB(), ScenarioAnalyzer())
    tools = tools or AnalysisTools()
    kb = kb or HybridKB(yaml_path="kb/structured", chroma_path="kb/vector_store")
    memory = memory or MemoryStore(db_path="ad_agent.db")
    # ...
```

### 10.4 可替换性

| 组件 | 默认实现 | 可替换为 |
|------|---------|---------|
| DataProvider | DataAgent + DbAdapter + StarRocks MCP | MockDataAgent(测试) / RedshiftAdapter |
| KnowledgeBase | HybridKB(YAML + ChromaDB) | PGVector KB / Elasticsearch KB |
| MemoryStore | SQLiteMemory | PostgresMemory / RedisMemory |
| ToolProvider | AnalysisTools(MCP 14 工具) | MockTools(单元测试) |
| LLM Backend | DeepSeekClient | Claude API / 本地模型(vLLM) |

## 十三、关键设计决策

| # | 决策 | 选择 | 理由 |
|---|------|------|------|
| 1 | Agent 数量 | **4** (Data/Strategy/Analyst/Guardian) | Supervisor 退化为固定边，不需要单独 Agent |
| 2 | Analyst 推理 | **真 ReAct** (Think→Act→Observe 循环) | 不是生成→校验→重试；每次工具调用获取新信息，可能改变推理方向 |
| 3 | MCP 工具 | **意图适配层 11 个** 包装原始 14 个 MCP | 不拆分原始工具，不改 MCP Server；只改 Agent 看的接口 |
| 4 | 知识库 | **双层** (YAML 结构化 + ChromaDB 向量) | YAML 给 Strategy 确定性查表；RAG 给 Analyst 语义增强 |
| 5 | RAG 嵌入 | **DeepSeek Embedding API** | 与 LLM 同供应商，降低集成复杂度 |
| 6 | 记忆 | **三层** (Checkpoint + SQLite + 向量画像) | LangGraph 管短期；SQLite 管历史；ChromaDB 管相似案例 |
| 7 | 数据库 | **SQLite → PG 渐进** | Phase 1-3 SQLite 单文件零运维；Phase 4+ PG 生产级 |
| 8 | 批量 | **batch_supervisor Send 扇出** | 同一 asin_workflow 子图复用；LangGraph 原生并发；Semaphore 限流 |
| 9 | 解耦 | **Protocol + 依赖注入** | 每个 Agent/工具/KB/记忆 可独立测试、可替换实现 |
| 10 | Checkpoint | **SqliteSaver** P0→P3；评估 Redis P4+ | 单机够用；多 worker 前切换 |
| 11 | Demo 兼容 | **v1 API 转发 v2** | 不破坏现有前端；URL 不变 |
| 12 | ERP 接入 | **异步 Job + Webhook** (轮询兜底) | 全链路 >60s，不适合同步 HTTP |
