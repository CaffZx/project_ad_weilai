## 1. 四条结构性约束（v3.4.0 立三条，v3.4.2 补第四条，不可违反）

v3.3.0 的 14 项规则冲突中有 9 项源于同一数值在多个文件里各自表述后漂移。v3.4.0 用三条硬约束消除这个来源。**新增或修改任何知识库文件前，先确认不违反这三条。**

### 约束 1：单一数值来源

任何阈值只在 **一个** 文件里定义一次，其他文件只能引用编号，**不得复述数值**。

| 数值类型 | 唯一权威文件 | 其他文件的正确写法 |
| --- | --- | --- |
| 标签维度的枚举值 | `02-标签维度定义.md` | 「按 02号§N 的枚举」 |
| 所有阈值数字 | `03-阈值参数.md` | 「按 03号§N」 |
| Bid / 预算 / ACOS 容忍的约束值与公式 | `执行规则/15-策略约束值规则.md` | 「按 15号§N 计算」 |
| 调整幅度的基础值 | `执行规则/19-执行层数值规则.md` | 「按 19号§N 的基础幅度」 |
| 术语定义 | `14-名词定义.md`（核心词除外，见 `29号`） | 「按 14号§N 的定义」 |
| 动作码与生命周期 | `30-动作词表与映射.md` | 「按 30号 的 action_code」 |

> 违反示例（v3.3.0 实际存在）：淘汰花费门槛在 05号 写 `$10`、在 21号 与 18号 写 `$15`。
> 正确做法：只在 03号 定义一次，05/18/21 全部改为「按 03号§7 的淘汰花费门槛」。

### 约束 2：单一动作词表

`30-动作词表与映射.md` 是 action_code 的唯一权威表。以下四处必须从它派生，不得各自定义：

1. `app/domain/advertising.py` 的 `ActionType`（物理码）
2. `12-输出规范.md` 的 `action_type` 枚举（业务码）
3. `ontology/actions.yaml` 的 actions 键
4. ERP 写入映射（`app/persistence/erp_writer/mappers.py`）

### 约束 3：切片全覆盖

每个知识库文件必须满足以下之一，否则视为规则悬空：

- **A. 已纳入至少一个 prompt 切片**（见 §4 覆盖矩阵）
- **B. 显式标注 `reference_only`**（人读文件，不进模型），且不被其他文件当作运行时口径引用

`tests/test_kb_slicing.py` 中的 `test_every_kb_file_is_covered_or_reference_only` 强制校验此约束。

### 约束 4：无死资产（v3.4.2 新增）

**前三条只管知识库，代码这一半一直没有任何约束** —— 于是「写了模块」和「模块生效」
之间没有闸门。外部评审实测发现：v3.4.0 声称把 ontology 从死件变为可执行资产（C-01），
但 `OntologyValidator` 从生产入口不可达；v3.4.1 又新增了 5 个同样不可达的模块。
这与 v3.3.0「ontology YAML 从未被加载」是**同一个失效模式**，只是死件从 YAML 换成了 Python。

任何新增的模块、领域枚举、模型字段、动作码，必须满足以下之一：

- **A. 在生产链路可达** —— 从 `app.main` 出发的 import 图能到达它，且有真实消费点；
- **B. 在交接文档 §0.1 断链清单显式登记为「待接线」**，并写明**接线前的真实行为**
  （不是写「待接入」，而是写「现在它完全不生效，因此 XX 规则不执行」）。

`tests/test_no_dead_assets.py` 强制校验此约束：可达性分析 + 断链账本比对，
账本**只允许变短**。

> **为什么必须机械化**：§13「必须同步更新五项」和 v3.3.0 那句「必须同步更新 ontology」
> 是同一种空承诺。约束 3 的价值不在文字而在 `test_kb_slicing` 会失败；
> 约束 4 同理 —— 价值全在那个会失败的测试上。
>
> **判据为什么用「可达」而不是「有没有人 import」**：后者会把
> `attribution_maturity`（被 `ontology_validator` import，而后者自己是死的）
> 误判为已接线。v3.4.1 的自查就是这么得出错误结论的。

## 7. 维护规则

修改本知识库时，以下五项必须同步，缺一不可（这是 v3.3.0 的失效点：只改 Prompt 或只改阈值文件）：

1. `app/domain/` 与 `app/models/` 的领域枚举与模型
2. 对应的知识库切片文件，以及本文 §4 的覆盖矩阵
3. `ontology/` 对应 YAML 与 `OntologyValidator` 的校验规则
4. `12-输出规范.md` 的输出字段与 ERP 映射（`erp_writer/mappers.py`）
5. 测试与 `01_交接说明/广告Agent改造交接文档_v3.4.1.md` 的验收清单

**新增动作的强制前置**：任何新动作必须先在 `30号` 注册（业务码、物理码、对象范围、是否增长型、必需证据、失败语义、生命周期），再接入执行链路。未注册的动作码由 `OntologyValidator` 直接 BLOCKED。
