# 广告组合与预算分配规则

> 本文件用于补充广告组合（预算控制层）与广告活动（执行层）之间的关系。  
> 适用场景：父 ASIN 下活动数量较多，单个 Campaign 调整后需要回算组合预算和父 ASIN 总预算，避免活动层预算看似合理但整体预算失控。

---

## 1. 核心问题

父 ASIN 下活动较多时，仅看活动层预算会整体失控：活动预算相加可能超父目标、淘汰释放的预算没被回收、三组之间缺少二次分配。因此需要增加一层预算控制对象：

```text
ParentASIN
  └── AdBudgetGroup（广告组合 / 预算组合）
        └── Campaign（广告活动）
```

---

## 2. 对象定义

### 2.1 ParentASIN

父 ASIN 是广告预算总盘的控制主体。

| 字段 | 说明 |
| --- | --- |
| `parent_asin` | 父 ASIN |
| `parent_target_daily_budget` | 父 ASIN 目标日预算 |
| `current_total_group_budget` | 当前组合预算总和 |
| `proposed_total_group_budget` | 建议组合预算总和 |
| `net_budget_change` | 本轮调整后的净预算变化 |

### 2.2 AdBudgetGroup

广告组合是父 ASIN 下的预算控制层。

> 注意：本文中的广告组合可以映射到 Amazon Portfolio、ERP 广告组合，或内部预算分组。  
> 它的核心作用是控制预算，不替代 Campaign 执行动作。

| 字段 | 说明 |
| --- | --- |
| `group_id` | 组合 ID |
| `group_name` | 组合名称 |
| `group_type` | 组合类型 |
| `current_group_budget` | 当前组合预算 |
| `proposed_group_budget` | 建议组合预算 |
| `group_budget_delta` | 组合预算变化 |
| `campaigns` | 组合下包含的活动 |

### 2.3 Campaign

Campaign 是广告动作执行层。

| 字段 | 说明 |
| --- | --- |
| `campaign_id` | 活动 ID |
| `campaign_name` | 活动名称 |
| `campaign_type` | exact_keyword / broad_keyword / phrase_keyword / auto_discovery |
| `current_daily_budget` | 当前活动日预算 |
| `proposed_daily_budget` | 建议活动日预算 |
| `campaign_budget_delta` | 活动预算变化 |
| `belongs_to_group` | 所属广告组合 |

## 3. 组合类型定义

> **v3.4.3：四组**（v3.4.0 曾为五组）。商品定投收回为 `auto_broad_group` 内的逻辑子桶，见 §8.5。
> 五组的完整定义见 `02号§9`，本节聚焦预算分配语义。

第一期组合不要拆太细，建议固定为以下四类。

| group_type | 组合名称 | 核心目的 | 活动类型限制 | 预算特征 |
| --- | --- | --- | --- | --- |
| `exact_core_group` | 精准主力组 | 承接已经连续验证的精准活动。 | **仅精准广告（EXACT）** | 预算由经营目标和组合约束决定，预算高低不代表已经验证 |
| `exact_testing_group` | 精准测试组 | 验证单关键词精准活动是否值得持续经营。 | **仅精准广告（EXACT）** | 未通过连续3日验证即留在本组 |
| `auto_broad_group` | 广泛自动组 | 以低Bid获取探索流量和有效搜索词；商品定投作为本组逻辑子桶承接商品/类目投放。 | **Auto / Broad / Phrase / Product Targeting** | 不因预算大小改变组合；商品定投子桶保留 PP 权限 |
| `low_bid_retention_group` | 低价捡漏组 | 精准活动退出后的超低成本保留池。组合预算固定 $1，Bid = `min(current_bid, $0.20)`。 | **仅精准广告（EXACT）** | 不计入父ASIN正常经营预算 |

### 3.1 组合判定规则

| 判定条件 | 归属组合 |
| --- | --- |
| campaign_type = `broad_keyword` / `phrase_keyword` / `auto_discovery` | 广泛自动组 |
| campaign_type = `exact_keyword` 且为多关键词活动 | 低价捡漏组 |
| campaign_type = `exact_keyword`，连续过去3个完整站点自然日每日实际花费均严格大于 $5，且3日汇总ACOS低于目标ACOS，且近7天自然排名较前一个7天周期提升 | 精准主力组 |
| campaign_type = `exact_keyword` 且尚未通过上述验证 | 精准测试组 |
| 单关键词精准活动命中退出/淘汰规则 | 低价捡漏组 |

### 3.1A 全局广告目标与预算优先级

广告整体目标是推出词的自然位和自然流量，不只是精准测试组升入精准主力组时才考虑自然排名。所有预算增加、预算挪移、升组筛选、预算不足压缩和二次分配，都必须优先服务自然流量增长。

当多个活动同时表现较好、但预算不能全部满足时，不得只看“自然排名上升位数”。Agent 必须先计算 `natural_traffic_priority_score`，优先给分数最高的活动分配预算。

```yaml
natural_traffic_priority_score:
  formula: search_volume_score * 3
         + current_position_score * 3
         + page_uplift_score * 3
         + relevance_score * 2
         + acos_score * 1
```

评分规则：

| 评分项 | 5分 | 4分 | 3分 | 2分 | 1分 | 0分 |
| --- | --- | --- | --- | --- | --- | --- |
| `search_volume_score` | 搜索量 Top 20% 或明显大流量词 | - | 搜索量 Top 20%–50% | 搜索量缺失但词高度相关 | 低搜索量词 | - |
| `current_position_score` | 第1页 / Top20 | 第2页 / Top21–40 | 第3页 / Top41–60 | 第4–5页 | 第6页以后 | 无自然排名 |
| `page_uplift_score` | 本轮进入第1页 / Top20 | 本轮进入第2页 | 本轮进入第3页 | 仍在第4页以后但有上升 | 轻微上升但仍无有效流量位置 | 无上升或下滑 |
| `relevance_score` | 核心精准词，直接对应产品主卖点 | 强相关长尾词 | 中相关词 | 弱相关但可观察 | 泛词 / 相关性低 | 明显不相关 |
| `acos_score` | ACOS ≤ 目标 ACOS | - | ACOS ≤ 有效容忍上限 | - | ACOS 接近容忍上限且有订单 | ACOS 超容忍上限或无转化支持 |

执行说明：

- 预算优先给 `natural_traffic_priority_score` 最高的活动。
- 不得仅因某词从第7页升到第4页，就优先于从第2页升到第1页的词；后者通常能带来更高自然流量。
- 不得仅按排名提升幅度判断。10万搜索量词和2万搜索量词，同样提升一页，带来的自然流量不同。
- ACOS 是成本约束，不是第一优先级。只要 ACOS 在有效容忍范围内，应优先考虑自然流量机会、搜索量和词精准度。
- 若关键字段缺失（搜索量、自然位、相关性、ACOS），不得自动大幅加预算；输出 `MANUAL_REVIEW` 或小预算观察。
- 不得因为多个活动都表现好，就平均加预算；平均加预算会稀释推词预算，削弱自然位推进效果。

### 3.1B 精准测试组预算与升组筛选规则

精准测试组是验证池，不是精准主力组的低预算版本。活动预算达到任何金额都不能代替连续3日验证。

| 规则 | 内容 |
| --- | --- |
| 精准测试组预算豁免 | 精准测试组用于小预算验证，通常活动预算为 $1–$4.99；不套用 `15-策略约束值规则.md §2.1` 的存量活动预算范围，只受活动预算硬下限、硬上限和父 ASIN 总预算护栏约束。 |
| 升组验证门槛 | 只有连续3个完整站点自然日每日实际花费均严格超过 $5，3日汇总ACOS低于目标ACOS，且近7天自然排名较前一个7天周期提升，才进入精准主力组。 |
| 升组筛选原则 | 不是每个精准测试活动都加预算。升组和加预算统一遵循 §3.1A 的全局广告目标与预算优先级；其余测试活动维持小预算观察或压缩。 |
| 预算不足时 | 优先保证已经验证且仍有真实消耗能力的对象；不得通过平均加预算制造“主力”活动。 |
| 低价捡漏组预算豁免 | 低价捡漏组不套用15号文件的存量活动预算范围；活动层预算固定 $1，Bid = `min(current_bid, $0.20)`；组合层是父 ASIN 下的低价捡漏组合总预算，固定 $1。 |

### 3.2 优先级规则

当多个条件同时命中时，按以下顺序判定：

```text
广泛流硬路由 > 多关键词精准进入低价捡漏 > 单关键词精准验证状态
```

说明：

- Broad / Phrase / Auto 始终属于广泛自动组，不能进入低价捡漏组。
- 多关键词精准活动确定性进入低价捡漏组。
- 单关键词精准活动通过连续3日验证后进入精准主力组，否则留在精准测试组。
- 组合身份不再随本轮建议预算跨越某个金额而改变。

### 3.3 组合可为空规则

不是每个父 ASIN 都必须同时存在精准主力组、精准测试组、广泛自动组和低价捡漏组。

| 场景 | 组合存在逻辑 |
| --- | --- |
| 新品起步，尚未跑出有效词 | 可能只有广泛自动组，例如总预算 $20 全部用于 Auto / Broad / Phrase 探索，此时无精准主力组和精准测试组，属正常状态 |
| 已有词在精准主力组消耗预算 | 精准测试组和广泛自动组不得因扩张挤占精准主力组预算，精准测试组预算优先压缩 |
| 没有低价捡漏活动 | 低价捡漏组可以不存在；一旦存在，组合预算固定 $1，不参与预算分配 |

### 3.4 广泛跑出有效词 → 新建精准测试活动

当父 ASIN 广泛自动组中出现有效信号时，Agent 应识别并建议新建精准活动进入精准测试组。数据来源不限于搜索词报告，也包括同词根下的词根级验证。

**信号一：搜索词报告直接信号**

| 判断条件 | 说明 |
| --- | --- |
| 该搜索词 7 天有效订单 ≥ 3 单 | 有真实出单验证 |
| 该搜索词 7 天 ACOS ≤ 目标 ACOS | 花费效率达标 |
| 尚无对应精准活动 | 避免重复建活动 |

满足以上全部条件 → Agent 建议新建该搜索词的 Exact 精准活动，初始预算按 `16号§2`，进入**精准测试组**。
审核等级 `MANUAL_REVIEW`。

**信号二：同词根验证信号**

当某个词根下，多个搜索词合计表现达标时，可新建以该词根为核心的精准活动：

| 判断条件 | 类型 | 说明 |
| --- | --- | --- |
| 同一词根下搜索词合计 7 天有效订单 ≥ 3 单 | 性能条件（满足其一即可） | 词根整体有出单验证 |
| 合计 ACOS ≤ 目标 ACOS | 性能条件（满足其一即可） | 词根整体效率达标 |
| 尚无精准活动承接该词根 | 前提条件（必须满足） | 避免重复建活动 |

满足前提条件 + 任一性能条件 → Agent 建议新建以该词根为目标的 Exact 精准活动，初始预算 < $5，进入**精准测试组**。

**信号三：CVR 通道（v3.4.0 新增，C-13）**

覆盖「点击多、CVR 达标、订单差一两单」的真实好词——纯订单门槛会把它们永久留在广泛里
与无关词共享预算和 Bid。

| 判断条件 | 说明 |
| --- | --- |
| CVR > 品类均值 × 0.8 | 已证明承接能力（`03号§4` Ranking 段的品类 CVR 基准） |
| 7天花费 ≥ `03号§7.3` 的无单花费门槛 | 样本量下限，防止「点击 20 次出 1 单 = CVR 5%」的假信号 |
| 尚无对应精准活动 | 避免重复建活动 |
| 相关性达 R1（`28号§2`） | 相关性前提 |

满足以上全部条件 → 新建 Exact 精准活动，进入**精准测试组**，
**审核等级强制 `HIGH_RISK_REVIEW`**（样本量风险由人工兜底）。

> 三个信号均可独立触发建活动，不需要同时满足。

### 3.5 活动升入精准主力组的触发条件

精准测试组中的精准活动，满足以下**全部条件**时，Agent 建议将该活动升入精准主力组：

| 条件 | 说明 |
| --- | --- |
| 活动类型 = `exact_keyword` 且为单关键词活动 | 仅单关键词精准活动可进入精准主力组 |
| 连续过去 3 个完整站点自然日（**成熟窗：T-3/T-4/T-5，不是 T-1..T-3**，见 `03号§12.2` 成熟窗定义），每日实际花费均**严格大于**门槛 | 门槛 = **固定 $5.00** |
| 3日**汇总** ACOS < 目标 ACOS | 汇总口径，**不是**日 ACOS 平均值 |
| 近7天自然排名较前一个7天周期提升 | 必要准入条件；自然位数据缺失或窗口不完整时转 `MANUAL_REVIEW` |
>
> **判定性质 `admission_only`**：三日验证只在准入时判定，已在主力组的活动不因门槛变化
> 被自动降级；降级只走 `32号§2` 的三级回落。

广告整体目标是推出词的自然位和自然流量。当多个精准测试活动同时满足升组条件时，按 §3.1A 的 `natural_traffic_priority_score` 筛选，不得全部平均加预算：

| 优先级 | 判断标准 |
| --- | --- |
| 第1优先 | `natural_traffic_priority_score` 最高 |
| 第2优先 | 分数接近时，优先当前自然位更接近第1页 / Top20 的词 |
| 第3优先 | 再优先词更精准 / 相关性更强的词 |
| 第4优先 | 最后比较 ACOS、订单数、CVR 等成本和转化指标 |

预算不足时，只允许优先级最高的少数活动升入精准主力组，其余活动继续留在精准测试组小预算观察。

> Broad / Phrase / Auto 永远在广泛自动组；精准活动也不能仅凭预算金额升入主力组。

### 3.6 精准主力组保护触发规则

**精准主力组保护规则（GROUP-BUDGET-004）只在父 ASIN 预算不够分配时触发。**

如果 `available_reallocation_budget >= requested_increase_budget`，说明本轮可分配预算足够覆盖精准主力组、精准测试组和广泛自动组的全部请求，则 GROUP-BUDGET-004 不需要介入压缩，直接按各组合 requested_delta 执行。

当 `available_reallocation_budget < requested_increase_budget` 时，再判断精准主力组是否有实际花费，并据此决定压缩顺序。

这覆盖以下所有场景：
- 测试阶段：精准主力组尚未建立
- 测试→推进期过渡：精准主力组建立但数据不稳定、花费为 $0 或极低
- 推进期中：某些关键词表现回落，精准主力组短期花费萎缩

| 精准主力组状态 | 判断标准 | 预算规则 |
| --- | --- | --- |
| **精准主力组无实际花费** | 精准主力组为空，或精准主力组所有活动 7 天花费 = $0 | 即使预算不足，GROUP-BUDGET-004 暂不生效；精准测试组 + 广泛自动组按 §7 分配 |
| **精准主力组有少量花费** | 精准主力组存在活动且 7 天花费 > $0 但 < $5 | 仅在预算不足时轻度生效：精准主力组预算优先保障，但精准测试组无需大幅压缩 |
| **精准主力组有稳定花费** | 精准主力组 7 天花费 ≥ $5 且有出单 | 仅在预算不足时完全生效：精准主力组不得断供，精准测试组优先压缩，广泛自动组次之 |

> 产品阶段标签（testing / pushing）仅影响 Bid 和预算幅度系数（见 15号文件），不决定精准主力组保护是否生效。
> 保护是否介入，先看父 ASIN 预算是否不够分配，再看精准主力组当前是否有实际花费。

### 3.7 精准主力组活动降级路径

精准主力组内活动数据回落时，按以下三级处理：

| 回落程度 | 判断标准 | 处理方式 |
| --- | --- | --- |
| 轻度回落 | ACOS超标但仍有出单 | 留在精准主力组，按目标ACOS约束降Bid/降预算观察 |
| 中度回落 | 持续ACOS超标且出单极少 | 回落到精准测试组，重新完成连续3日验证 |
| 严重回落 | 在精准测试组内走完低价捡漏前诊断路径（7天无改善） | 进入低价捡漏组 |

> 从精准主力组回落到精准测试组不是低价捡漏，是重新验证。
> 后续数据恢复时，仍需重新满足连续3日验证，不能用预算恢复代替验证。

## 4. 预算控制层级

预算控制按三层回算：

```text
父 ASIN 总预算
  ↓
广告组合预算
  ↓
Campaign 活动预算
```

### 4.1 核心原则

| 规则 | 内容 |
| --- | --- |
| GROUP-BUDGET-001 | Campaign 预算调整后，必须回算所属组合预算。 |
| GROUP-BUDGET-002 | 组合预算调整后，必须回算 ParentASIN 总预算。 |
| GROUP-BUDGET-003 | 转入低价捡漏释放的预算发生在 Campaign 活动层，不以低价捡漏组组合预算作为释放来源。 |
| GROUP-BUDGET-004 | 当父 ASIN 预算不够分配时，精准主力组不得因精准测试组或广泛自动组扩张而断供。 |
| GROUP-BUDGET-005 | 低价捡漏组组合预算固定 $1，Bid = `min(current_bid, $0.20)`，不参与预算增加和二次分配。 |
| GROUP-BUDGET-006 | 所有预算增加和预算挪移均遵循全局广告目标，优先给 `natural_traffic_priority_score` 最高的活动。balance_maintain 类活动最后，预算紧张时可不加。 |
| GROUP-BUDGET-007 | Agent 每次调整前必须判断瓶颈层级：组合利用率=100% 且活动平均利用率<80%，说明组合是瓶颈，不得调整单个活动预算，应先提升组合预算。 |
| GROUP-BUDGET-008 | 精准主力组内预算集中规则：① 活动层：balance_maintain / profit 方向的活动，若预算利用率低且自然位无有效提升，17号规则不对其加预算，预算自然向 `natural_traffic_priority_score` 高的 ranking push 活动集中；② 当高分 ranking push 活动预算已满但组合预算仍紧张时，执行内部挪移：将利用率<50%的非ranking活动压缩至实际花费×1.3，释放给高分 ranking push 活动。 |
| GROUP-BUDGET-009 | 父 ASIN 总预算需要降低时，各组合按当前预算占比等比例压缩，维持原有结构比例不变。精准主力组内的ranking push保护（GROUP-BUDGET-006/008）在组合层等比例降低后，仍在组内层面继续生效。 |

### 4.2 Campaign 预算总和与真实预算

Campaign 日预算是上限，不等于实际花费。

因此：

```yaml
campaign_budget_sum:
  can_exceed_parent_target_budget: true
  reason: 多数活动实际花费低于日预算，Campaign 预算总和不等于真实花费
  must_control_by:
    - parent_target_daily_budget
    - group_budget
    - expected_spend
```

Agent 不得只用 Campaign 预算总和判断是否超预算，必须结合组合预算和父 ASIN 目标预算判断。

### 4.3 活动预算总和与组合预算的健康比例

组合预算是当天总花费上限，一旦触达，组内所有活动当日全部停止，不管单个活动预算剩余多少。因此活动预算总和与组合预算的比例过高时，会造成策略失控。

| 比例状态 | 判断标准 | 处理方式 |
| --- | --- | --- |
| 可执行 | 活动总和 ≤ 组合预算 × 2.0 | 允许超配；例如组合预算 $100 时，活动预算总和不得超过 $200 |
| **本轮跨越** | 调整前 ≤ 2.0，调整后 > 2.0 | **BLOCKED**（`GROUP-010`）。本轮动作自己造成的越界必须拦 |
| **存量已超** | 调整前已 > 2.0 | **MANUAL_REVIEW**（`GROUP-010`），且本轮**只允许输出降预算动作** |

> 组合花到上限后当日关停所有活动。活动花了 $10 就停了，Agent 看到利用率 33% 会误判"花不出去"。必须先查组合利用率，再决定是否调整活动层。
>
> 瓶颈判断：组合利用率 100% 且活动平均利用率 < 80% → 瓶颈在组合层，提升组合预算；活动利用率 100% 且组合利用率 < 80% → 瓶颈在活动层，正常调整；两者均 ≈100% → 提升父 ASIN 总预算。

### 4.4 精准主力组内预算挪移规则（自然流量优先）

当精准主力组内有活动命中 `push_natural_rank + RANK_OPPORTUNITY`，但组合预算受限时，按以下顺序执行：

**Step 1：识别可释放活动（组内挪移来源）**

| 条件 | 说明 |
| --- | --- |
| 广告方向 = `balance_maintain` 或 `profit` | 不需要放量的活动 |
| 活动预算利用率 < 50% | 有多余预算未花完 |
| 释放金额 = 当前预算 - 实际花费 × 1.3 | 保留30%缓冲，不全砍 |

**Step 2：识别优先增加活动（组内挪移目标）**

按以下优先级排序：

| 优先级 | 判断标准 |
| --- | --- |
| 第1优先 | `natural_traffic_priority_score` 最高 |
| 第2优先 | 分数接近时，优先当前自然位更接近第1页 / Top20 的词 |
| 第3优先 | 再优先词更精准 / 相关性更强的词 |
| 第4优先 | 最后比较 ACOS、订单数、CVR 等成本和转化指标 |

**Step 3：执行顺序**

```
Step 3-1  从可释放活动砍预算，汇入挪移池
Step 3-2  按优先级依次补给 ranking push 活动，每个活动不超过其 requested_delta
Step 3-3  若挪移池仍不足 → 提升组合预算
Step 3-4  若组合预算提升后仍不足 → 提升父 ASIN 总预算
```

> **核心原则：广告的核心目的是推出词的自然位和自然流量，不是词越多越好。**
> 预算流向始终优先给 `natural_traffic_priority_score` 最高的活动，其余活动让位。

## 5. 本轮预算变化计算

每次广告调整后，先在 Campaign 层计算预算变化。

```yaml
campaign_budget_delta = proposed_daily_budget - current_daily_budget
```

然后按组合汇总非低价捡漏组、且本轮未转入低价捡漏的活动预算变化：

```yaml
group_requested_delta =
  sum(campaign_budget_delta of campaigns in group
      where campaign not moved_to low_bid_retention_group)
```

转入低价捡漏的活动单独计算释放预算：

```yaml
low_bid_retention_release =
  sum(current_daily_budget - 1 for campaigns moved_to low_bid_retention_group)
```

说明：

- 低价捡漏组组合预算永远固定 $1，不参与预算增加，也不作为一个“释放预算的组合”参与比例分配。
- 释放预算来自精准 Campaign 活动层：活动从精准主力组或精准测试组转入低价捡漏组时，活动日预算降到 $1。广泛、词组、自动停止投放时释放预算，但不迁入低价捡漏组。
- 例如某精准测试活动当前预算 $8，本轮转入低价捡漏组后，活动层 proposed_daily_budget = $1，释放预算 = $8 - $1 = $7；低价捡漏组组合层 group_delta 仍然为 0。
- 本轮转入低价捡漏的 Campaign 只能计入 `low_bid_retention_release`，不得再计入原组合的负向 `group_requested_delta`，也不得计入 `other_campaign_budget_decrease`，避免同一笔释放预算被重复计算。

最后得到父 ASIN 级别净变化：

```yaml
requested_increase_budget =
  sum(positive group_requested_delta)

released_budget =
  low_bid_retention_release
  + other_campaign_budget_decrease

# other_campaign_budget_decrease 只包含仍留在原组合内的降预算活动，
# 不包含本轮 moved_to low_bid_retention_group 的活动。

net_required_increase =
  requested_increase_budget - released_budget
```

### 5.1 预算变化类型

| 类型 | 说明 |
| --- | --- |
| `positive_delta` | 本轮需要追加的预算 |
| `negative_delta` | 本轮释放或回收的预算 |
| `net_delta` | 正负抵扣后的净预算变化 |

示例：

```yaml
campaign_changes:
  existing_campaign_increase: +20
  low_bid_retention_release: 20
  new_campaign_budget: +10

net_required_increase: +10
```

## 6. 预算挪移与二次分配逻辑

### 6.1 基础逻辑

预算重分配先看本轮动作产生的预算变化，而不是先强行给每个组合固定比例。

处理顺序：

```text
Step 1：计算精准主力组、精准测试组、广泛自动组的 requested_delta
Step 2：单独计算转入低价捡漏释放预算 low_bid_retention_release
Step 3：计算可用于本轮重分配的预算 available_reallocation_budget
Step 4：如果可分配预算不足，则先判断使用请求比例还是按经营目标动态分配
Step 5：输出组合预算变化与解释
```

### 6.2 有加有减时怎么处理

如果本轮同时存在预算增加和预算减少：

```yaml
released_budget =
  low_bid_retention_release
  + sum(abs(group_delta) where group_delta < 0 and group != low_bid_retention_group)
requested_increase = sum(group_delta where group_delta > 0)
net_required_increase = requested_increase - released_budget
available_reallocation_budget = released_budget + parent_allowed_net_increase
```

解释：

- 先用活动层低价捡漏释放、非低价捡漏组降预算释放的金额抵扣新增和加预算需求。
- 如果释放预算足够覆盖新增需求，则父 ASIN 不需要额外加预算。
- 如果释放预算不够，再判断父 ASIN 还能追加多少。
- `available_reallocation_budget` 才是本轮真正可分配给精准主力组、精准测试组、广泛自动组的预算池。

### 6.3 可分配预算不足时的默认比例分配

如果各组合请求增加预算总额大于 `available_reallocation_budget`，且未命中 §7.2 的加权场景，则按本轮请求增量比例分配。

公式：

```yaml
group_actual_increase =
  available_reallocation_budget
  × group_requested_positive_delta
  / total_requested_positive_delta
```

示例：

```text
精准主力组请求增加：+$20
精准测试组请求增加：+$3
广泛自动组请求增加：+$7
总请求增加：+$30

父 ASIN 本轮只允许净增加：+$10
转入低价捡漏释放预算：+$20
available_reallocation_budget = $20 + $10 = $30
```

则：

```text
可分配预算 $30，刚好覆盖总请求 $30：
精准主力组实际增加 = $20
精准测试组实际增加 = $3
广泛自动组实际增加 = $7
```

输出时可按后台预算粒度四舍五入。

### 6.4 有组合减少、有组合增加时的示例

```text
精准主力组：请求 +$20
精准测试组：请求 +$3
广泛自动组：请求 +$7
转入低价捡漏释放：$20
```

计算：

```text
请求增加总额 = 20 + 3 + 7 = $30
活动层低价捡漏释放预算 = $20
净新增需求 = $10
```

如果父 ASIN 允许增加 $10，则：

```text
先用活动层低价捡漏释放预算 $20 抵扣一部分增加需求
剩余 $10 由父 ASIN 总预算追加
最终组合预算按各组合 requested_delta 输出
```

如果父 ASIN 不允许增加，只能使用释放的 $20，则：

```text
可用增加预算 = $20
精准主力组实际增加 = 20 × 20 / 30 = $13.33
精准测试组实际增加 = 20 × 3 / 30 = $2.00
广泛自动组实际增加 = 20 × 7 / 30 = $4.67
```

此时总增加 $20，刚好由活动层低价捡漏释放预算覆盖，父 ASIN 净预算不变。

## 7. 组合预算分配优先级

预算分配方式由场景决定，不再混用。

```text
普通重分配 → 按 requested_delta 比例分配
存在明确经营优先级 → 按经营模式、广告目标和真实消耗能力动态分配
```

无论使用请求比例还是动态分配，最终分配金额都不得超过各组合本轮 `requested_delta`。
如果 `available_reallocation_budget >= requested_increase_budget`，说明本轮可分配预算足够覆盖全部请求，不需要按比例或加权拆分，直接按各组合 `requested_delta` 全额执行。

### 7.1 默认比例分配

适用场景：

- 数据健康
- 无强护栏
- 各组合都允许执行预算增加
- 本轮只是预算重分配
- `available_reallocation_budget < requested_increase_budget`
- 未命中明确推词、限时修复、积极推进等优先场景

规则：

```yaml
allocation_method: proportional_by_requested_delta
```

### 7.2 按经营目标动态分配

只有当 `available_reallocation_budget < requested_increase_budget` 时，才需要压缩请求。可分配预算足够时，直接按各组 `requested_delta` 全额执行。

动态分配必须读取：

- 当前唯一经营模式与广告目标；
- 父 ASIN 目标 ACOS、目标总预算；
- 各组合真实花费、预算利用率和本轮请求；
- 可选人工护栏 `max_exact_push_share`（精准推词预算占比上限）。

禁止使用固定 60/20/20。Agent 先生成优先级，再按真实消耗能力分配：

| 场景 | 分配要求 |
| --- | --- |
| 明确推词 / ranking | 精准主力组优先，但精准推词分配占比不得超过人工设置的 `max_exact_push_share`。**未设置时按规模分档处理**：本轮给精准主力组的加预算额 > 本轮可分配预算 × 50% → `MANUAL_REVIEW`（不自行发明上限）；≤ 50% → 按动态分配正常执行，并在输出的 `exact_push_share_note` 里写明「未设置精准推进占比上限，本轮加预算 $X 占可分配预算 Y%，低于 50% 阈值故自动执行」 |
| 限时修复 | 以恢复单量为目标，在目标 ACOS 与父 ASIN 总预算内运行；伴随运营下调目标 ACOS 后，以新目标重新计算，不额外套固定组比例 |
| 积极推进 | ACOS 健康且请求合理时可满足增长需求；广泛自动组表现好、能稳定获取低成本流量时，不机械压缩其占比 |
| 稳定经营 / 获取利润 | 优先真实可消耗、ACOS 达标的活动，减少无效测试；仍按证据分配，不平均撒预算 |
| 控制清货 / 立即退出 | 遵循模式权限；不为探索或推词增加预算，立即退出的广泛/词组/自动走停止投放路径 |

硬约束：

```yaml
group_actual_increase <= group_requested_positive_delta
sum(group_actual_increase) <= available_reallocation_budget
low_bid_retention_group_actual_increase = 0
exact_push_allocation_share <= max_exact_push_share  # 字段已配置时
```

动态分配后的剩余额度，只能在仍有未满足请求且有真实消耗能力的组合之间重新分配；不要求把预算池强行分完。

### 7.3 什么时候使用动态分配

| 场景 | 分配方式 |
| --- | --- |
| 父 ASIN 预算充足 | 全额满足合规 requested_delta |
| 父 ASIN 预算不足、无明确优先级 | 按 requested_delta 比例压缩 |
| 父 ASIN 预算不足、有明确经营优先级 | 按经营目标与真实数据动态分配 |
| 明确推词 | 动态优先精准主力组，并执行 `max_exact_push_share` 上限 |
| 测试词质量差 | 动态下调精准测试组；广泛自动组是否下调仍看其实际数据 |
| 库存不足 | 阻断增长型预算增加 |
| 高退货 / 低评分 | 降低所有增长组权重，必要时只保留精准主力组低强度承接 |

## 8. 组合预算动作规则

### 8.1 精准主力组

| 场景 | 处理 |
| --- | --- |
| 核心词 `natural_traffic_priority_score` 高，预算不足 | 优先加预算 |
| Ranking 任务进行中 | 不得断供 |
| ACOS 在容忍上限内 | 可保留或小幅增加 |
| ACOS 超容忍且无排名支持 | 降非核心词，核心词谨慎处理 |

### 8.2 精准测试组

| 场景 | 处理 |
| --- | --- |
| 精准新词测试中 | 小预算观察 |
| 跑出有效词 | 提取到精准主力组 |
| 搜索词质量差 | 降预算或转否词治理 |
| 预算不足 | 可压缩 |
| 已有精准主力组消耗预算且需要保护推广 | 精准测试组优先压缩 |

### 8.3 广泛自动组

| 场景 | 处理 |
| --- | --- |
| 搜索词有沉淀价值 | 保留预算，提词到精准承接 |
| 高点击无单 / 搜索词质量差 | ① 排除高度相关词后再判断否词 ② 降预算 ③ 降 Bid ④ 仍无改善则关闭；不进入低价捡漏组 |
| 花不出去 | 先检查 Bid 和词覆盖，不直接加大预算 |
| 预算紧张 | 优先压缩，让位精准主力组 |
| 组内活动均已关闭但仍需探索 | 根据经营模式决定是否新建广泛/自动活动；不为了花完预算强制新建 |

> 广泛、词组、自动活动不能进入只允许精准的低价捡漏组。表现差时执行否词、降预算、降Bid或停止投放。
> **不保留"最差活动"兜底。** 组内活动清空后，若组合预算有余量，应新建活动而非死守烂活动。

### 8.4 低价捡漏组

| 场景 | 处理 |
| --- | --- |
| 已决定低价捡漏的活动 | 移入低价捡漏组 |
| 组合预算 | 父 ASIN 下低价捡漏组总预算固定 $1 |
| Bid | `min(current_bid, $0.20)` |
| 是否参与新增预算 | 不参与 |
| 是否参与二次分配 | 不参与，只释放预算，不接收预算 |
| 是否允许预算增加 | 不允许 |

低价捡漏组是预算回收组，不是预算再分配对象。  
任何进入低价捡漏组的活动，活动层预算都降为 $1，Bid = `min(current_bid, $0.20)`；这些活动共同归入父 ASIN 下同一个低价捡漏组。无论组内有 10 个还是 80 个活动，低价捡漏组的组合层总预算都固定为 $1，不是每个活动各自拥有一个 $1 组合预算。活动层释放出来的预算只能分配给精准主力组、精准测试组或广泛自动组，不得再分配回低价捡漏组。

低价捡漏组创建口径：

| 场景 | 组合层处理 |
| --- | --- |
| 低价捡漏组已存在 | 组合预算保持 $1，`group_delta = 0` |
| 低价捡漏组本轮首次创建 | 新建组合，`group_create_budget = $1`；该 $1 不参与新增预算分配，优先由本轮活动层释放预算覆盖 |

## 10. 校验规则

| 规则编号 | 内容 | 处理 |
| --- | --- | --- |
| GROUP-001 | 每个 Campaign 必须归属一个 AdBudgetGroup | 缺失则 MANUAL_REVIEW |
| GROUP-002 | Campaign 预算调整后必须回算组合预算 | 未回算则 BLOCKED 输出 |
| GROUP-003 | 组合预算调整后必须回算父 ASIN 总预算 | 未回算则 BLOCKED 输出 |
| GROUP-004 | 低价捡漏组不得参与新增预算分配 | 违反则 BLOCKED |
| GROUP-004A | 低价捡漏组组合预算必须固定为 $1，Bid 必须为 `min(current_bid, $0.20)` | 违反则 BLOCKED |
| GROUP-005 | 精准主力组不得因精准测试组或广泛自动组预算扩张而断供 | 违反则 MANUAL_REVIEW 或 BLOCKED |
| GROUP-006 | 当 `requested_increase_budget > available_reallocation_budget` 时，所有正向增量必须按请求比例或经营目标动态压缩 | 未压缩则 MANUAL_REVIEW |
| GROUP-007 | 释放预算大于新增需求时，不得强行分配完，多余部分进入预算缓冲 | 违反则 MANUAL_REVIEW |
