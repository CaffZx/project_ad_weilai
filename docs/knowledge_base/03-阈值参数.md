> **本文是知识库全部数值阈值的唯一来源**（`00号§1` 约束 1）。

## 8 ERP硬上限与 Bid 三概念分离

### 8.1 Bid 的三个不同概念（v3.4.0 修正，C-10）

v3.3.0 把 `$0.20` 同时当作「低价捡漏组固定值」和「全站 Bid 硬下限」，导致两个真实问题：
① 本来 Bid = $0.15 的词转入低价捡漏组时被**强行抬到 $0.20**（给正在淘汰的词加价 33%）；
② 所有低于 $0.20 的合法策略被阻断（女装长尾里 $0.10–0.18 的 Bid 是常见的）。

| 概念 | 值 | 性质 | 适用范围 |

## 10. 精准主力组 3 日验证门槛（v3.4.3 恢复固定 $5）

`23号§3.5` 的精准主力组准入条件之一是「连续 3 个完整站点自然日，每日花费均达到门槛」。

| 参数 | 取值 | 状态 |
| --- | --- | --- |
| 每日花费门槛 | **固定 `$5.00`**（严格大于；`settings.campaign_exact_main_daily_spend_threshold`） | ✅ 已确认 |
| 连续天数 | 3 个完整站点自然日，成熟窗 T-3/T-4/T-5（见 §12.2） | ✅ 已确认 |
| ACOS 条件 | 3 日**汇总** ACOS < 目标 ACOS（不是日 ACOS 平均值） | ✅ 已确认 |
| 判定性质 | `admission_only` —— 只用于准入，已在主力组的活动不因门槛变化被自动降级 | ✅ 已确认 |

> **口径沿革与为什么回到固定值**
>
> v3.3.0 固定 `$5` → v3.4.0（C-08）改为「父 ASIN 目标日预算 × 8%，下限 $1 / 上限 $8」
> → **v3.4.3 经营决定恢复固定 `$5`**。
>
> 改比例的动机是真实的：`15号§2.1` 给 P3 的活动预算范围是 $5–20/天，
> 父 ASIN 日预算 $10–20 时，「连续 3 天每日 >$5」意味着单个活动要连续三天吃掉
> 25–50% 的父级预算才有资格升组 —— P3 长尾精准词在结构上很难建立主力组，
> 会永久停在 `exact_testing_group`，拿不到 `GROUP-BUDGET-004` 的断供保护，
> 且因「精准测试组优先压缩」在预算紧张时第一个被砍。
>
> 但比例口径的 `8% / $1 / $8` 三个数**没有经营验证依据**，属于用一组未验证的数
> 替换一个已验证的数。运营选择回到固定 `$5`：宁可保留一个已知边界，
> 也不引入三个来源不明的参数。
>
> **长尾问题没有消失，只是没有用未验证的参数去掩盖。** 后续解法有数据后再定，
> 候选方向：按产品定位分档固定值（P0/P1 $5、P2 $3、P3 $1.5）、
> 或 `max(父预算 × 比例, 绝对下限)` 并封顶 $5。
> 代码保留比例口径能力，但只能通过
> `campaign_exact_main_threshold_mode=ratio` **显式启用**。
> `fixed` 模式下把门槛设为 0 或负数会阻断升组并记录错误，不会自动回落比例。
>
> **实现防线**：门槛值 `0` 或负数**不得**被当作「已显式指定门槛」。
> v3.4.0/v3.4.1 的判据是 `is not None`，而主链无条件传入迁移兼容值 `0.0`，
> 导致实际门槛退化为 `$0`（每日花费 $0.01 连续 3 天即升组）。
> 该防线在领域层（`evaluate_exact_main_validation`），
> 回归用例 `test_zero_threshold_must_never_be_treated_as_explicit`。

## 12. 归因成熟度（v3.4.8 修正）

Amazon SP 为 7 天点击归因，销售数据在点击后最长 14 天持续重述。全部 ACOS/CVR 判定
优先使用**校正后指标**（`app/core/attribution_maturity.py`），原始值只作事实展示；
绩效驱动的不可逆动作还必须通过成熟窗口门禁。

### 12.1 可控成熟度曲线（US 女装初始值）

| 数据龄（天） | 1 | 2 | 3 | 4 | 5 | 7 | 10 | 14 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 已到位比例 | 0.55 | 0.75 | 0.85 | 0.90 | 0.93 | 0.97 | 0.99 | 1.00 |
| 状态 | ⚠️ 可配置初始值，尚待 ERP 重述快照校准 | | | | | | | |

> **唯一运行时配置**：`app/config/thresholds.toml [attribution_maturity]`。
> 曲线比例、不可逆动作最低数据龄和成熟窗口滞后天数均从该处读取；成熟窗口固定为
> 已确认的连续 3 日契约。非法比例、
> 非单调曲线、非 3 日窗口、或“窗口滞后小于动作最低数据龄最大值”直接阻断，
> 不允许代码常量或提示词静默覆盖。修改后须保留配置
> 变更记录；ERP 重述快照就绪后用 `fit_curve_from_restatements` 生成候选曲线，经验证再更新。
>
> `data_min_age_days` / `data_maturity` /
> `acos_corrected` 现在逐活动真实计算并随动作输出，ONT-022 成熟度门**已从
> warn-only 转为强制**。龄期口径：`business_date` 为当地昨天时龄期 = 1
> （数仓窗口 `end = 当地今天-1`，是最后一个完整日）。
>
> **两个窗口的精度不同，必须知道**：精准验证窗按日读取 → **逐日精确校正**；
> 广泛/自动/词组只拉一次成熟聚合窗，以控制 MCP 调用量；
> 7 天窗只有聚合值 → **均匀分布近似**（在 `maturity_basis` 字段标注）。
> 精准逐日窗缺任意一天即视为窗口不完整，由 Agent 自动延后，不得把剩余的更老日期
> 误当作“更成熟”而放行。
> 要让 7 天窗也精确，需把日拉取从 3 天扩到 7 天（MCP 调用量 ×7/3），
> 或等 §11.9 重述快照。近似方向是保守的：均匀假设不会像「整窗按最老龄期校正」
> 那样低估未成熟度。

**0 销售 + 未成熟窗口 → `acos_corrected = None`（证据不足），不是 ∞、不是「无转化」。**
调用方必须把 None 当「本轮不判定」处理——这一条直接消灭「数据事故日批量降价」的最常见来源。

### 12.2 不可逆动作最小数据龄（ONT-022 成熟度门）

| 动作 | 最小数据龄 | 状态 |
| --- | --- | --- |
| `eliminate_to_low_bid_pool` / `close_campaign` / `add_negative_search_term` / `demote_to_exact_testing` / `promote_to_exact_core` | 默认 3 天，按统一配置读取 | ✅ 可配置 |
| 数据龄未知或不足 | Agent 自动延后，本轮不生成可执行动作；下轮重取成熟窗再判断，不增加过程人工节点 | ✅ 已确认 |
| **立即退出豁免** | 人工已在前置标签选择 `immediate_exit` 时，精准迁捡漏组、非精准关闭只豁免成熟度门；其他 Ontology 规则和最终人工执行确认仍保留 | ✅ 已确认 |
| **相关性驱动否词豁免** | R3/R4 否词（31号§4 档4）是语义判定不依赖表现数据，**不受本门约束**；效率驱动否词（05号§3 路径二）仍受约束 | ✅ 已确认 |
| 可逆动作（Bid/预算小幅调整） | 无最小龄，但必须用校正后指标 | ✅ 已确认 |

**成熟窗定义（消除窗口歧义）**：不可逆判定所用的「近 N 天」窗口，一律取**最新一天龄期
≥3 天**的窗口，即 T-3 起往前数。具体：升组的「连续 3 个完整站点自然日」= T-3/T-4/T-5
（不是 T-1..T-3）；降组的「连续 2 个 3 日评估周期」与严重回落的「近 7 天」同理后移。
`evaluate_exact_main_validation()` 本身只校验连续性，窗口日期由调用方按本条和
`thresholds.toml` 传入。
代价是判定慢 2 天——这是刻意的：对不可逆动作，宁可慢两天，不可用半熟数据错杀。
