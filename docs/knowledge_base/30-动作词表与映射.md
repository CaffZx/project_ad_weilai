# 动作词表与映射（action_registry.yaml）

> **本文是 action_code 的唯一权威表。**
> `app/domain/advertising.py` 的 `ActionType`、`12-输出规范.md` 的 `action_type` 枚举、
> `ontology/actions.yaml` 的 actions 键、ERP 写入映射（`erp_writer/mappers.py`）
> 四处全部从本文派生，不得各自定义。
>
> v3.3.0 的失效点：知识库用 `bid_up_for_ranking` 一类带意图的业务码，代码 `ActionType`
> 用 `adjust_bid` 一类物理码，两套交集只有 `create_campaign`，且无映射表。运营看到的
> `triggered_rule` 回不到 ONT 编号，输出里的 `ontology_rule_refs` 也回不到代码护栏。

## 0. 为什么要两套码

**业务码携带意图，物理码只描述操作。** 这个区分不能丢：

`bid_up_for_ranking`（提价冲排名）和 `bid_down_for_acos`（降价控 ACOS）在物理上是同一个动作（改一个 Bid 数值），但它们的**风险等级、必需证据、审核等级、阻断条件完全不同**：

| | `bid_up_for_ranking` | `bid_down_for_acos` |
| --- | --- | --- |
| 是否增长型 | 是（受库存/退货/评分阻断） | 否 |
| 必需证据 | 自然排名 + 库存 + Listing 承接 | 仅投放目标报告 |
| 默认审核等级 | MANUAL_REVIEW | AUTO_APPROVED |
| 阻断条件 | 库存不足、高退货、低评分、缺排名数据 | 该词承担 Ranking 任务且未超容忍上限 |

如果塌缩成一个 `adjust_bid`，`05-动作规则.md` 的审核等级分级和 `ontology/actions.yaml` 的必需证据索引就全部失去挂载点。所以：**业务码用于规则判断与审核分级，物理码用于执行与 ERP 写入。**

## 2. `stop_campaign` 与 `pause_campaign` 的区别（C-03）

v3.3.0 只有 `pause`，导致 `21号`/`18号`/`budget_groups` 里写的「关闭」实际全部落成 `pause`，
而 `10号§1.6` 又明文禁止输出 `pause` —— 代码、注释、护栏三方冲突。v3.4.0 分开定义。

| | `stop_campaign` | `pause_campaign` |
| --- | --- | --- |
| 业务语义 | **退出投放**：本方向不再经营 | **临时停投**：等待某个条件解除后恢复 |
| 典型场景 | 广泛/词组/自动活动整体长期低效；`immediate_exit` 模式下的非精准活动 | 极少使用。仅当业务语义确为「暂时停一下」且已有明确恢复条件时 |
| Amazon 后台状态 | `archived`（或长期 `paused` + 标记，取决于 ERP 接口能力） | `paused` |
| 可逆性 | 归档后不可恢复历史数据；恢复需新建活动 | 可随时恢复，保留历史数据 |
| 是否进低价捡漏组 | 否。低价捡漏组按 `ONT-014` 只收 EXACT | 否 |
| 是否触发预算回算 | 是。释放金额 = `current_daily_budget`，计入 `other_campaign_budget_decrease` | 是。同左 |
| 审核等级 | HIGH_RISK_REVIEW（不可降级） | HIGH_RISK_REVIEW（不可降级） |
| 是否需要人工确认 | 必须 | 必须 |

**四类退出路径的正确对应**（这是 v3.3.0 最容易搞错的地方）：

| 活动类型 | 退出动作 | 去向 | 依据 |
| --- | --- | --- | --- |
| 单关键词 EXACT | `eliminate_to_low_bid_pool` | 低价捡漏组，预算 $1、Bid `min(current_bid, 0.20)` | 21号§0、`ONT-014` |
| 多关键词 EXACT | `eliminate_to_low_bid_pool` | 低价捡漏组（确定性迁入，不看历史表现） | `ROUTE-002` |
| BROAD / PHRASE / AUTO | `stop_campaign` | 停止投放。**不得**进低价捡漏组 | `ONT-016`、21号§0 |
| PRODUCT_TARGETING | `stop_campaign` | 停止投放。**不得**进低价捡漏组（无关键词，$0.20 在 ASIN 定投上基本无曝光） | 23号§8.5（v3.4.0 新增） |

## 3. 复合动作的展开规则

`eliminate_to_low_bid_pool` / `demote_to_exact_testing` 是业务上的一个动作，但在物理层是多个动作。
`ActionBundle` 里必须展开为多条 `AdAction`，共享同一个 `bundle_id`，并保证**同批成功或同批回滚**。

### 3.1 `eliminate_to_low_bid_pool` 展开

```text
bundle_id: eliminate:{campaign_id}
├── AdAction 1: move_portfolio
│     scope=CAMPAIGN  target=campaign_id
│     current={portfolio: exact_core_group | exact_testing_group}
│     proposed={portfolio: low_bid_retention_group}
├── AdAction 2: adjust_budget
│     scope=CAMPAIGN  current={budget: 8.0}  proposed={budget: 1.0}
└── AdAction 3: adjust_bid
      scope=TARGET    current={bid: 0.15}   proposed={bid: 0.15}
      注：proposed_bid = min(current_bid, 0.20)。current_bid 已低于 0.20 时保持不变，
          不得抬高（C-10；违反则 GROUP-004A 阻断）
```

同时必须输出 `21号§5A` 要求的四个预算回算字段：
`released_at_campaign_level` = `current_daily_budget - 1`、`group_type_before_elimination`、
`low_bid_retention_group_delta` = `0`、`released_budget_flows_to`。

### 3.2 `demote_to_exact_testing` 展开（v3.4.0 新增）

```text
bundle_id: demote:{campaign_id}
├── AdAction 1: move_portfolio
│     current={portfolio: exact_core_group}  proposed={portfolio: exact_testing_group}
├── AdAction 2: adjust_budget（降预算，幅度按 19号§4 × 15号§2 系数）
└── AdAction 3: adjust_bid（降 Bid，幅度按 19号§3 × 15号§1.2 系数）
```

必须携带 `demoted_at`（降级日期），`32号§2.4` 的严重回落判定依赖它。

## 4. 动作生命周期（C-04）

v3.3.0 的 `01号` 与 `12号§三` 都写「仅允许 PROPOSED 或 BLOCKED」，与代码的 11 态生命周期不一致。
v3.4.0 统一为 11 态，并明确**谁能写哪一态**。

| # | 状态 | 含义 | 写入方 |
| --- | --- | --- | --- |
| 1 | `proposed` | Agent 已生成提案 | **Agent** |
| 2 | `blocked` | Agent 自检或护栏不通过，不生成可执行动作 | **Agent** / `OntologyValidator` |
| 3 | `validated` | 通过 Ontology 校验与安全护栏 | `OntologyValidator` |
| 4 | `human_approved` | 运营在 ERP 确认执行 | ERP（人工） |
| 5 | `erp_accepted` | ERP 护栏校验通过并受理 | ERP |
| 6 | `executing` | ERP 已提交异步任务，未收到终态 | ERP |
| 7 | `executed` | 收到终态且执行成功 | ERP |
| 8 | `rejected` | ERP 护栏明确拒绝 | ERP |
| 9 | `failed` | 系统性失败 | ERP |
| 10 | `observing` | 执行后进入观察窗（1/3/7/14 天） | 系统 |
| 11 | `evaluated` | 观察窗结束，已产出复盘结论 | 系统 |

```text
proposed → validated → human_approved → erp_accepted → executing
                                                          ├→ executed → observing → evaluated
                                                          ├→ rejected（不重试）
                                                          └→ failed（仅契约标记可重试者允许重试）
blocked（终态，不进入流转）
```

**硬规则**：

- Agent 只能产出 `proposed` 与 `blocked` 两态，不得自行写入其他状态。
- ERP 异步任务提交后只能标 `executing`；**收到终态结果前不得写成 `executed`**。
- `rejected` 不自动重试。只有契约标记为可重试的系统性 `failed` 才允许重试。
- `ActionBundle` 允许部分成功：同一 bundle 内不同 `AdAction` 可处于不同状态，但 §3 的复合动作必须同批。

## 5. ERP 字段映射

| 物理码 | ERP 写入字段 | 备注 |
| --- | --- | --- |
| `adjust_bid` | `target_bid` | Target 级 |
| `adjust_budget` | `campaign_daily_budget` | Campaign 级；组合/父级预算走摘要字段 |
| `adjust_placement` | `placement_tos_pct` / `placement_pp_pct` / `placement_ros_pct` | 三个位置必须全部输出；非精准与非商品定投填 `N/A` |
| `add_negative` | `negative_keyword_list` + `negative_match_type` | 默认精确否定 |
| `move_portfolio` | `portfolio_id` / `budget_group_type` | 四组合枚举见 `02号§9`；商品定投另带 `portfolio_subtype` |
| `create_campaign` | `campaign_create_payload` | 含 name / match_type / budget / bid / primary_placement |
| `create_target` | `target_create_payload` | 扩词用；向现有广告组新增 Target |
| `stop_campaign` | `campaign_state = archived` | **v3.4.0 新增，需 ERP 确认接口能力**（见交接文档§11.5） |
| `pause` | `campaign_state = paused` | |
| `enable` | `campaign_state = enabled` | |
| `keep` | —（不写 ERP） | 仅生成记录与复盘输入 |

> **待 ERP 确认**：`stop_campaign` 对应的 `archived` 状态是否可写、是否可逆、错误码。
> 若 ERP 只支持 `paused`，则 `stop_campaign` 降级实现为「`paused` + `exit_reason` 标记」，
> 但业务码与审核等级保持不变，避免规则层再次退化（这正是 v3.3.0 的失效路径）。

## 7. 未注册动作的处理

`OntologyValidator` 在 `ActionBundle` 输出前校验每条动作的 `action_code`：

| 情况 | 处理 |
| --- | --- |
| `action_code` 不在 §1 总表中 | `status = blocked`，`reason_code = ACTION_NOT_REGISTERED` |
| `action_code` 与 `physical_action_code` 不匹配 §1 映射 | `status = blocked`，`reason_code = ACTION_CODE_MISMATCH` |
| `action_code` 与 `scope` 不匹配 §1 | `status = blocked`，`reason_code = ACTION_SCOPE_INVALID` |
| `action_code` 与 `campaign_type` 不匹配 `ontology/campaign_types.yaml` | `status = blocked`，引用对应 `ONT-*` 编号 |

新增动作必须先在本文 §1 注册（业务码、物理码、scope、是否增长型、审核等级、规则出处），
再接入执行链路。这是 `00号§7` 的强制前置。
