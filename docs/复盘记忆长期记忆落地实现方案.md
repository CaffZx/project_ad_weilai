# 复盘记忆长期落地实现方案

> 版本：v1.0  
> 日期：2026-07-17  
> 状态：讨论稿  
> 目标：形成可追溯、可审核、可回滚的复盘记忆闭环，并验证其能提升广告 Agent 推荐建议的准确率。

## 1. 目标与边界

正式系统的目标不是生成一段“看起来合理”的总结，而是让每一条可用记忆都能回到：决策时证据、真实执行动作、T+3 结果、人工审核和文本版本。

系统需要形成以下异步闭环：

```text
分析时冻结数据与版本
        ↓
运营同意并执行，写入统一 decision_id
        ↓
确认 Amazon 最终生效时间
        ↓
T+3 自动采集活动级与产品级结果
        ↓
确定性计算 + AI 生成复盘记忆
        ↓
人工审核、启停、版本与过期管理
        ↓
按父 ASIN 受控注入下一次广告分析
        ↓
离线 benchmark 证明建议准确率提升
        ↓
SkillOpt 优化指定文本对象并受控发布
```

主广告分析流程不等待复盘完成。快照写入、T+3 任务、复盘生成和 SkillOpt 均为异步任务；任何复盘失败都不得阻断新一轮广告分析。

本方案不允许 SkillOpt 改写原始数据、指标计算、关联规则、安全阈值、执行 guardrail、数据切分规则或 scorer 的硬门槛。

## 2. 核心约定

### 2.1 复盘与生命周期单位

- 一次复盘以 `decision_id` 为主线，包含一个产品级对象与一个或多个活动级对象。
- 父 ASIN 是记忆生命周期、检索、训练/验证隔离的管理单位。
- 活动级记忆使用 `decision_id + campaign_id` 关联，并保留活动自身的关键词 ID、匹配类型和广告位等业务身份。
- `decision_id` 不能替代动作自身的业务 ID；它只表达“该动作属于哪次 Agent 决策”。

### 2.2 时间与结果口径

- 第一阶段统一使用 T+3，且必须有完整三天数据。
- T+3 从 Amazon 最终生效时间开始计算，不能只以 MCP 已提交时间代替。
- 数据不足、改价、人工二次调整、断货或执行不完整必须结构化标记；不得被 AI 忽略后写成成功经验。

### 2.3 AI 与程序的职责

确定性程序负责数据校验、动作汇总、前后指标计算、干扰检查、样本合法性和证据整理。AI 只能在给定证据内解释结果并生成结构化记忆；不得补充输入不存在的数字、动作或因果。

### 2.4 两层记忆

- 产品级记忆：服务产品方向、预算和整体策略分析。
- 活动级记忆：服务对应活动或高度相似活动的调整。

两层分别存储、分别注入，但可源自同一个 `decision_id` 的复盘案例。

### 2.5 正式样本合法性条件

`review_case` 不是只要有前后数据就能生成可用记忆。系统必须先给出可审计的合法性判定；AI 无权自行放宽条件。

| 条件 | 必须具备的证据 | 不满足时的处理 |
|---|---|---|
| 决策可追溯 | `decision_id`、不可变分析快照、卡片/建议动作、当时知识库与提示词版本 | 不生成正式记忆；标记 `EXCLUDED` |
| 运营同意范围 | 同意时间、同意的活动/动作范围 | 不进入复盘任务 |
| 实际执行可追溯 | MCP 请求、ERP 主表与子表的 `decision_id`、动作业务 ID、成功/失败结果 | 不能将计划动作当成执行动作；部分成功只复盘成功部分 |
| Amazon 最终生效 | 最终生效状态与 `effective_at` | 任务不开始计时；超时后进入人工核查 |
| 完整观察窗口 | 自 `effective_at` 起完整 T+3 活动级和产品级数据，且前后统计口径一致 | `INSUFFICIENT_DATA` |
| 干扰检查 | 改价、人工二次调整、库存/断货等结构化检查记录 | 重大干扰为 `EXCLUDED`；轻微干扰降低 `attribution_confidence` |
| 数据充分性 | 预先定义的曝光、点击、订单、花费和时间窗口阈值 | `INSUFFICIENT_DATA`，不得写为成败经验 |
| 产品上下文完整 | 父 ASIN、店铺、产品定位/阶段、淡旺季、广告目的/方向、目标 ACOS、目标预算 | 只保留事实，不允许产出可注入的策略记忆 |
| 版本完整 | 快照、知识库、提示词、复盘器、代码发布版本均可定位 | 可保存案例，但不可用于训练、评分或发布 |

只有全部硬性条件满足、且无重大干扰的案例，才可标记 `eligible=true` 并进入“可审核记忆”。`EXCLUDED` 和 `INSUFFICIENT_DATA` 仍应保留，用于审计、异常分析和防止 Agent 学到错误经验，但不得成为正向记忆来源。

## 3. 现有执行链路的长期治理

### 3.1 要补的执行子表字段

以下 ERP 执行子表新增 `decision_id`：

| 表 | 新增字段 | 作用 |
|---|---|---|
| `t_advert_agent_modify_campaign_record` | `decision_id` | 关联预算、活动状态等活动级执行结果 |
| `t_advert_agent_modify_keyword_record` | `decision_id` | 关联 Bid、关键词状态、否词等关键词级执行结果 |
| `t_advert_agent_modify_placement_record` | `decision_id` | 关联广告位百分比调整结果 |

`t_advert_agent_modify_advert_record` 主表已有 `decision_id` 字段，不新增字段，但必须确保 ERP 实际写入，不能继续为空。现有 campaign、keyword、placement 三张 pending 表已有 `decision_id`，也不新增。

### 3.2 MCP 传参契约

对于预算、Bid、活动状态、广告位等既有活动调整，调用 whpadvert：

```text
agent_async_batch_update_advert
```

在一次运营同意所触发的每一次该 MCP 调用的最外层请求上下文传入一个统一 `decision_id`。即使内部因 `portfolioId` 拆为多条 `paramsVo`，仍属于同一次决策，不得生成不同的 `decision_id`。

ERP 写入主表和三个子表时都保存这个值。否词等其他 MCP 链路后续应采用同一原则，但不混入本次三张子表改造。

### 3.3 分析快照

每次分析完成时，复用主流程本轮已读取的数据异步写快照，不再重复调用 MCP。快照必须保存：数据截止时间、数据来源、产品基线、产品/活动指标、卡片与建议动作、知识库版本和内容哈希、提示词/代码可定位版本。

快照不可原地修改；发现错误时新建修订版本并保留旧版本。

## 4. 正式数据表

### 4.1 `t_advert_agent_analysis_snapshot`

保存决策时的不可变事实。核心字段：

| 字段 | 用途 |
|---|---|
| `snapshot_id` | 快照主键 |
| `decision_id` | 决策关联 |
| `parent_asin` / `child_asins_json` | 产品归属与涉及子 ASIN |
| `analysis_at` / `data_as_of` | 分析时间与数据截止时间 |
| `snapshot_origin` | 正式版一律为 `LIVE` |
| `kb_version` / `kb_content_hash` | 知识库版本与内容定位 |
| `product_baseline_json` | 定位、阶段、淡旺季、目标、预算、目标 ACOS |
| `product_metrics_json` / `campaign_metrics_json` | 决策时产品和活动指标 |
| `decision_cards_json` | 卡片和建议动作 |
| `source_refs_json` | 数仓、MCP、业务表来源与查询条件 |
| `schema_version` | 结构版本 |

### 4.2 `t_advert_agent_review_task`

管理 T+3 到期和重试。核心字段：`task_id`、`decision_id`、`snapshot_id`、`parent_asin`、`review_window`、`effective_at`、`due_at`、`task_status`、`retry_count`、`last_error`、`locked_by`、`locked_at`、时间戳。

唯一约束：`decision_id + review_window`，保证幂等。

### 4.3 `t_advert_agent_review_case`

保存可供复盘的事实包。核心字段：`review_case_id`、`snapshot_id`、`decision_id`、`parent_asin`、`review_window`、`effective_at`、`review_at`、`approval_evidence_json`、`execution_evidence_json`、`activity_after_json`、`product_after_json`、`interference_json`、`eligible`、`exclusion_reason`、`calculated_evidence_json`、`outcome_label`、`attribution_confidence`、`case_status`、`schema_version`、时间戳。

一个 `decision_id + review_window` 对应一个案例；案例内活动使用 JSON 数组，并分别保留 `campaign_id`。

### 4.4 `t_advert_agent_review_memory`

保存产品级/活动级记忆及审核结论。核心字段：`review_memory_id`、`review_case_id`、`memory_scope`、`parent_asin`、`campaign_id`、`structured_memory_json`、`memory_text`、`renderer_version`、`model_name`、`human_status`、`human_comment`、`human_revised_text`、`is_active`、时间戳。

建议唯一约束：`review_case_id + memory_scope + campaign_id + renderer_version`。

### 4.5 审计与文本版本表

新增：

- `t_advert_agent_review_memory_audit`：记录审核、启用、停用、替换和回滚的前后状态、操作者和原因。
- `t_advert_agent_text_artifact_version`：统一记录知识库、Agent 提示词、复盘 skill、记忆注入模板和 SkillOpt 产物的版本、内容哈希、存储位置、来源运行和状态。
- `t_advert_agent_skillopt_run`（可选）：记录训练/验证集版本、scorer、模型、初始分、最佳分、候选产物和人工发布结论。

## 5. 正式复盘加工链路

### 5.1 分析完成

异步写 `analysis_snapshot`。写入失败需告警和补偿，但不阻断分析结果返回。

### 5.2 运营同意并执行

向每次执行 MCP 传统一 `decision_id`，记录 Amazon 最终生效状态和时间。仅最终生效的动作进入复盘；部分成功时按实际成功动作复盘。

### 5.3 T+3 到期

异步 worker 拉取到期 `review_task`，获取活动级和产品级 T+3 数据，核查价格、人工调整、库存和执行完整性，写入 `review_case`。数据不足写 `INSUFFICIENT_DATA`；存在重大干扰写 `EXCLUDED`。

### 5.4 生成与审核

确定性计算器先生成标准证据 JSON，复盘 skill 据此生成产品级和活动级记忆。新记忆默认待审核或影子状态；达到稳定质量后才允许按规则自动启用低风险记忆。

正式拆分/落库程序只做：读取已审核统一复盘记忆 JSON、拆出产品级与活动级对象、分别写入记忆表、返回写入状态。它不拉数、不计算、不调用 AI、不决定注入资格。

## 6. 记忆使用与版本控制

- 产品级记忆只在产品方向、预算和整体策略分析环节注入。
- 活动级记忆只在对应或高度相似活动调整环节注入。
- 记忆必须附带适用条件、避免条件、证据时间和可信度。
- `INSUFFICIENT_DATA`、`EXCLUDED`、未审核、停用或 `SHADOW_ONLY` 记忆不得作为正向经验注入。
- 每次分析记录实际使用的记忆 ID/版本、知识库版本、主提示词版本、复盘生成器版本和 Agent 代码发布版本。
- 每个已发布文本对象必须可一键切回上一版本。

## 7. 推荐建议 benchmark：唯一的业务优化评分对象

当前要优化的是“广告 Agent 在分析时实际读取的文本对象”，例如已审核复盘记忆、记忆注入模板、提示词中与记忆使用有关的片段，以及以后明确开放的知识库模块。因此，SkillOpt 的业务 benchmark 只评估推荐建议，不能以“复盘文字写得更像人工”代替业务效果。

复盘加工仍需要质量验收：事实是否忠实、样本是否合法、记忆是否经人工审核。但这属于生产数据质量 gate，不是本期 SkillOpt 的优化目标，也不单独作为业务 benchmark。

### 7.1 推荐建议样本的定义

一个 `recommendation_case` 是某一真实决策时点的回放单元，而不是该决策 T+3 后形成的复盘结果。它必须冻结：

- 该时点 Agent 原本可见的产品和活动数据；
- 产品策略上下文和目标；
- 当时允许使用的知识库、提示词与代码版本；
- 在该时点之前已经完成、审核通过且可注入的历史记忆；
- 该时点对应的真实建议、运营同意/拒绝、实际执行与后续 T+3；
- 人工对“推荐是否合理、是否触发风险、应该采取什么方向”的标注。

评分回放时，候选文本对象替换当前版本，其余输入全部冻结。至少对同一案例比较：

1. 不注入复盘记忆的基线；
2. 当前生产/当前候选的记忆、提示词或 skill；
3. SkillOpt 产出的单一候选版本。

### 7.2 “复盘样本”和“评分样本”不能怎样重叠

你的理解基本正确，但需要精确到“同一决策事件不能泄漏到自己的评分时点”。

- 某个 `decision_id=A` 的 T+3 结果生成的复盘记忆，**不得**用于评分 `A` 当时的推荐；因为 T+3 结果在 A 的决策时尚不存在。
- 该记忆可以在之后的 `decision_id=B` 评分中使用，前提是 A 的 `effective_at + T3` 早于 B 的 `analysis_at`，且 A 的记忆已审核启用。这正是历史记忆的正常使用方式。
- 一个父 ASIN 的全部决策、其快照、T+3 结果、复盘记忆和推荐评分案例必须只在同一个数据分区，不能一部分训练、一部分验证或测试。
- 验证/测试案例的真实后验信息（运营结果、实际执行、T+3、人工答案）只能交给 scorer，绝不能出现在 Agent 输入、记忆检索结果或候选提示词中。

### 7.3 80/20 的准确含义

80/20 指按**父 ASIN 分组**切分推荐建议案例，而不是把同一个产品的相邻决策随机分开：

| 分区 | 建议比例 | 用途 | 能否参与 SkillOpt 生成候选 |
|---|---:|---|---|
| train | 约 80% 的父 ASIN | SkillOpt 读取案例、产生反思和候选文本，并计算训练侧分数 | 可以 |
| validation | 约 20% 的父 ASIN | 从未参与候选生成，只用于选择是否优于当前版本 | 不可以 |
| final test（数据量足够后） | 留出未来新增的父 ASIN 或未来新产生案例 | 发布前/发布后一次性审计，不参与调参、挑版本 | 不可以 |

POC 样本少时可以先只有 train/validation 的 80/20；此时 20% 应准确称为 held-out validation，而不是测试集。案例量足够后再建立独立 final test。无论分几层，同一父 ASIN 绝不跨分区。

### 7.4 推荐建议 scorer

scorer 先执行不可被优化绕过的硬门槛，再计算质量分。硬门槛包括：建议只使用决策时可见事实；不越过预算/ACOS/业务 guardrail；不生成无对应证据的动作；不将 `EXCLUDED`、`INSUFFICIENT_DATA` 记忆作为正向经验；不误关联 ASIN、活动或关键词。

质量分应由业务人工标注校准，至少包括：

| 项目 | 要回答的问题 |
|---|---|
| 推荐方向正确性 | 是否符合该产品的阶段、目标、当前问题和历史经验？ |
| 动作合理性 | Bid、预算、广告位、否词等建议是否与证据和 guardrail 一致？ |
| 风险控制 | 是否识别数据不足、干扰或不应执行的情况？ |
| 历史记忆使用 | 是否正确引用适用记忆，而没有错误泛化或照搬无关经验？ |
| 可执行性 | 建议是否具体、可被运营理解与执行？ |
| 结果代理指标 | 对有真实后验的案例，建议方向是否与人工标注、实际执行和 T+3 结果一致？ |

运营同意和 T+3 结果都是重要证据，但不是唯一正确答案；人工标注和业务 guardrail 共同定义评分标准。LLM Judge 可辅助批量评分，但必须定期用人工抽检校准。

## 8. SkillOpt 的正式优化边界与运行方式

### 8.1 优化对象的顺序

每轮只开放一个文本对象，其他对象冻结，避免无法归因：

1. 已审核记忆的注入模板：决定哪些记忆、以何种长度和冲突规则进入 Agent 上下文；
2. 广告 Agent 提示词中“理解并使用记忆”的指定片段；
3. 复盘记忆本身的呈现模板或经过人工批准的记忆结构；
4. 仅在版本治理成熟后，开放知识库中边界明确的模块。

不把“复盘生成器”作为当前首个优化对象。它先接受事实忠实度与人工审核的质量 gate；只有未来明确要优化其生成方式时，才为它单独建立非业务质量评估，而不与推荐建议 benchmark 混用。

### 8.2 每次离线运行的固定输入输出

输入：冻结的 train/validation 版本、当前文本对象版本、推荐案例快照、当时可用记忆集合、scorer 版本、模型版本与随机种子。  
输出：候选文本、train 分数、held-out validation 分数、硬门槛失败列表、逐案例差异、token/成本、人工发布结论和可回滚版本。

候选不得自动覆盖生产文件。只有 held-out validation 优于当前版本、硬门槛为零、高风险案例不退化、人工抽检通过且推荐建议 benchmark 不回退，才能进入影子版本。

## 9. 落地顺序：先长期治理，再跑通链路

### 阶段 0：冻结合同与验收规则

先确认 `decision_id` 传递、样本合法性、T+3 口径、三层数据分区、记忆 JSON、推荐案例 JSON、硬门槛和人工审核职责。此阶段不接入 SkillOpt。

验收：产品、研发、ERP 维护方对字段、MCP 位置、写入归属和“不允许泄漏”的规则签字确认。

### 阶段 1：执行链路长期治理

1. ERP 三张执行子表新增 `decision_id`；
2. `agent_async_batch_update_advert` 的最外层请求接收并透传统一 `decision_id`；
3. ERP 主表与三个子表真实写入该值；
4. 对成功、失败、部分成功和重复调用定义幂等写入规则；
5. 随机抽取真实执行，验证能从子表回查到决策、卡片和实际动作。

验收：不再依赖人工猜测，能由任一执行记录唯一回到本次决策与动作范围。

### 阶段 2：分析快照与版本冻结

1. 分析完成后异步写 `analysis_snapshot`；
2. 冻结产品基线、活动数据、卡片、知识库/提示词版本和来源；
3. 记录快照失败重试和人工补偿；
4. 不重复发起同一批 MCP 请求。

验收：随机一条 `decision_id` 可恢复决策时 Agent 的真实可见输入。

### 阶段 3：T+3 任务与样本合法性判定

1. 确认 Amazon 最终生效后创建唯一 `review_task`；
2. 到期采集 T+3 产品/活动数据；
3. 执行干扰检查、数据充分性检查和实际动作核对；
4. 写入 `review_case`、`eligible`、排除原因和确定性证据；
5. 对异常、超时、部分成功设置重试和人工处理队列。

验收：任务幂等、无错关联；每个案例都能明确解释为什么可用、数据不足或被排除。

### 阶段 4：跑通“合法案例 → 审核记忆”的影子链路

1. 仅取 `eligible=true` 的案例生成统一复盘记忆 JSON；
2. 程序拆分并写产品级/活动级记忆；
3. 人工审核，记录通过、修订、拒绝和原因；
4. 记忆默认 `SHADOW_ONLY`，不注入线上 Agent；
5. 建立记忆过期、停用、版本替换和审计。

验收：无虚构事实、无错误关联、人工审核链路可追溯。此处验证的是数据加工质量，不是 SkillOpt 效果。

### 阶段 5：构建推荐建议 benchmark 与基线

1. 按父 ASIN 将全部历史素材先分为 train/validation；
2. 对每个推荐案例按其 `analysis_at` 截断可见信息，只保留此前已完成并审核的记忆；
3. 冻结人工标注、scorer 和无记忆基线；
4. 运行“无记忆”和“当前人工审核记忆”的回放；
5. 先验证记忆注入是否不降低建议质量，再考虑优化。

验收：验证侧没有训练泄漏；每条评分建议的输入、输出、分数和后验依据都可回放。

### 阶段 6：SkillOpt 离线优化与影子发布

1. 只选定一个文本对象，例如记忆注入模板；
2. 用 train 产生候选，用 held-out validation 选择版本；
3. 人工审核候选差异和失败案例；
4. 影子运行候选版本，持续记录真实建议差异；
5. 满足发布门槛后小范围启用，并保留一键回滚。

验收：held-out validation 有提升、硬错误为零、影子运行无明显风险回退。

### 阶段 7：扩大场景与建立 final test

先完成精准词，再逐步增加广泛词、扩词、预算、广告位、否词和复合动作。数据量足够后使用新进入系统的父 ASIN/未来案例建立 final test；它只用于最终审计，绝不用于选择候选版本。
