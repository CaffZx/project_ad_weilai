# 广告 Agent 复盘记忆系统实现方案

> 版本：2026-07-13  
> 范围：Campaign 广告活动分析后的复盘记忆，不包含长期跨产品模式归纳。  
> 核心原则：复盘产出分活动级与产品级，注入到不同 LLM 调用点；但复盘记忆的管理、活性与遗忘以父 ASIN 为单位统一治理。

---

## 1. 目标与边界

复盘记忆用于回答两个问题：

1. **活动级**：这个活动上一次被调整后，1/3/最终窗口的表现如何？下一次逐活动决策是否应该延续、加码、观察或换打法？
2. **产品级**：这个父 ASIN 上一轮围绕广告目的执行了一组调整后，整体广告目的是否达成？下一次策略总览应该如何定调？

和操作记忆的边界：

| 类型 | 粒度 | 解决的问题 | 注入点 | 生命周期 |
|---|---|---|---|---|
| 操作记忆 | 活动级 | 近期做过什么，避免重复/反向调整 | 逐活动决策 | 短，通常 7-14 天 |
| 复盘记忆 | 活动级产出 + ASIN 级汇总管理 | 上次动作/策略有没有效果 | 活动级注入逐活动，产品级注入总览 | 以父 ASIN 管理，最后一次更新起 14 天 |

复盘窗口固定为 **1 / 3 / 7 天**，不引入 14 天复盘窗口。14 天只用于记忆活性，不作为复盘检查点。

## 2. 当前数据依赖核查

### 2.1 已满足的数据

当前系统已经具备复盘记忆的一部分原料：

| 数据 | 当前来源 | 用途 |
|---|---|---|
| 决策批次 | `t_advert_agent_decision` | 确定父 ASIN、批次、分析模式、创建时间、前置配置快照 |
| 建议卡 | `t_advert_agent_modify_suggest_card` | 确定活动、动作类型、原因、证据、置信度、审核/执行状态 |
| 具体 pending 动作 | `t_advert_agent_modify_campaign_pending` / `keyword_pending` / `placement_pending` | 确定预算、出价、状态、广告位等 old/new 值 |
| 人工确认状态 | card 与 pending 的 `confirm_status` / `confirm_time` | 只对已同意执行的建议生成复盘链 |
| 执行状态 | pending 的 `execute_status` / `execute_time` / `execute_msg` | 只对真实执行成功的动作生成复盘链 |
| 执行前活动指标 | card 的 `perf_json` | 作为活动级 7 天基线 |
| 前置策略快照 | decision / decision_config / purpose_score / ai_suggest / direction_detail | 产品级广告目的、目标 ACOS、预算、方向快照 |
| 当前表现数据 | 现有 Campaign MCP 数据管道 | 到期后拉取活动级与产品级实际表现 |

### 2.2 目前缺少的数据依赖

复盘系统上线前，需要补齐以下数据或约束：

| 缺口 | 影响 | 建议 |
|---|---|---|
| 复盘任务表 | 系统不知道哪些动作需要在 1/3/7 天复盘 | 新增 `t_advert_agent_review_memory` 与 `t_advert_agent_review_checkpoint` |
| 结构化成功标准 | 只有 `description/evidence`，不能稳定判定达成/未达成 | 由代码模板按动作类型 + 广告目的生成 `success_criteria_json` |
| 产品级基线快照 | 仅有活动 `perf_json`，产品整体基线需要冻结 | 执行成功时写入 ASIN 级 `baseline_product_json` |
| 淡旺季阶段快照 | 遗忘规则要求淡旺季阶段未变更 | 执行成功时冻结 `season_stage_snapshot`，注入前与当前 long-term config 比对 |
| 直接“同意+执行”链路追踪 | 当前 `load_pending_by_card_ids` 路径注释说明不写 confirm/record/pending 状态，会导致复盘漏数 | 必须改为写入同等可追溯状态，或禁止该路径进入复盘 |
| 外部后台人工调整识别 | 3-7 天内可能在 Amazon/ERP 后台被改，系统需知道是否提前触发最终复盘 | 每日/分析前对比 expected old/new 与当前 MCP 状态，发现变化生成 `EXTERNAL_CHANGE` 事件 |
| 异步执行最终结果确认 | 部分 MCP 执行可能只是提交任务，未必代表平台最终生效 | 若 MCP 有 task result，需补一个执行结果同步 job；否则复盘口径标注为“已提交成功” |
| MCP 复盘轻量数据视图 | 复盘不应重复拉主流程全量数据 | 设计 `review_observe` meta_filter，只拉必要指标 |

## 3. 主进程与复盘进程的关系

### 3.1 结论

复盘记忆总结必须在**主分析落库链路之外异步进行**，不能阻塞、不能拖慢主进程。

但这不等于完全脱离主进程。最佳设计是：

> 主进程只负责“顺手留下可复用快照和事件”，复盘 worker 负责“到期拉缺失数据、判定、生成记忆”。

### 3.2 原则

1. **主流程不等待复盘**
   - Campaign 分析、LLM 决策、ERP `write_full`、`finalize_batch` 不等待复盘任务生成之外的任何复盘动作。
   - 复盘任务生成必须是轻量 DB 写入；失败只打 warning，不影响主流程返回。

2. **主流程可写复用快照**
   - 主流程已经取到的数据，例如 `perf_json`、产品级 summary、strategy context、direction/purpose 快照，应写入复盘基线。
   - 这属于“复盘原料落库”，不是复盘计算，不应调用额外 MCP。

3. **复盘 worker 优先复用主流程数据**
   - 如果当前分析刚好已经拉过某 ASIN 的 CampaignData / ASINData，主流程可以把轻量观测快照写入 `review_observation_cache`。
   - 复盘 worker 到期时先查缓存；缓存足够则不请求 MCP。
   - 缓存不足或过期时，worker 再按轻量 meta_filter 请求 MCP。

4. **复用只能是旁路，不是依赖**
   - 主流程没有跑、缓存缺失、缓存不完整时，复盘 worker 仍能自己补数据。
   - 不能因为复盘需要数据而扩大主流程必拉的数据范围。

### 3.3 推荐数据复用路径

```
Campaign 主分析
  ├─ 已有：拉取活动 7d 指标、产品级指标、策略上下文
  ├─ 已有：write_full 落决策与建议卡
  ├─ 新增：轻量写 review baseline / observation cache（不额外请求 MCP）
  └─ 返回前端，不等待复盘

复盘 worker
  ├─ 扫描 due review tasks
  ├─ 优先读取主流程留下的 observation cache
  ├─ 不足时按 review_observe meta_filter 轻量拉 MCP
  ├─ 代码规则判定 checkpoint outcome
  ├─ 更新活动级 memory text
  └─ 汇总更新 ASIN 级 product memory
```

## 4. 复盘触发模型

### 4.1 复盘链创建

对每个“被人工同意并执行成功”的活动级调整行为，创建一条 `activity_review_memory`。

创建条件：

1. card `confirm_status = CONFIRMED`
2. 至少一个 pending 动作 `execute_status = SUCCESS`
3. 动作不是灰卡、预过滤、LLM 丢失项
4. 非 dry-run；dry-run 只归档，不生成活跃复盘链

### 4.2 检查点规则

每条活动级复盘链最多三次复盘：

| 次数 | 触发时间 | 说明 |
|---|---|---|
| 第 1 次 | 执行后第 1 天 | 必做 |
| 第 2 次 | 执行后第 3 天 | 必做；完成后该复盘链成为合法复盘记忆 |
| 第 3 次 | 第 7 天，或第 3-7 天内再次调整前 | 最终复盘；完成后该复盘链结束 |

合法性规则：

1. 只有完成 **1 天 + 3 天** 两次复盘后，才允许注入 LLM。
2. 如果第 3 天前再次调整，该复盘链标记为 `EARLY_INTERRUPTED`，仅归档，不注入。
3. 如果第 3-7 天期间再次调整，先立即触发最终复盘，例如 `1/3/5`；随后新调整创建新的复盘链。
4. 如果第 3-7 天期间没有再次调整，第 7 天自动触发最终复盘，即 `1/3/7`。
5. 最终复盘后不再做第 4 次复盘。

### 4.3 再次调整的识别

再次调整分两类：

| 类型 | 识别方式 | 处理 |
|---|---|---|
| Agent 调整 | 同一 `parent_asin + campaign_id` 出现新的执行成功 pending | 若处于 3-7 天窗口，先做最终复盘，再创建新链 |
| 外部后台调整 | 当前 MCP 状态与系统 expected state 不一致，且无本系统执行记录 | 记录 `EXTERNAL_CHANGE`，若处于 3-7 天窗口，同样触发最终复盘 |

外部调整不直接判定原动作失败，只说明归因窗口提前结束。

## 5. 数据模型设计

### 5.1 ASIN 级管理表

表：`t_advert_agent_product_review_memory`

职责：按父 ASIN 管理活性、遗忘、产品级汇总文本。

核心字段：

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `parent_asin` | 父 ASIN |
| `decision_id` | 来源批次 |
| `season_stage_snapshot` | 执行时淡旺季阶段 |
| `ad_purposes_snapshot_json` | 执行时广告目的 |
| `target_acos_snapshot` | 执行时目标 ACOS |
| `baseline_product_json` | 产品级基线 |
| `latest_product_json` | 最近一次复盘观测 |
| `action_mix_json` | 本轮动作组合统计 |
| `activity_summary_json` | 活动复盘聚合，如达成/部分/未达成数量 |
| `product_outcome` | `ACHIEVED / PARTIAL / MISSED / MIXED / DATA_INSUFFICIENT` |
| `product_memory_text` | 注入策略总览的产品级复盘记忆 |
| `last_updated_at` | 最后一次 checkpoint 更新时刷新 |
| `active_until` | `last_updated_at + 14 days` |
| `status` | `ACTIVE / ARCHIVED` |
| `archive_reason` | `EXPIRED / SEASON_CHANGED / SUPERSEDED` |

### 5.2 活动级复盘链表

表：`t_advert_agent_activity_review_memory`

职责：记录某活动某次执行后的复盘链，产出活动级注入文本。

核心字段：

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `product_review_id` | 关联 ASIN 级管理表 |
| `parent_asin` | 父 ASIN |
| `decision_id` | 来源批次 |
| `suggest_card_id` | 来源建议卡 |
| `campaign_id` / `campaign_name` | 活动标识 |
| `child_asin` / `keyword` / `match_type` | 活动上下文 |
| `action_type` / `action_direction` | 动作类型与方向 |
| `executed_at` | 执行成功时间 |
| `baseline_activity_json` | 活动级基线，优先来自 `perf_json` |
| `success_criteria_json` | 代码模板生成的成功标准 |
| `checkpoint_count` | 已完成复盘次数 |
| `final_checkpoint_day` | 最终复盘天数，可能是 5 或 7 |
| `activity_outcome` | 活动级结论 |
| `activity_memory_text` | 注入逐活动 LLM 的复盘记忆 |
| `legal_after_3d` | 是否完成 1/3 天复盘 |
| `status` | `PENDING / LEGAL_ACTIVE / FINALIZED / EARLY_INTERRUPTED / ARCHIVED` |

### 5.3 检查点表

表：`t_advert_agent_review_checkpoint`

职责：保存每一次 1/3/最终复盘的观测与判定。

核心字段：

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `activity_review_id` | 活动级复盘链 |
| `parent_asin` | 父 ASIN |
| `checkpoint_day` | 1 / 3 / 7 / 实际提前天数 |
| `trigger_type` | `SCHEDULED_1D / SCHEDULED_3D / SCHEDULED_7D / BEFORE_NEXT_ADJUSTMENT / EXTERNAL_CHANGE` |
| `observed_activity_json` | 活动级观测 |
| `observed_product_json` | 产品级观测快照 |
| `comparison_json` | 与基线的差异 |
| `outcome` | 检查点结论 |
| `confidence` | `HIGH / MEDIUM / LOW` |
| `reason_code` | 规则命中码 |
| `created_at` | 复盘时间 |

### 5.4 可选观测缓存表

表：`t_advert_agent_review_observation_cache`

职责：主流程或复盘 worker 写入轻量观测，减少重复 MCP 请求。

核心字段：

| 字段 | 说明 |
|---|---|
| `parent_asin` | 父 ASIN |
| `campaign_id` | 活动 ID，可空 |
| `observe_date` | 观测日期 |
| `window_days` | 观测窗口 |
| `source` | `MAIN_ANALYSIS / REVIEW_WORKER` |
| `payload_json` | 指标快照 |
| `created_at` | 写入时间 |

缓存有效期建议 24 小时。缓存只用于减少 MCP 请求，不作为唯一真源。

## 6. 成功标准生成

成功标准由代码模板生成，不由 LLM 生成。

理由：

1. 复盘结论需要可审计、可回放。
2. 动作方向、指标阈值、窗口合法性属于规则系统，不应由 LLM 临场改写。
3. LLM 可在二期用于文案润色，但不得修改 `outcome`、`active_until`、`checkpoint_day` 等结构化结论。

建议新增模块：

```text
app/memory/review_criteria.py
```

模板输入：

```text
action_type
action_direction
ad_purposes_snapshot
target_acos_snapshot
campaign_group_type
baseline_activity_json
baseline_product_json
```

模板输出：

```json
{
  "primary": [
    {"metric": "acos", "op": "decrease_or_lte_target_plus", "value": 5}
  ],
  "guardrails": [
    {"metric": "orders", "op": "not_drop_more_than_pct", "value": 30}
  ],
  "required_metrics": ["spend", "orders", "acos"],
  "purpose": ["转化型"],
  "baseline_window_days": 7
}
```

典型动作模板：

| 动作 | 主判据 | 护栏 |
|---|---|---|
| 降 bid | ACOS 下降或接近目标 ACOS | 订单不明显下滑，花费不异常归零 |
| 提 bid | 曝光/点击/订单/排名改善 | ACOS 不明显失控 |
| 降预算 | 花费下降，ACOS 改善 | 订单不大幅损失 |
| 提预算 | 订单/销售/曝光增长 | ACOS/TACOS 不明显恶化 |
| 淘汰入低价池 | 无效花费下降 | 若仍出单，触发复评线索 |
| 新增活动 | 有曝光/点击/订单冷启动 | 花费不过阈值，ACOS 不失控 |

## 7. 复盘生成流程

### 7.1 执行成功后：创建复盘链

触发点：pending 表 `execute_status` 更新为 `SUCCESS` 后。

处理：

1. 读取 decision、card、pending、前置配置快照。
2. 冻结 ASIN 级基线：广告目的、目标 ACOS、预算、淡旺季阶段、产品级指标。
3. 冻结活动级基线：`perf_json`、old/new bid、old/new budget、state、placement。
4. 生成 `success_criteria_json`。
5. 写入 product review memory 与 activity review memory。
6. 生成 due checkpoint：T+1、T+3、T+7。

### 7.2 到期后：执行 checkpoint

复盘 worker 每天定时扫描：

```text
status in (PENDING, LEGAL_ACTIVE)
and due checkpoint <= today
and product memory status = ACTIVE
```

对每个 checkpoint：

1. 先读 `review_observation_cache`。
2. 缓存不足时，用 `review_observe` meta_filter 拉 MCP。
3. 计算 activity comparison。
4. 计算 checkpoint outcome。
5. 更新 activity memory text。
6. 聚合同一 product_review_id 下的合法活动复盘，更新 product memory text。
7. 刷新 `last_updated_at` 与 `active_until`。

### 7.3 第 3-7 天再次调整

当系统发现同活动发生新调整：

1. 如果旧链未完成 3 天复盘：标记 `EARLY_INTERRUPTED`，仅归档。
2. 如果旧链已完成 1/3 天，但未做最终复盘：立即触发 `BEFORE_NEXT_ADJUSTMENT` checkpoint。
3. 设置 `final_checkpoint_day = 实际天数`。
4. 旧链 `FINALIZED`。
5. 新调整创建新的复盘链。

## 8. 记忆文本生成与注入

### 8.1 活动级注入

活动级复盘记忆注入逐活动决策 prompt。

注入条件：

1. `legal_after_3d = true`
2. 所属 product memory `status = ACTIVE`
3. `active_until >= today`
4. 当前淡旺季阶段等于 `season_stage_snapshot`
5. 匹配同一 `campaign_id`，无 campaign_id 时用 `campaign_name + child_asin` 兜底

示例：

```text
【该活动复盘记忆】
上次降价控 ACOS 后，1/3/5 天复盘显示 ACOS 持续下降，订单未明显下滑；第 5 天再次调整前已完成最终复盘，结论为达成。本次避免反向提价，除非新数据证明流量明显不足。
```

### 8.2 产品级注入

产品级复盘记忆注入 Campaign 策略总览 prompt。

注入条件：

1. product memory `status = ACTIVE`
2. `active_until >= today`
3. 当前淡旺季阶段等于 `season_stage_snapshot`
4. 至少有一条合法活动级复盘链，或产品级数据足够形成 `DATA_INSUFFICIENT` 以外结论

示例：

```text
【产品复盘记忆】
本品上一轮以转化型为目标，执行 12 个活动调整。当前已有 8 条合法活动复盘，其中 5 条达成、2 条部分达成、1 条未达成；产品级 ACOS 下降但订单略降，整体判定为部分达成。本轮可继续控成本，但避免进一步压缩高转化活动预算。
```

### 8.3 文案生成方式

一期使用代码模板，保证稳定。

二期可加 LLM 润色，但必须满足：

1. LLM 输入只包含结构化结论。
2. LLM 输出只写 `memory_text`。
3. LLM 不能改 `outcome`、`confidence`、`active_until`、`checkpoint_day`。
4. LLM 失败时回退代码模板。

## 9. 遗忘与归档

复盘记忆按父 ASIN 管理活性。

活跃条件：

```text
today <= last_updated_at + 14 days
and current_season_stage == season_stage_snapshot
and status != ARCHIVED
```

遗忘规则：

| 情况 | 处理 |
|---|---|
| 超过最后一次更新 14 天 | `ARCHIVED / EXPIRED` |
| 淡旺季阶段变化 | `ARCHIVED / SEASON_CHANGED` |
| 新一轮产品级复盘覆盖旧轮 | 旧轮可 `ARCHIVED / SUPERSEDED` |
| 数据不足 | 保留 checkpoint，但不注入，等待补偿复盘 |

遗忘不是删除。归档后：

1. 不再注入任何 LLM 调用。
2. 可用于后台查看。
3. 可用于二期长期模式统计。

## 10. MCP 请求控制

目标：不阻塞主流程，同时尽量减少 MCP 请求。

设计：

1. 主流程已取得的数据全部通过 baseline/cache 复用。
2. 复盘 worker 使用专用轻量 meta_filter，例如：

```python
REVIEW_OBSERVE_META_FILTER = [
    "META_AD_PRODUCT",
    "META_CAMPAIGN_PERF",
    "META_KEYWORD_RANK",
]
```

实际名称以当前 `mcp_mapping.py` 支持的 meta 为准，原则是只拉复盘判定必需字段。

3. 同一父 ASIN 同一天多个 checkpoint 合并请求：
   - 先按 `parent_asin + observe_date + window_days` 分组。
   - 一次 MCP 拉回产品与活动集合。
   - 本地拆分给多个 activity review。

4. 缓存策略：
   - 当天主分析写入 `MAIN_ANALYSIS` cache。
   - 复盘 worker 写入 `REVIEW_WORKER` cache。
   - 24 小时内同 ASIN 同窗口复用。

5. 失败策略：
   - MCP 失败不重试阻塞主流程。
   - checkpoint 标记 `DATA_INSUFFICIENT`，进入下一次补偿扫描。
   - 连续失败超过 3 次，归档并标注 `DATA_UNAVAILABLE`。

---

## 11. 一期落地清单

一期只做可控闭环：

1. 新增三张复盘表：product memory、activity memory、checkpoint。
2. 修正或约束“同意+执行”直跑路径，确保执行成功可追溯。
3. 执行成功后异步/轻量创建复盘链。
4. 实现 `review_criteria.py` 代码模板。
5. 实现 `review_evaluator.py` 代码判定。
6. 实现每日复盘 worker。
7. 实现 activity/product memory 文案模板。
8. 在 Campaign 总览 prompt 注入产品级复盘记忆。
9. 在逐活动 prompt 注入活动级复盘记忆。
10. 实现 14 天 + 淡旺季变化的归档遗忘。

---

## 12. 二期扩展

二期再做：

1. LLM 文案润色，但不参与判定。
2. 跨产品长期记忆聚合。
3. 失败模式自动提高 review_level。
4. 外部后台调整的更精确识别与来源标注。
5. 可视化复盘面板：按 ASIN 展示产品级结论和活动级证据链。

---

## 13. 关键决策摘要

1. 复盘窗口只做 1/3/7 天。
2. 活动级复盘完成 1/3 天后才成为合法记忆。
3. 3-7 天内再次调整时，立即触发最终复盘，形成 1/3/N。
4. 3-7 天没有再次调整时，第 7 天自动最终复盘，形成 1/3/7。
5. 不做第 4 次复盘。
6. 复盘产出有活动级和产品级，但生命周期按 ASIN 统一管理。
7. 活性从最后一次更新起 14 天，并要求淡旺季阶段未变化。
8. 归档只是不再注入 LLM，不删除历史。
9. 复盘计算异步独立，绝不阻塞主分析落库。
10. 主流程可以留下可复用快照，复盘 worker 优先复用，减少 MCP 请求。
