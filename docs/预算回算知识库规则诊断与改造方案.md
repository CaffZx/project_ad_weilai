# 预算回算知识库规则诊断与改造方案 v2

> 记录时间：2026-08-05。诊断对象：`docs/knowledge_base/执行规则/23-广告组合与预算分配规则.md`。
> 触发现象：① 父预算大于组合当前预算和时 AI 不扩展；② 未按花费/表现分配；③ 父预算紧张时收缩表现好的组合；④ 组合预算极低偏离活动预算和。

---

## 一、发现的问题

### 1. 父预算大于组合和时，AI 不向上扩展

父预算 $80，各组合当前预算和 $60，AI 按 $60 来分而不是 $80。

**根因**：23号 §7（L553）硬约束"最终分配金额都不得超过各组合本轮 `requested_delta`"——这明确告诉 LLM **不要扩超出请求量**。§7.3（L609）进一步说"父 ASIN 预算充足→全额满足合规 requested_delta"。整个 §7 的语义是**按照请求来、不要超请求**，没有"父预算有富余时应主动识别可加预算的组合"的规则。

### 2. 未按组合花费和表现分配

**根因**：§7.2 给出场景表要求"经营者先生成优先级，再按真实消耗能力分配"，但没有收缩优先级——哪个组合先砍、按什么信号砍，LLM 自由裁量空间过大。§7.3 的场景表只给出了"什么时候用什么方式"，没有"预算不够时怎么选组合、砍多少"的具体规则。

### 3. 父预算紧张时，AI 收缩表现好的组合

父预算 $80，各组合花费和 $100 且表现还行，AI 会把主力组也砍掉。

**根因**：§3.6（GROUP-BUDGET-004）只有正向保护"精准主力组不得断供"，没有负向约束"不得砍花完且表现好的组合"。没有规则告诉 LLM"预算收缩时不该砍产出贡献者"——LLM 按常识均摊，砍掉了表现好的组合。

### 4. 组合预算极低，偏离活动预算和

组合 proposed $5，但组合内 3 个活动预算和 $18——组合管不住活动。

**根因**：知识库有安全上限（§4.3 超配比 ≤ 2 倍），但**没有安全下限**——没有规则说"组合预算最低不能低于活动预算和的多少"。§4.2 是放松约束（活动预算和可超父预算，因为不等于花费），不是下限规则。LLM 给出极低组合预算时没有任何规则阻止它。

### 5.（附带发现）`parent_allowed_net_increase`（可用净增）无数据源

23号 §7 用了 `available_reallocation_budget` 概念（= `released_budget + parent_allowed_net_increase`，L459），但没有规定 `parent_allowed_net_increase` 的计算方式或数据来源——它是占位概念。

## 二、知识库现有局限

### 2.1 §7 分配逻辑不完整

§7 现有三条路径（§7.3 场景表 L607-615）：
- 父 ASIN 预算充足 → 全额满足 requested_delta
- 父 ASIN 预算不足、无明确优先级 → 按 requested_delta 比例压缩
- 父 ASIN 预算不足、有明确优先级 → 按经营目标与真实数据动态分配

缺失三种场景的规则：
- **预算有富余**：父预算大于组合当前和时应主动扩展（不限于满足 requested_delta）——§7 没有扩张规则,只有"满足请求"
- **预算紧张**：§3.6/§4.1 给了保护方向但缺少收缩时砍谁、砍多少、砍的顺序——"动态分配"只说"先生成优先级"但不给优先级生成规则
- **预算显著不合理**：花费已远超父预算且表现好时,§3.6/§4.1 的硬约束(`proposed 之和 ≤ budget_pool`)会让 LLM 压缩产出贡献者——缺少降级处理规则告诉 LLM 可以"不强制压到 budget_pool,按保障产出原则维持"

### 2.2 缺少组合预算安全下限

§4.3 定义超配比上限（活动预算和 ≤ 组合预算 × 2.0,≥$5 主力有出单时不可超 2.0）,但**没有下限**——即"组合预算最低不得低于活动预算和的 X%"。没有下限,AI 可以给极低值。

### 2.3 §7.2 动态分配缺少收缩优先级

§7.2（L573-601）写"经营者先生成优先级,再按真实消耗能力分配"，给了场景表(推词/限时修复/积极推进/稳定/控制清货),但这些场景描述的是**扩张时谁优先加**，没有**收缩时谁优先砍**。两者是不同的:扩张优先不等于收缩豁免——一个组合在"推词场景"应当优先加,但预算不够时是否就不能砍?规则里没有说。

### 2.4 `parent_allowed_net_increase`（可用净增）无数据源

23号 §7（L459）使用 `available_reallocation_budget = released_budget + parent_allowed_net_increase` 概念,但知识库本身没有规定 `parent_allowed_net_increase` 的计算方式或数据来源——它是一个占位概念。

## 三、改造建议方案（仅知识库 23号）

### 3.1 §4.1 核心原则补一条防御原则

在 GROUP-004 和 GROUP-005 之间插入：

```
| GROUP-BUDGET-004A | 预算收缩不得砍花完且表现好的组合（spend_utilization ≥ 70% 且 ACOS ≤ 目标）。这些组合贡献产出，砍它们不如砍花不完/ACOS 超标的。收缩按 §7.4 优先级执行。 |
```

### 3.2 §7.3 场景表补三种场景的分配方式

原 §7.3（L607-615）场景表的"父 ASIN 预算充足/不足/明确推词…"已经覆盖了部分场景。在表格后补充：

```
| 父 ASIN 预算显著低于花费总和 | 不强制压缩到 budget_pool；按花费比例维持有产出能力的组合，reason 写"花费已超父预算，建议提升" |
| 父 ASIN 预算有富余（> 组合当前和） | 不限于满足 requested_delta；识别 spend_utilization≥70% 且 ACOS 达标的组合主动加预算 |
| 父 ASIN 预算不足需要收缩 | 按 §7.4 优先级执行，不得均摊 |
```

### 3.3 新增 §7.4 预算收缩优先级

在 §7.3 之后新增：

```
### 7.4 预算收缩优先级

当 budget_pool < Σcurrent_group_budget 时，按以下优先级收缩，不得均摊。

| 优先级 | 条件 | 处理 |
| --- | --- | --- |
| P0（不可砍） | spend_utilization ≥ 70% 且 acos_7d ≤ 目标 ACOS（花完且表现好） | 保护，proposed = current |
| P1（保护） | GROUP-BUDGET-004 触发：精准主力组 7天花费 ≥ $5 且有出单 | 维持或微降（降幅 ≤ 10%），不得断供 |
| P2（可砍） | spend_utilization < 50%（花不完）或 acos_7d > 有效容忍上限 | 优先压缩，proposed 降至 campaign_budget_sum_after × 0.8 |
| P3（压缩） | 其余组合 | 按比例降，proposed 不低于 campaign_budget_sum_after × 0.7 |

硬约束：收缩后每组 proposed ≥ campaign_budget_sum_after × 0.6（绝对下限，低于此值是组合管不住活动）。
```

### 3.4 新增 §7.5 父预算不合理时的降级处理

```
### 7.5 父预算不合理时的降级处理

触发条件（全部满足）：
① Σ各组日均花费 > parent_target_daily_budget（父目标已填不满花费）
② 存在 ACOS 达标的组合（有产出，不是全盘低效）
③ parent_allowed_net_increase = 0 或不足以覆盖差额

处理：
- proposed 按各组当前花费比例分配可用 budget_pool（不是按 requested_delta，不是均摊）
- proposed 之和不强制 ≤ budget_pool（允许接近但不超过各组花费合计），最高不超过 Σ 当前花费
- reason 必须写明：当前花费已超父预算 × 多少，主力组 ACOS 现状，建议提升父预算至多少

约束：
- 仅当有产出证据（至少一个组合有花费且 ACOS 达标）时触发
- 花不完的组合不适用（走 §7.4 正常收缩）
```

### 3.5 补组合预算安全下限

在 §4.3"健康比例"表里，除现有的上限（≤ 2.0 倍）外，补下限行：

```
| 绝对下限 | 活动预算和 × 0.6 ≤ 组合预算 | 低于此值时组合管不住活动，proposed 不得低于此值 |
```

并在 §7.4 硬约束里引用（`proposed ≥ campaign_budget_sum_after × 0.6`）——已含在 3.3 的表中。

### 3.6 补 `parent_allowed_net_increase` 数据源说明

在 §4 或 §7 开篇补一段：

```
> `parent_allowed_net_increase`（可用净增）：当前无自动化数据源，由运营手动配置。
> 为父目标预算之上的额外增长空间（如旺季要扩预算）。默认 = 0 = 无净增，
> budget_pool = parent_target。后续数据源方向：按父预算 × 20%，或与长期配置 daily_budget_override 联动。
```
