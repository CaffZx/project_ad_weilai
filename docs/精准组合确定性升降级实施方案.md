# 精准组合确定性升降级实施方案

> **For agentic workers:** REQUIRED SUB-SKILL: Use `executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**目标：** 用 32 号精准组合规则替换现有精准活动的旧 `$5` 分组迁移；分组判断完全由代码完成，并将结果落入既有 ERP decision/card/pending/执行链路。

**架构：** 广泛、词组、自动的确定性收拢已完成；本方案只覆盖单关键词 EXACT。每日指标事实、生命周期、诊断状态和 Agent 已确认动作均持久化在 ERP，不使用 State 库。Campaign 分析先采集并落 ERP 事实，再运行确定性精准规则；执行 MCP 只读取 `campaign_pending.target_campaign_group_type`，不再次判断是否迁组。

**技术边界：** Python、MySQL ERP、既有 `ErpDualWriterRepository`、既有 Campaign MCP 与 pending/执行 mapper。不开新 pending 表，不开新 MCP 工具，不修改 `mysql_state_manager.py`。

8. 上表中的“3 个成熟自然日”必须按站点日期的 D-1 快照计数：锚点当天不计入，快照缺失或不是连续完整日则不计数。不得以“已经过了72小时”替代。

## 1. 已确认的权威口径

1. 适用对象仅为单关键词 `EXACT` 活动；多关键词 EXACT 不进入本规则引擎。
2. 当前归属必须每轮从 `ad_campaign_list` 返回的真实广告组合名称读取，再经公共 helper 判定；生命周期表不维护“当前组别”。
3. 精准测试→主力的必要条件：连续 3 个站点已结束自然日每日花费严格大于 `$5`、三日汇总 ACOS 小于目标 ACOS、近 7 日自然排名较前 7 日提升。
4. **目标 ACOS** 与 **有效容忍上限**是两个不同的预计算值：目标 ACOS 用于主力准入和“表现好”判断；有效容忍上限用于判断何时进入降 Bid、降预算、回落和淘汰路径。
5. 有效容忍上限严格按 15 号§4.1 的加法公式计算：`目标ACOS + 阶段加值×经营模式系数 + 广告目的加值 + 淡旺季加值 + 特殊场景加值 − 女装毛利退货修正`；不得使用目标 ACOS 的乘法倍数代替。
6. 轻度回落：`目标 ACOS < 三日汇总 ACOS <= 有效容忍上限`，且近 7 日有订单；留主力组，维持或小幅优化，不迁组。
7. 中度回落：连续两个三日周期的汇总 ACOS 均 `> 有效容忍上限`，且满足“无转化或订单下降”及自然位条件，才能主力→测试。
8. 严重回落只能由测试组进入低价捡漏组；预算 `$1.00`、Bid 为 `min(current_bid, 0.20)`、三个广告位均为 `0%`。
9. 无可降低广告位时，诊断路径跳过“降广告位→观察”，直接走“降基础 Bid→观察 3 个成熟自然日”；不得伪造广告位动作。
10. 运营手动改动以本轮实际读取的广告配置为准；“改了又改回”无法从快照恢复，按已确认边界不处理。

32 号中“自然位仅在 Ranking 场景为强校验”的旧表述，不采用；本功能以自然位提升为精准主力准入必要条件。ACOS 相关口径则以 15 号§4 的有效容忍上限为唯一权威。

## 1.1 ACOS 约束预计算与统一消费

### 两条 Campaign 入口必须同义，不共享“策略层实时产出”作为前提

| 入口 | 配置来源 | 既有数据加载 | 本功能可消费的字段 |
| --- | --- | --- | --- |
| 实时分析 | 现有 State 中已保存的 `long_term_config`、`workflow_state` | 现有 `ensure_data()` / `DataAggregator` 得到的 `ASINData` | 已保存的产品阶段、经营模式、广告目的、季节阶段；既有 `ASINData` 的毛利率、退货率、广告销售额、订单数；既有三级回落已解析的目标 ACOS |
| 定时批跑（`cfg_source=config`） | ERP `decision_config` 的已保存 1–4 层配置，覆盖本轮 `long_term` | API 入口现有 `DataAggregator.fetch(... META_AD_PRODUCT, META_TREND)` 得到的 `ASINData` | 与实时分析同一组字段；**不依赖、不触发策略层实时产出** |

因此，本功能不要求策略层新透传任何字段，也不新增 MCP。两条入口都在各自已经完成“读取已保存配置 + 拉取 Campaign 既有 `ASINData` + 三级解析目标 ACOS”之后，调用同一个无 I/O 的填充函数。它只接受 `CampaignStrategyContext` 和本轮已加载的 `ASINData`，不读 State/ERP/MCP，不自行解析配置。

在进入下游 LLM、护栏和精准规则前，组装唯一的运行时约束包：

```text
target_acos
effective_acos_tolerance
tolerance_components
target_cpa
```

- `effective_acos_tolerance` 是百分点数值，不是倍率；
- `tolerance_components` 保存每个加/减项，供卡片 evidence、日志和排查使用；
- `target_cpa = 平均订单金额 × target_acos`，按 14 号§20 / 03 号§7 用于无单花费门槛；平均订单金额取本轮已加载的 `ASINData.ad_data.sales / orders`，不单独拉取；不可得时沿用知识库规定的兜底值并提升审核等级；
- 以上值只在本轮运行时 `CampaignStrategyContext` / `ctx_dict` 中派生，不写为运营手工配置，不加入经营模式映射；
- Campaign 分析只读取这组已传入或已派生字段，**不为计算有效容忍上限或目标 CPA 新增任何 MCP 调用**；毛利率/退货率只读取既有 `ASINData`，不在 Campaign 内重复拉取。

当前没有“是否促销”的已确认字段：`long_term_config`、`decision_config` 与 `ASINData` 均不能提供可作为 15 号§4.1 依据的促销状态。本期计算中促销加值固定为 `0pp`，并在纯函数调用处保留如下明确注释，禁止把 `discount_rate` 或任意 Listing 信号臆断为促销：

```python
# TODO(promotion-context): 当前 Campaign 上下文没有已确认的促销标记；
# 15号§4.1 的 promotion +15pp 本期固定为 0。
# 不得用 discount_rate 或其他字段推断；待上游提供明确字段后再透传接入。
```

LLM prompt、既有护栏、精准确定性规则引擎都只读取这组已算好的值；任何下游不得自行重新计算容忍上限或写目标 ACOS 倍数判断。

- `keyword_child_asins` / `own_keyword_flow`：当前自然排名；前者还可能提供近次变化。
- `ad_campaign_product_report`：按日期窗口返回花费、销售额、点击、订单；当前主流程使用它拉 7 日汇总。

### 3.2 必须补的 D-1 指标拉取

`own_keyword_flow` 不返回某个自然日的 spend / sales / orders / clicks，不能充当日指标快照来源。

在 `app/data/campaign_fetcher.py` 中复用现有 `ad_campaign_product_report` 调用和解析器：

- 仅对单关键词 EXACT 活动额外请求一次；
- 日期为 `make_date_window(1, site_code)` 返回的 `end_date`，即站点最新已结束自然日 D-1；
- 不新增 MCP 工具，不调用无关工具；
- 7 日报告继续服务既有 LLM/看板，D-1 报告只服务 ERP 日快照。

`stat_date` 本身已表示完整已结束站点日，因此规则查询不使用 `is_complete_day`。若 ERP 真实表仍保留该历史列，代码不读、不写；后续 DDL 整理另行执行，不与功能接线混在本期。

## 4. ERP Repository 方法

在 `app/persistence/erp_writer/repository.py` 增加最小方法集，不新建 repository：

| `upsert_campaign_metric_daily(...)` | 每次 Campaign 分析拿到 D-1 指标后 | 按 ERP 唯一键单行 `INSERT ... ON DUPLICATE KEY UPDATE`，覆盖同日事实 |

## 5. 生命周期与运营干预判定

### 5.1 初始化与观察窗

- 首次看到单关键词 EXACT 时创建生命周期行。
- `campaign_created_at` 必须来自 `ad_campaign_basic_info_v2`；缺失或无法解析时，不得作原生型严重回落。
- 当前在测试组、且从未记录 Agent 降级时，初始化 `testing_origin=native`。若该活动实际曾由运营人工降级，按原生型 14 天观察是保守处理，不会提前淘汰。
- Agent 主力→测试最终执行成功后，写 `testing_origin=demoted` 与 `demoted_at`；严重回落观察窗才可按 7 天计算。

### 5.2 配置差异与归因

本轮 `basic_info_v2` 的实际值与 lifecycle 的 `last_seen_*` 比较：

- Bid：绝对差大于 `0.01`；
- 预算：绝对差大于 `0.50`；
- 广告位：差异大于 1 个百分点；
- 活动状态：字符串不同。

若当前值符合已确认的 `last_agent_*_target`，归因 Agent，自身诊断进度保留。否则归因 `OPERATOR_OBSERVED`：

- 人工上调、恢复广告位或改状态：清空诊断路径/阶段，下轮依据当前状态重新判定；
- 人工下调 Bid/预算：写入一轮可审计温和动作，可参与保护词“至少一轮温和动作”的事实判断；
- 运营短暂修改后又改回：不可从两次快照识别，明确不处理。

## 6. 纯确定性精准规则模块

新建 `app/workflow/steps/campaign_exact_transition.py`，只放无 I/O 的规则和数据模型；不让 `campaign.py` 堆积 32 号布尔判断。

输入：当前单关键词 EXACT `CampaignUnit`、实时组合分类、已预计算的 ACOS 约束包、日指标窗口、生命周期、保护词结果。

输出：`ExactTransitionDecision`，包含：

- `transition_type`：`promote_to_core` / `demote_to_testing` / `eliminate_to_low_bid` / `stay_with_adjustment` / 空；
- `target_campaign_group_type`；
- `severity_tier`；
- 预算/Bid/广告位的确定性目标值；
- `review_level`；
- 验证窗口、自然位比较、保护结论、诊断步骤等结构化 evidence。

判定顺序固定：

1. 验证活动为单关键词 EXACT，当前真实组为主力或测试；否则无结果。
2. 验证数据成熟度。升组和中度/严重自然位条件至少需要 14 个 D-1 及以前的日快照；不足不迁组。
3. 测试组先判升主力；未通过再判严重回落。
4. 主力组依次判轻度、中度；轻度使用“目标 ACOS 与有效容忍上限之间”的区间，中度使用“连续两轮超过有效容忍上限”的条件；主力不得直接转低价。
5. 任何中度/严重路径先执行保护词否决和诊断门槛。
6. 不满足迁组门槛时返回空迁组，不把 LLM 的旧 `$5` 分类作为后备方案。

保护词判定须覆盖核心词、标题、后台 Search Term、核心卖点。当前可靠输入为 `is_core_keyword`；标题/ST/卖点的确定性来源在实现前逐项核对。任何保护维度缺数据时，不允许自动中度降级或严重淘汰，输出 `MANUAL_REVIEW` 原因。

## 7. 诊断与动作值

1. 轻度回落：保持主力组；按 32 号§2.2 的精准专用规则下调 Bid 或预算并继续观察，确定性引擎不迁组。19 号§1 的通用“表现一般”分级不能覆盖该精准专用回落规则；具体下调数值仍复用 19 号与 15 号的已确认幅度/护栏。
2. 中度回落：主力→测试；必须同时写目标组合、下调预算、下调 Bid，并标 `MANUAL_REVIEW`。
3. 严重回落：测试→低价；写目标组合、预算 `$1.00`、Bid `min(current_bid, 0.20)`、TOS/PP/ROS 均为 `0%`，标 `HIGH_RISK_REVIEW`。
4. 诊断有广告位可降时：先写广告位下降动作和阶段；满 3 个成熟日后才可写 Bid 下调动作。
5. 诊断无广告位可降时：直接写 Bid 下调阶段；满 3 个成熟日后才可评估严重回落。

中度降级的具体下调幅度复用知识库 19 号、15 号已实现的数值/护栏口径；实现前必须定位现有可复用计算函数。若现有代码没有可复用的确定性幅度函数，不得由 LLM 补值，也不得擅自硬编码新比例；应先补一个基于已确认规则的纯计算函数，再接入迁组。

## 8. Campaign 主流程接入

### 8.1 入口一致性接线（先于规则引擎）

为避免实时和定时的目标 ACOS/容忍上限漂移，先将“目标 ACOS 已解析后的约束填充”收敛为同一个无 I/O 函数；函数不新增输入来源。

1. `app/workflow/steps/campaign.py:run_campaign_analysis()`：保持现有顺序，`manual → P3 → algorithm` 解析完 `strat_ctx.target_acos` 后调用该函数。
2. `app/api/campaign.py:_do_analyze()`：实时 API 与 `cfg_source=config` 定时批跑共用此入口；在该入口同样完成 `manual → P3 → algorithm` 后、调用 `analyze_campaigns()` 前调用同一函数。
3. `cfg_source=config` 仅改变 `long_term` 的来源（已保存 ERP 配置），不改变约束函数的输入形状；不调用目的/策略/经营模式的策略层生成流程。
4. `analyze_campaigns()` 及后续 LLM、护栏、精准引擎只读取已填好的 `CampaignStrategyContext`，不得补拉数据或再次计算。

验收点：对同一份已保存配置、同一份 `ASINData`、同一目标 ACOS，实时和定时入口生成的 `effective_acos_tolerance`、`tolerance_components` 与 `target_cpa` 完全相同。

### 8.2 精准规则主流程

修改 `app/workflow/steps/campaign.py`，顺序固定为：

```text
CampaignFetcher 获取当前数据
→ 精准 D-1 报告
→ ERP 写日指标、更新生命周期配置观察
→ 原有 LLM 分析与既有护栏重试
→ 已完成的广泛确定性收拢
→ 精准确定性规则覆盖迁组/诊断结果
→ 最终护栏一次（不触发新的 LLM 重试）
→ 既有预算回算
→ mapper 落 card + campaign_pending/keyword_pending/placement_pending
```

精准规则生成的 `CampaignAdjustmentItem` 必须使用既有字段：

- `target_campaign_group_type`：只有确实需要迁组且当前真实组不同才填；
- `proposed_budget`：活动预算动作；
- `proposed_bid`：关键词 Bid 动作；
- `placement_adjustments`：严重回落的三个 0%；
- `triggered_rule`、`reason`、`evidence`、`review_level`：运营审计展示。

现有 mapper 已能把一张卡拆到同一活动的 `campaign_pending`、`keyword_pending`、`placement_pending`；不加挪组 pending 表。`campaign_pending.target_campaign_group_type` 为空时，执行 MCP 不得携带 `campaignGroupType`。

迁组/降预算后必须继续走既有组合和父 ASIN 预算回算；预算回算不通过时，不得输出该迁组 pending。

## 9. 执行终态回写

修改 `app/workflow/steps/advert_execution.py` 的普通 Campaign 异步终态回写路径：

1. MCP 提交成功仅标 `IN_PROGRESS`，不得写 Agent 动作确认锚点。
2. 终态查询得到活动 `SUCCESS` 后，从该活动已执行的 pending 取实际目标值。
3. 调用 ERP repository 的 `record_exact_agent_action_success(...)` 回写 lifecycle。
4. `FAIL`、`DRY_RUN`、未返回终态、未确认的 pending 均不写锚点。

立即退出使用独立链路；本方案不改变其已存在的执行与终态行为。
