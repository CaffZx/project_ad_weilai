## 一、需要什么数据

### 1.1 数据粒度

```
campaign_key = campaign_name + " × " + child_asin
每行 = 一个广告活动的完整画像

运营确认：活动名称 × 子ASIN 唯一确定一个广告活动。
同活动多关键词、同关键词多活动是存在的少数特殊情况，
仅靠 child_asin + match_type + keyword 不能区分。
```

### 1.2 数据来源

**原则：Doris 轻量发现 campaign 上下文（仅维度） → MCP 主力拉效果数据 → MCP 失败时降级 Doris。**

| 数据 | 来源 | 获取方式 |
|------|------|---------|
| 广告名称 / 子ASIN / 关键词 / match_type | **Doris 上下文查询** | `dwd_amazon_ad_keyword_report` JOIN `dwd_amazon_ad_product`，仅取维度字段。`campaign_budget`/`campaign_status` 不参与 GROUP BY（预算变更会产生重复行，且 MCP 返回真实值）；仅 `campaign_name + campaign_id + child_asin + keyword_text + match_type` 参与分组 |
| keyword_bid | **Doris 上下文查询** | `AVG(keyword_bid)`，同一条 SQL |
| campaign_budget / 状态 | `ad_campaign_basic_info` (MCP) **必拉** | ~110 次并行 (semaphore=8)，交叉验证 Doris 上下文中的同名字段 → 失败回落 Doris |
| **days_online（活动上线天数）** | `ad_campaign_basic_info` (MCP) **必拉** | 返回真实创建日期（如 2025-01-10 → 504 天）。Doris 上下文查询无法提供此字段（7d 窗口限制） |
| 活动级汇总指标 (CTR/CPC/CVR/ACOS/花费/销售额/订单/曝光) | `ad_campaign_product_report` (MCP) **必拉** | ~110 次并行，传 7d 日期范围 → 失败回落 Doris 按 campaign_name 聚合 7d |
| per-campaign 广告位拆分 | `ad_campaign_placement_report` (MCP) **懒加载** | LLM 标记需调整的精准广告后按需拉取 → 失败回落 Doris（按 campaign_id 查 `dwd_amazon_ad_placement_report_update`，需新写四桶聚合，不复用现有 TOS/ROS 两桶函数） |
| per-campaign 搜索词表现 | `ad_campaign_search_term_report` (MCP) **懒加载** | LLM 标记需调整的广泛广告后按需拉取 → 失败回落 Doris |
| 长周期数据 (21d) | `ad_campaign_product_report` (MCP) **按需** | 仅 sanity_check 触发，传 start=21d 前 → 失败回落 Doris 查 21d 窗口 |

### 1.3 数据缺口状态

| 缺口 | 状态 | 解决方案 |
|------|:--:|------|
| campaign_budget | ✅ 已填 | `ad_campaign_basic_info` 实测返回预算字段 |
| placement per-campaign | ✅ 已填 | MCP 返回 + Doris 回落均已验证 |
| 搜索词 per-campaign | ✅ 已填 | `ad_campaign_search_term_report` 实测返回 |
| 活动上线天数 | ✅ 已填 | `ad_campaign_basic_info` 实测返回真实创建日期 |
| match_type | ✅ Doris | 上下文查询补（`dwd_amazon_ad_keyword_report.match_type`） |
| keyword_bid | ✅ Doris | 上下文查询补（`AVG(keyword_bid)`） |
| 品类参考 CPC | ⚠️ 运营配置 | KB 标注为 ERP/运营提供 |
| Custom 词池 | ⚠️ 运营配置 | 运营手动维护 |

## 二、数据模型

### 2.1 CampaignUnit — 活动画像

```python
class CampaignPerf(BaseModel):
    clicks: int = 0
    cost: float = 0.0
    sales: float = 0.0
    orders: int = 0
    acos: float | None = None
    cvr: float | None = None

class CampaignUnit(BaseModel):
    """campaign_key = campaign_name + " × " + child_asin（运营确认：唯一确定一个活动）"""
    campaign_name: str                       # 广告名称（Doris 发现 / MCP 返回）
    campaign_key: str = ""                   # "活动名 × 子ASIN"
    child_asin: str                          # 广告ASIN（Doris 发现）
    seller_sku: str = ""                     # 广告SellerSku（Doris 发现）
    keyword_text: str                        # 关键词（Doris 发现）
    match_type: str = "EXACT"                # EXACT / BROAD / PHRASE（Doris 发现，MCP 不返回）
    current_bid: float = 0.0                 # 关键词出价（Doris 发现，MCP 不返回）
    current_budget: float = 0.0              # ad_campaign_basic_info → Doris 回落
    campaign_status: str = ""                # ad_campaign_basic_info → Doris 回落
    days_online: int = -1                    # ad_campaign_basic_info（-1=未知，勿当新活动）
    perf_7d: CampaignPerf                    # ad_campaign_product_report(7d) → Doris 回落
    placements: dict[str, dict] = {}         # ad_campaign_placement_report(懒加载) → Doris 回落
    placement_data_available: bool = False   # 懒加载前为空
    # 元数据
    source: str = "mcp"                      # "mcp" | "doris" | "mixed"
    flags: list[str] = []
```

## 三、Agent 需要输出什么

### 3.1 action 枚举（以 KB 为准）

```
eliminate_to_low_bid_pool — 淘汰（预算=$1, bid=$0.20, 广告位清零，活动保持启用）
adjust_budget             — 仅调预算
adjust_bid                — 仅调出价
adjust_placement          — 仅调广告位分配（仅精准广告）
keep                      — 保持现状
（suggest_split — 建议拆分：本期不启用，多关键词活动已在代码层过滤；后续迭代再加）
```

### 3.2 淘汰广告活动（对应 KB 21 号文件）

```
触发条件 + 保护条件 + 固定执行值 → 全部由 LLM 对照 KB 21 号文件判定。
代码不做淘汰判断，仅提供事实数据。
```

### 3.3 调整广告活动（对应 KB 18 流程 + 22 方向判定 + 19 数值规则）

**精准广告（exact）**：
- Budget 调整：按 19 §6 预算决策矩阵
- Bid 调整：按 19 §3 Bid 变化幅度（大涨±$0.05、小涨±$0.02）
- Placement 调整：按 19 §5 广告位决策矩阵

**广泛/词组广告（broad/phrase/auto）**：
- Budget/Bid 调整：按 19 §7 自动广泛组规则
- 不做 Placement 调整
- 必须执行 Search Term 否词（19 §8）

### 3.4 调整建议必须输出的字段（以 KB 为准）

```
proposal_type, campaign_key, action_type
adjustments: {budget: {current, proposed, reason}, bid: {current, proposed, reason}}
placement_adjustments: [{placement, current_pct, proposed_pct}] 仅精准广告
search_term_actions: {negative_keywords, promoted_keywords}      仅广泛广告
elimination_values: {budget, bid, placements}                    仅淘汰
elimination_reasons: [{reason_code, evidence}]                   仅淘汰
evidence: []
review_level: AUTO_BATCHABLE | MANUAL_REVIEW | SENIOR_APPROVAL
```

## 四、Agent 决策流程

### 4.1 核心原则

规则和阈值全部在 KB `.md` 文件中，代码不做 if-else 判断。LLM 通过分批 + 多轮投票机制解决上下文爆炸、交叉污染、误判三大问题。

### 4.2 分批机制

每批 ≤ 6 个 campaign，2 轮随机重分组。每批之间完全独立的 LLM 会话。

### 4.3 投票机制

```
Round1 + Round2 对比:
  9 种方向中同一种 → 采纳, confidence: "high", 取幅度更保守的
  不同 → Round3

Round3:
  直接采信, confidence: "medium"
  （R1/R2 已不一致需要打破僵局；若 R3 与其中一个一致则自然两票胜出；
   若三者全不一致，经层层筛选后出错概率极低，直接采信 R3）

### 4.4 suggest_split 暂不启用

```
条件: COUNT(DISTINCT keyword) per campaign_name > 1
当前阶段：多关键词活动在代码层直接过滤，不进入 LLM 分析。
后续迭代再启用 suggest_split 判定。
```

### 4.5 执行步骤

```
Step 1 — 数据准备（详见 campaign 数据源改造方案）
  · Doris 上下文查询 → 仅维度字段 (campaign_name / child_asin / keyword_text /
                          match_type / keyword_bid)
  · 代码硬过滤 → 排除 status 非 ENABLED / 近7天无数据 / 多关键词活动(暂)
  · MCP ad_campaign_basic_info 并行 (~110次, semaphore=8) → days_online / budget / status
  · MCP ad_campaign_product_report 并行 (~110次, semaphore=8, 7d) → CTR/CPC/CVR/ACOS/指标
  · MCP 失败 → Doris 单活动回落
  · placement / search_term 不在首轮拉取，LLM 标记后按需懒加载

Step 2 — 分批 LLM 调用 (Round 1 + Round 2)
  输入: docs/knowledge_base/执行规则/ 下的 KB 文件 (18/19/21/22号) + strategy_params
  每批: ≤ 6 个 campaign 独立判断
  LLM 为每个 campaign 输出: action + direction + reason + evidence

Step 3 — 投票判定
  R1+R2 同方向 → 采信, confidence: high, 取保守幅度
  R1+R2 不同 → Round3 直接采信, confidence: medium

Step 4 — 合并排序
  淘汰 > 调整 > 拆分 > 保持

Step 5 — 后处理
  resolve_budget_conflicts (按优先级依次执行，超限截断不缩放)
  sanity_check:
    · 仅做纯事实陈述，不硬编码 KB 阈值（消除"代码与 KB 双源漂移"）:
      - 对每个活动汇总: "近 7 天花费 $X, 订单 Y, CVR Z%, 自然位支撑 否"
        （KB 21 判断窗口=近7天 + 连续3天 ACOS，无 14/21 天）
      - 让 LLM 对照 KB 21/22 规则自行判定是否触发淘汰/调整条件
    · 一致性校验: LLM 结论 vs 事实矛盾（如判 eliminate 但 CVR>0 与
      NO_CVR_HIGH_SPEND 不符）→ 进 warnings，不重编 KB 数字
    · "连续3天 ACOS" 等逐日证据: 仅对 LLM 标记为疑似淘汰的少数活动，
      懒加载阶段补 3 个单日 ad_campaign_product_report 确认
```
