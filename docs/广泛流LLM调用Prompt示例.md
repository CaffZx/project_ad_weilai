## 业务知识优先级（必须遵循）
1. 本次注入 KB 中的禁止条件、保护条件和前置诊断步骤优先于任何经验判断。

## 文本与数值自洽（强制，输出前自检）
reason 里的动作描述（含(3)调整建议）必须与你同时输出的 proposed 数值**严格同向同值**：
- 方向词「提升/调高/加大」⟺ proposed > current；「降低/下调/收紧」⟺ proposed < current；「维持」⟺ proposed = current。bid 与 budget 各自独立判断。

## KB 引用指引（决策链：诊断 → 取值 → 动作）
1. **先算容忍度**: KB 17 §2 + KB 15 §4（目标ACOS + 阶段加值 + ranking/旺季/promotion 加值）。所有 ACOS 高低判断必须对比该值，禁止硬编码"ACOS>40%"。
2. **再定问题类型**: KB 17 §1（BLOCKED / SAMPLE_INSUFFICIENT / CVR_WEAK / HIGH_ACOS_* / BUDGET_* / KEYWORD_POOL_DIRTY / ALL_HEALTHY）。广泛/词组活动尤其关注 KEYWORD_POOL_DIRTY、HIGH_ACOS_* 的否词治理路径。
3. **查动作矩阵**: KB 17 §3 按广告方向 × 问题类型取有序动作（广泛活动多走 §3.2 expand_keywords / §3.3 optimize_acos）；冲突时进 KB 17 §4 裁决；如指向淘汰，必须先走 KB 17 §7 的"广泛/词组淘汰前诊断路径"（先否词 → 仍无改善才降 Bid/预算 → 仍无改善才淘汰）。
4. **取约束数值**: KB 15 §1（Bid 公式/保护规则/硬上下限）、KB 15 §2（预算范围 + 淡旺季系数）。
5. **应用幅度系数**: 最终幅度 = KB 19 基础幅度 × KB 17 §5.2 阶段系数 × KB 17 §5.3 淡旺季系数。
6. **否词决策**: 仅对输入中带有逐词搜索词数据的活动判断否词；先读 KB 30 §2（必需数据）确认数据可用，再按 KB 30 §3 判断相关性，最后走 KB 30 §5 准入规则和 KB 30 §6 精准/词组选择。7d 是动作基线，14d 仅是长尾/低流量/样本不足词的辅助观察，不能单独触发动作。词级样本不足按 7d「点击<10 且花费<max($15, 目标 CPA)」判定；无逐词搜索词数据或取数状态为跳过/失败时，`negative_keywords=[]` 且不得输出该活动的提精准候选。证据中的点击、花费、订单、销售额、ACOS、CVR 数字必须明确写 7d 或 14d；校正指标不可用时不得用 raw 指标替代动作判断。

## 1. 问题类型定义

### 1.1 判断顺序（命中即止）

```
① 特殊场景已激活（02号§7）→ 直接走特殊场景逻辑，跳出本文
② BLOCKED 类（数据/库存阻断）
②b 经营模式硬路径（立即退出）→ 确定性动作，不进入 LLM 判断（18号§0）
③ STAGE_EXPIRED_TESTING（测试期超期）
④ SAMPLE_INSUFFICIENT（样本不足）
④ CVR_WEAK（页面转化问题）
⑤ ACOS 类问题
⑥ 预算类问题
⑦ 排名类问题
⑧ 词池 / 广告位类问题
⑨ ALL_HEALTHY
```

### 1.2 问题类型表

**注意：所有 ACOS 类问题的判断阈值，必须先用 `15-策略约束值规则.md §4` 计算当前有效容忍上限，不得使用硬编码倍数。**

| 问题类型代码 | 判断条件 | 描述 |
|------------|---------|------|
| `BLOCKED_INVENTORY` | 库存天数 < 7天 | 库存不足，阻断所有增长动作 |
| `BLOCKED_DATA_MISSING` | 必需数据缺失（排名/广告位/库存） | 数据缺失，无法决策 |
| `STAGE_EXPIRED_TESTING` | `product_stage = 测试期` 且距阶段设置日已满 `03号§2` 的最长测试天数 | 测试期超期。冻结增长型动作 + 阶段 ACOS 加值归零（`15号§4.2`）+ 输出 MANUAL_REVIEW 要求运营确认阶段。Agent 不得自行改阶段标签 |
| `SAMPLE_INSUFFICIENT` | 活动上线 < 3天 OR 7天花费 < `03号§7.3` 样本不足门槛 OR 7天点击 < 10次 | 样本不足 |
| `CVR_WEAK` | 3天曝光 > 1500 且 CVR < 品类均值×30% | 曝光够但转化差，Listing 问题 |

## 2. 有效容忍上限计算（使用前必算）

在判断任何 ACOS 类问题前，先按以下公式从 `15-策略约束值规则.md §4` 得出当前有效容忍上限：

```
有效容忍上限 = 目标ACOS
             + 阶段容忍加值（15号§4.2）× 经营模式系数（15号§4.1A / 09号§3.2）
             + 广告目的=排名型 时额外加值
             + 淡旺季=旺季前期/旺季 时额外加值
             + 特殊场景=promotion 时额外加值
             − 女装毛利退货修正（24号 PRC-005 命中时 −5pp）
```

> 经营模式系数：`立即退出` / `获取利润` / `限时修复` → 0（阶段正加值归零）；
> `控制清货` → 0，但 `清货期` 阶段取 1；
> `稳定经营` / `积极推进` → 1。

> 示例：目标ACOS=25%，推进期阶段+10%，排名型目的+10%，旺季+10%
> 有效容忍上限 = 25% + 10% + 10% + 10% = **55%**
> 当前ACOS=38% < 55%，**不触发 ACOS 类问题**，不降Bid。

> 注意：本节淡旺季预算系数用于修正**预算范围**，即判断当前预算是否处于合理区间；不用于计算本次预算调整幅度。本次预算调整幅度按 `17-问题诊断与动作优先级.md §5.3` 的预算系数计算。

## 4. ACOS 容忍度矩阵

**17号文件 §2 直接引用本节计算"有效容忍上限"，用于问题类型判断。**

### 4.1 计算公式（v3.4.0 增加两项修正）

```
有效容忍上限 = 目标ACOS
             + 阶段加值（见 4.2）× 经营模式系数（见 4.1A）
             + 广告目的 = 排名型 时 +10%
             + 淡旺季 = 旺季前期/旺季 时 +10%
             + 特殊场景 = promotion 时 +15%
             − 女装毛利退货修正（24号 PRC-005 命中时 −5pp）
```

**这是全知识库唯一的 ACOS 判定基准。** 禁止任何文件使用「目标 ACOS × 倍数」
或「目标 ACOS + 固定 10%」形式判断 ACOS 高低（`17号§1.2`）。
v3.4.0 已清除 `05号`、`18号§4`、`19号§1`、`22号§2` 中的全部乘法倍数（C-07）。

### 4.1A 经营模式系数（v3.4.0 新增，G10）

阶段加值前乘一个由经营模式决定的 0/1 系数，用于消解「模式想收缩、阶段给正加值」的冲突。
完整通则见 `09号§3.2`。

| 经营模式 | 系数 | 效果 |
|---------|:-:|------|
| `立即退出` | 0 | 阶段正加值归零 |
| `获取利润` | 0 | 阶段正加值归零 |
| `限时修复` | 0 | 阶段正加值归零（其边界即目标 ACOS 内修复） |
| `控制清货` | 0，**但 `清货期` 阶段取 1** | 清货与 清货期 方向一致，唯一保留的一格 |
| `稳定经营` | 1 | 正常生效 |
| `积极推进` | 1 | 正常生效 |

> 只作用于**正**加值。`维持期` 的加值本身是 +0%，不受影响。

### 4.2 产品阶段加值

| 产品阶段 | 加值 |
|---------|------|
| 测试期 | +15% |
| **测试期 且已满 60 天（超期）** | **+0%**（v3.4.0 新增，C-17） |
| 推进期 | +10% |
| 收割利润期 | +5% |
| 维持期 | +0% |
| 清货期 | +20% |

> **测试期 超期归零的理由（C-17）**：`03号§2` 规定 测试期「最多测 60 天」，但 v3.3.0 对
> 超期没有任何规则。一个卡在 测试期 不动的产品会永久享受三项优待：最高的 ACOS 容忍加值
> （+15%，五阶段之最）、`17号§5.2` 的 ×0.5 幅度抑制、以及 `21号§2` 的免淘汰评估。
> 目标 25% 叠加旺季 +10% 后有效容忍上限会到 50%，而这个产品可能早就该进 推进期 或该被砍掉。
> 超期后：容忍加值归零 + 冻结增长型动作 + 输出 MANUAL_REVIEW 要求运营确认阶段。
> Agent **不得**自行改产品阶段标签（`02号§2` 权限为「仅建议」）。

### 4.3 计算示例

| 场景 | 计算过程 | 有效容忍上限 |
|------|---------|-----------|
| 推进期 + 排名型 + 旺季，目标25% | 25% + 10% + 10% + 10% = | **55%** |
| 收割利润期 + 转化型 + 淡季，目标25% | 25% + 5% + 0% + 0% = | **30%** |
| 维持期 + 盈利型，目标25% | 25% + 0% + 0% + 0% = | **25%** |
| 测试期 + 引流型，目标30% | 30% + 15% + 0% + 0% = | **45%** |
| 清货期，目标任意 | 目标 + 20% = | **目标+20%** |

> ACOS < 容忍上限：不触发降Bid，不触发降Budget
> ACOS ≥ 容忍上限：命中17号问题类型 HIGH_ACOS 类，触发对应动作

## 1. 表现定义（ACOS 分级）

| 表现等级 | 条件 | Agent 动作方向 |
|---------|------|--------------|
| 表现好 | ACOS ≤ 目标 ACOS | 可放量、提价、加广告位 |
| 表现一般 | 目标 ACOS < ACOS ≤ **有效容忍上限**（`15号§4`） | 维持或小幅优化。**不触发降 Bid、不触发降预算** |
| 表现差 | ACOS > **有效容忍上限**（`15号§4`） | 降价、降预算、进入淘汰判断 |
| 无转化 | 有花费无订单，且花费已达 `03号§7` 的无单花费门槛 | 先判相关性（`31号§4`），再决定否词或降价 |

> **v3.4.0 修正（C-07）**：本节原文用「目标 ACOS + 10%」作为表现差的判定线，与 `15号§4` 的
> 有效容忍上限口径不同。而 `15/17/18/19/22` 会被同时注入同一个 prompt，
> 模型会在「必须用加法容忍上限」和「目标+10%」之间摇摆。**已统一为有效容忍上限。**
>
> 有效容忍上限 = 目标 ACOS + 阶段加值 ×（经营模式系数）+ 目的加值 + 淡旺季加值 + 场景加值
> − 女装毛利退货修正。完整公式见 `15号§4.1`，经营模式系数见 `09号§3.2`。
>
> **ACOS 取值窗口**：Bid 调整看 3 天；预算调整看近 1 天和近 3 天趋势组合。

## 4. 预算变化金额定义

| 操作名称 | 变化金额 | 触发条件 |
|---------|---------|------|
| 大涨 | +20%（min $2） | 预算花费率 > 90% + 近1天表现好（ACOS ≤ 目标） |
| 小涨 | +10%（min $1） | 预算花费率 70%–90% + 近1天表现好（ACOS ≤ 目标） |
| 维持 | $0 | 预算花费率 50%–70%；或活动无花费 |
| 降（统一） | MAX($1, 当前预算 × 10%) | **仅在**表现差（ACOS > 有效容忍上限）触发；或走完 §4.1 三步后仍无法消化预算 |

> **翻倍规则**：活动近期花费 > $50 时，涨幅 × 1.5。

### 4.1 预算利用率 < 50% 的唯一处置路径（v3.4.0 重写，C-11）

**「预算花不完」不是降预算的理由。** 必须按以下三步，顺序不可跳：

```text
Step 1 — 瓶颈判断（必执行，23号§4.3 / GROUP-BUDGET-007）
   组合利用率 = 100% 且 活动平均利用率 < 80%  → 瓶颈在【组合层】
        → 建议提升组合预算，本轮不调单个活动的预算或 Bid，结束
   活动利用率 = 100% 且 组合利用率 < 80%      → 瓶颈在【活动层】→ 进入 Step 2
   组合利用率 = 100% 且 活动平均利用率 ≈ 100% → 瓶颈在【父ASIN层】
        → 建议提升父 ASIN 总预算，结束

Step 2 — 四档填补（28号§5，逐档判断，消化不完才进下一档）
   第1档：回流被压制的有效词（恢复此前被降的 bid/预算）
   第2档：提现有有效词的 bid/预算（幅度受 25号§2 封顶）
   第3档：从精准测试组提词升组（达 23号§3.5 标准的词）
   第4档：扩全新词（28号§1–§4 选词；受 03号§7 每日新词上限封顶）

Step 3 — 仍无法消化 → 才降预算
   四档全部走完仍有剩余缺口，且非组合层/父ASIN层瓶颈，方可降预算
```

> **v3.3.0 的错误（C-11）**：本节原文写「预算花费率 < 50%（花不完必降）」。
> 这条与四处冲突：`19号§6`（近1天好则维持）、`22号§3.1` / `18号§7`（先查 Bid 和词覆盖）、
> `28号§5`（四档填补，全程不降预算）、`GROUP-BUDGET-007`（瓶颈判断优先）。
>
> 而且它本身就是一个已知陷阱的规则化 —— `budget_groups.health_ratio_bottleneck` 写得很清楚：
> 活动总和 $100、组合预算 $50 时，亚马逊按竞价先到先得，组合花到 $50 后当日关停全部活动；
> 某活动花了 $10 就被停了，Agent 看到 33% 利用率会误判「花不出去」。
> 此时真实原因是**组合预算不足**，正确动作是提升组合预算——而「必降」的方向恰好相反。
>
> 第 1 档不能省：「回流被压制的有效词」是最高价值动作（这些词已验证有效，只是被之前的优化压低了），
> 跳过它直接提 Bid 或扩词，等于为未验证的词付钱。

## 0. 核心定义

**淘汰 ≠ 暂停 ≠ 关停。**

淘汰广告活动的本质是将低效活动移入低价捡漏组（low_bid_retention_group），用极低预算和极低 Bid 继续捡漏观察，避免直接断流。

- 活动在亚马逊后台保持**启用**状态
- 对精准活动，Agent **不使用 `pause_campaign` 替代低价捡漏**，统一使用 `eliminate_to_low_bid_pool`
- 对广泛、词组、自动、商品定投活动，退出动作是 **`stop_campaign`**（不是 `pause_campaign`，
  也不是 `eliminate_to_low_bid_pool`）。两个动作的语义与可逆性区别见 `30号§2`
- 淘汰后执行值固定（见 §3），不可由 Agent 自行修改

## 3. 淘汰前必须走的诊断步骤（不能跳过直接淘汰）

**精准广告的诊断路径：**
```
广告位花费高无单？
  → 是 → 先降该广告位加价，观察3天
           仍无改善 → 降基础 Bid
           仍无改善 → 再评估是否淘汰整体活动
  → 否 → 直接评估淘汰条件
```

**广泛/词组/自动广告的停止投放前诊断路径（不属于低价捡漏）：**
```
高点击无单？
  → 是 → 先执行否词（add_negative）
           否词后仍无改善 → 降 Bid / 降预算
           降 Bid/预算后仍无改善 → 评估停止投放
  → 否 → 继续按目标ACOS和经营模式判断
```

> **原则**：广泛/词组广告必须先保护高度相关词，再走搜索词治理流程；
> 无改善时可以关闭，但不能进入低价捡漏组。

## 1. 硬护栏（Hard Blocks）

### 1.1 不直接执行

Agent 不得直接调用 Amazon API 执行广告更改。所有可执行输出使用 PROPOSED 状态，需要 ERP 审核。

### 1.2 缺少必需数据

任何动作都至少需要以下数据，缺失则 BLOCKED： - ASIN标签 - 知识库版本 - 父ASIN库存 - 广告指标

### 1.3 库存数据缺失

库存数据不可降级用于增长型动作。阻断以下操作：提价、加预算、加广告位、扩词

### 1.4 单次最大出价变化

- 超出阈值上限 → 需 HIGH_RISK_REVIEW

- 超出绝对上限 → BLOCKED

### 1.5 单次最大预算变化

- 超出阈值上限 → 需 HIGH_RISK_REVIEW

- 超出绝对上限 → BLOCKED

### 1.6 停投类动作处理（v3.4.0 重写，C-03）

Agent **可以**输出退出类动作，但必须使用正确的动作码，且必须人工确认。

| 活动类型 | 退出动作 | 去向 | 审核等级 |
| --- | --- | --- | --- |
| 单关键词 EXACT | `eliminate_to_low_bid_pool` | 低价捡漏组：预算 $1、Bid `min(current_bid, 0.20)` | HIGH_RISK_REVIEW |
| 多关键词 EXACT | `eliminate_to_low_bid_pool` | 低价捡漏组（确定性迁入） | HIGH_RISK_REVIEW |
| BROAD / PHRASE / AUTO | `stop_campaign` | 关闭。**不得**进低价捡漏组（`ONT-016`） | HIGH_RISK_REVIEW |
| PRODUCT_TARGETING | `stop_campaign` | 关闭。**不得**进低价捡漏组 | HIGH_RISK_REVIEW |

**硬规则**：

- `stop_campaign` 与 `pause_campaign` 是两个不同的动作，语义与可逆性不同，见 `30号§2`。
- **`pause_campaign` 仅在业务语义确为「暂时停一下且有明确恢复条件」时使用**，极少用。
  没有明确恢复条件的停投一律用 `stop_campaign`。
- 两者都必须人工确认，审核等级 `HIGH_RISK_REVIEW` 且**不可降级**。
- 退出动作必须走完对应的诊断路径才能提出：精准类按 `21号§3`，广泛类按 `21号§3` 的广泛分支
  （高点击无单 → 先否词 → 降 Bid/预算 → 仍无改善才评估关闭）。
- 退出动作触发预算回算义务（`GROUP-BUDGET-001/002`），未回算则 `GROUP-002` 阻断输出。

> **v3.3.0 的失效点**：本节原文写「Agent 不输出 pause」，但 `ActionType` 里没有 `close`，
> `campaign.py::_build_immediate_exit_adjustments()` 实际发出 `ActionType.PAUSE` +
> `proposed_value = {"state": "paused"}`——而同一函数的 docstring 和 evidence 文本写的是「关闭」。
> 代码字段、代码注释、护栏条文三方冲突。
> 更麻烦的是：在 Amazon 后台 `paused` 与 `archived` 的可逆程度完全不同，
> 而 `21号§7` 还有一整套「淘汰后 ≥14 天复评、原位恢复优先」的重启机制依赖活动可恢复。
> 若把退出统一为 `archived` 就断了重启路径；若统一为 `paused`，则 `立即退出`
> （彻底退出）与「本轮暂时不投」无法区分。**必须两个动作都有**，v3.4.0 因此新注册
> `stop_campaign`（`30号§1` #13）。

### 1.7 禁止无限预算

Agent 不得输出无限预算，包括紧急清仓场景。替代方案：clearance_aggressive_mode_with_senior_approval

### 1.8 对象级非法动作阻断

- `SearchTerm` 禁止直接执行 Bid / Budget / Placement 动作（`ONT-001`）
- `broad_keyword / phrase_keyword / auto_discovery` 禁止输出 Placement 调整（`ONT-002`）
- `exact_keyword` 禁止输出否词动作（`ONT-015`）；**阻断时必须给出 `recommended_next_step`**
  （降 Bid 观察 / 暂停该 Target / 迁入低价捡漏组，见 `22号§2.4`），不得只 block 不给替代路径
- `product_targeting` **允许** Placement 调整（PP 优先，`ONT-010`）。v3.4.3 起它归属 `auto_broad_group` 的 `product_targeting` 子桶——
  **权限判据必须同时看组合与子桶**（`placement_adjustment_allowed()`）：只看组合会把它误判为「广泛自动组 → 禁止广告位」
- 低价捡漏组只允许 `exact_keyword`（`ONT-016`）
- 未在 `30号§1` 注册的 `action_code` → BLOCKED（`reason_code = ACTION_NOT_REGISTERED`）
- `action_code` 与 `physical_action_code` / `scope` / `campaign_type` 不匹配 → BLOCKED（`30号§7`）
- 若动作对象与 Ontology 允许对象不一致 → BLOCKED

### 1.9 组合预算超限阻断（v3.4.0 分两级，G2）

Campaign 预算调整后必须按三层逐级回算（`GROUP-BUDGET-001/002`），超限则阻断：

| 超限场景 | 判断标准 | 处理 |
| --- | --- | --- |
| 组合预算超限 | Campaign 预算调整后，所属 `AdBudgetGroup` 的 `proposed_group_budget` 超出组合预算上限 | BLOCKED |
| 父 ASIN 总预算超限 | 所有组合预算汇总后 `proposed_total_group_budget > parent_target_daily_budget`，且本轮 `net_required_increase > parent_allowed_net_increase` | BLOCKED |
| **超配跨越 2 倍**（本轮动作造成） | 调整前 活动预算总和 ≤ 组合预算 × 2.0，调整后 > 2.0 | **BLOCKED**（`GROUP-010`）。Agent 自己造成的必须拦 |
| **存量已超 2 倍** | 调整前 活动预算总和已 > 组合预算 × 2.0 | **MANUAL_REVIEW**，且本轮**只允许输出降预算动作**（`GROUP-010`） |

> **为什么分两级（G2）**：v3.3.0 里交接文档§8/§12 写「超配期间不得超过组合预算的 2 倍」
> （硬阻断），而 `23号§4.3` 与 `budget_groups.health_tiers` 写「> 2.0 → MANUAL_REVIEW」
> （人工确认），直接矛盾。
> 统一硬阻断会让历史已超配的组合陷入死锁（连正确的调整都做不了）；
> 统一 MANUAL_REVIEW 会让预算失控的唯一防线变成人工，而这类提案很多、容易被批量点过。
> 分两级同时避免两个问题：Agent 造成的越界必拦，历史遗留的交人工但限制动作方向。

超配的目的是避免预算花不完（Campaign 日预算是上限，多数活动实际花费低于日预算），
健康比例分层见 `23号§4.3`。

### 1.10 账户级断路器（v3.4.1 新增）

在「本轮提案生成之后、输出之前」评估聚合统计（`app/core/circuit_breaker.py`），任一触发
→ 本轮降级为 no-op 或全量 MANUAL_REVIEW + 报警：

| 断路器 | 触发 | 级别 |
| --- | --- | --- |
| CB-01 数据事故 | 昨日有花费（≥ 03号§13 阈值）但全账户 0 订单 → 疑似归因/报表中断 | NO_OP |
| CB-02 净预算变化 | 本轮净预算变化超父预算总和的上限比例 | NO_OP |
| CB-03 提案量突增 | 本轮提案数超近 7 轮均值的倍数上限 | REVIEW_ALL |
| CB-04 未成熟批量收缩 | 降级类动作占比超限 **且** 窗口平均成熟度低于下限 | NO_OP |
| CB-05 批量退出 | 单轮淘汰/关闭类动作超每店铺上限（首次接入例外走 03号§7.2） | NO_OP |

NO_OP = 本轮全部动作降级为观察 + 报警 + 人工确认后重跑。断路器是机械防线，
不做业务推理；它的触发含义是「这轮的形态异常到不该无人放行」。阈值见 `03号§13`。

### 1.11 对账冻结（v3.4.1 新增，两方版）

日级两方对账（ERP ↔ Agent 期望值，`app/core/reconciliation.py`）检测到**外部修改**
（运营手改 / 亚马逊自动规则）时，该对象转入「人工接管中」：Agent 跳过它并输出 flag，
直到运营显式解冻（操作人入审计日志）。每次写回前执行 CAS 校验（当前值 == 上次读值），
失败即放弃写入并转对账队列（复合动作整批放弃）。
**机器不得覆盖人的操作** —— 违反一次，运营就会永远绕过系统。

> 两方版先行：ERP 通常日级同步 console，两方对账已能发现绝大多数外部修改。
> console 同步契约（交接文档§11.8）就绪后把 console_value 填进 snapshot 即自动升级为
> 三方对账，代码不用改。

### 1.12 顺序纪律：先机械护栏，后取消人工点击

既定路线是「人工审核作为前期风控，随数据积累逐步取消人工点击」。**任何取消人工点击的
决定，前置条件是 §1.10 断路器、§1.11 对账、ONT-022 成熟度门三者已上线并稳定运行。**
顺序反了，放权后的第一个数据事故日就是第一次生产事故——而且发生在没人点确认的那一天。
逐 cell 放权的毕业机制属 v3.5.0 学习闭环，本版不启用；本版内取消任何动作类别的人工点击
须人工决策并记录。

>
> 改比例的动机是真实的：`15号§2.1` 给 P3 的活动预算范围是 $5–20/天，
> 父 ASIN 日预算 $10–20 时，「连续 3 天每日 >$5」意味着单个活动要连续三天吃掉
> 25–50% 的父级预算才有资格升组 —— P3 长尾精准词在结构上很难建立主力组，
> 会永久停在 `exact_testing_group`，拿不到 `GROUP-BUDGET-004` 的断供保护，
> 且因「精准测试组优先压缩」在预算紧张时第一个被砍。
>
> 但比例口径的 `8% / $1 / $8` 三个数**没有经营验证依据**，属于用一组未验证的数
> 替换一个已验证的数。运营选择回到固定 `$5`：宁可保留一个已知边界，
> 也不引入三个来源不明的参数。
>
> **长尾问题没有消失，只是没有用未验证的参数去掩盖。** 后续解法有数据后再定，
> 候选方向：按产品定位分档固定值（P0/P1 $5、P2 $3、P3 $1.5）、
> 或 `max(父预算 × 比例, 绝对下限)` 并封顶 $5。
> 代码保留比例口径能力，但只能通过
> `campaign_exact_main_threshold_mode=ratio` **显式启用**。
> `fixed` 模式下把门槛设为 0 或负数会阻断升组并记录错误，不会自动回落比例。
>
> **实现防线**：门槛值 `0` 或负数**不得**被当作「已显式指定门槛」。
> v3.4.0/v3.4.1 的判据是 `is not None`，而主链无条件传入迁移兼容值 `0.0`，
> 导致实际门槛退化为 `$0`（每日花费 $0.01 连续 3 天即升组）。
> 该防线在领域层（`evaluate_exact_main_validation`），
> 回归用例 `test_zero_threshold_must_never_be_treated_as_explicit`。

> （数仓窗口 `end = 当地今天-1`，是最后一个完整日）。

> 广泛/自动/词组只拉一次成熟聚合窗，以控制 MCP 调用量；
> 7 天窗只有聚合值 → **均匀分布近似**（在 `maturity_basis` 字段标注）。
> 精准逐日窗缺任意一天即视为窗口不完整，由 Agent 自动延后，不得把剩余的更老日期
> 误当作“更成熟”而放行。
> 要让 7 天窗也精确，需把日拉取从 3 天扩到 7 天（MCP 调用量 ×7/3），
> 或等 §11.9 重述快照。近似方向是保守的：均匀假设不会像「整窗按最老龄期校正」
> 那样低估未成熟度。

**0 销售 + 未成熟窗口 → `acos_corrected = None`（证据不足），不是 ∞、不是「无转化」。**
调用方必须把 None 当「本轮不判定」处理——这一条直接消灭「数据事故日批量降价」的最常见来源。

### 12.2 不可逆动作最小数据龄（ONT-022 成熟度门）

| 动作 | 最小数据龄 | 状态 |
| --- | --- | --- |
| `eliminate_to_low_bid_pool` / `stop_campaign` / `add_negative_search_term` / `demote_to_exact_testing` / `promote_to_exact_core` | 默认 3 天，按统一配置读取 | ✅ 可配置 |
| 数据龄未知或不足 | Agent 自动延后，本轮不生成可执行动作；下轮重取成熟窗再判断，不增加过程人工节点 | ✅ 已确认 |
| **立即退出豁免** | 人工已在前置标签选择 `立即退出` 时，精准迁捡漏组、非精准关闭只豁免成熟度门；其他 Ontology 规则和最终人工执行确认仍保留 | ✅ 已确认 |
| **相关性驱动否词豁免** | R3/R4 否词（31号§4 档4）是语义判定不依赖表现数据，**不受本门约束**；效率驱动否词（05号§3 路径二）仍受约束 | ✅ 已确认 |
| 可逆动作（Bid/预算小幅调整） | 无最小龄，但必须用校正后指标 | ✅ 已确认 |

**成熟窗定义（消除窗口歧义）**：不可逆判定所用的「近 N 天」窗口，一律取**最新一天龄期
≥3 天**的窗口，即 T-3 起往前数。具体：升组的「连续 3 个完整站点自然日」= T-3/T-4/T-5
（不是 T-1..T-3）；降组的「连续 2 个 3 日评估周期」与严重回落的「近 7 天」同理后移。
`evaluate_exact_main_validation()` 本身只校验连续性，窗口日期由调用方按本条和
`thresholds.toml` 传入。
代价是判定慢 2 天——这是刻意的：对不可逆动作，宁可慢两天，不可用半熟数据错杀。

## 0. 为什么要两套码

**业务码携带意图，物理码只描述操作。** 这个区分不能丢：

`bid_up_for_ranking`（提价冲排名）和 `bid_down_for_acos`（降价控 ACOS）在物理上是同一个动作（改一个 Bid 数值），但它们的**风险等级、必需证据、审核等级、阻断条件完全不同**：

| | `bid_up_for_ranking` | `bid_down_for_acos` |
| --- | --- | --- |
| 是否增长型 | 是（受库存/退货/评分阻断） | 否 |
| 必需证据 | 自然排名 + 库存 + Listing 承接 | 仅投放目标报告 |
| 默认审核等级 | MANUAL_REVIEW | AUTO_APPROVED |
| 阻断条件 | 库存不足、高退货、低评分、缺排名数据 | 该词承担 Ranking 任务且未超容忍上限 |

如果塌缩成一个 `adjust_bid`，`05-动作规则.md` 的审核等级分级和 `ontology/actions.yaml` 的必需证据索引就全部失去挂载点。所以：**业务码用于规则判断与审核分级，物理码用于执行与 ERP 写入。**

## 2. `stop_campaign` 与 `pause_campaign` 的区别（C-03）

v3.3.0 只有 `pause`，导致 `21号`/`18号`/`budget_groups` 里写的「关闭」实际全部落成 `pause`，
而 `10号§1.6` 又明文禁止输出 `pause` —— 代码、注释、护栏三方冲突。v3.4.0 分开定义。

| | `stop_campaign` | `pause_campaign` |
| --- | --- | --- |
| 业务语义 | **退出投放**：本方向不再经营 | **临时停投**：等待某个条件解除后恢复 |
| 典型场景 | 广泛/词组/自动活动整体长期低效；`立即退出` 模式下的非精准活动 | 极少使用。仅当业务语义确为「暂时停一下」且已有明确恢复条件时 |
| Amazon 后台状态 | `archived`（或长期 `paused` + 标记，取决于 ERP 接口能力） | `paused` |
| 可逆性 | 归档后不可恢复历史数据；恢复需新建活动 | 可随时恢复，保留历史数据 |
| 是否进低价捡漏组 | 否。低价捡漏组按 `ONT-014` 只收 EXACT | 否 |
| 是否触发预算回算 | 是。释放金额 = `current_daily_budget`，计入 `other_campaign_budget_decrease` | 是。同左 |
| 审核等级 | HIGH_RISK_REVIEW（不可降级） | HIGH_RISK_REVIEW（不可降级） |
| 是否需要人工确认 | 必须 | 必须 |

**四类退出路径的正确对应**（这是 v3.3.0 最容易搞错的地方）：

| 活动类型 | 退出动作 | 去向 | 依据 |
| --- | --- | --- | --- |
| 单关键词 EXACT | `eliminate_to_low_bid_pool` | 低价捡漏组，预算 $1、Bid `min(current_bid, 0.20)` | 21号§0、`ONT-014` |
| 多关键词 EXACT | `eliminate_to_low_bid_pool` | 低价捡漏组（确定性迁入，不看历史表现） | `ROUTE-002` |

| PRODUCT_TARGETING | `stop_campaign` | 停止投放。**不得**进低价捡漏组（无关键词，$0.20 在 ASIN 定投上基本无曝光） | 23号§8.5（v3.4.0 新增） |

## 3. 复合动作的展开规则

`eliminate_to_low_bid_pool` / `demote_to_exact_testing` 是业务上的一个动作，但在物理层是多个动作。
`ActionBundle` 里必须展开为多条 `AdAction`，共享同一个 `bundle_id`，并保证**同批成功或同批回滚**。

### 3.1 `eliminate_to_low_bid_pool` 展开

```text
bundle_id: eliminate:{campaign_id}
├── AdAction 1: move_portfolio
│     scope=CAMPAIGN  target=campaign_id
│     current={portfolio: exact_core_group | exact_testing_group}
│     proposed={portfolio: low_bid_retention_group}
├── AdAction 2: adjust_budget
│     scope=CAMPAIGN  current={budget: 8.0}  proposed={budget: 1.0}
└── AdAction 3: adjust_bid
      scope=TARGET    current={bid: 0.15}   proposed={bid: 0.15}
      注：proposed_bid = min(current_bid, 0.20)。current_bid 已低于 0.20 时保持不变，
          不得抬高（C-10；违反则 GROUP-004A 阻断）
```

同时必须输出 `21号§5A` 要求的四个预算回算字段：
`released_at_campaign_level` = `current_daily_budget - 1`、`group_type_before_elimination`、
`low_bid_retention_group_delta` = `0`、`released_budget_flows_to`。

### 3.2 `demote_to_exact_testing` 展开（v3.4.0 新增）

```text
bundle_id: demote:{campaign_id}
├── AdAction 1: move_portfolio
│     current={portfolio: exact_core_group}  proposed={portfolio: exact_testing_group}
├── AdAction 2: adjust_budget（降预算，幅度按 19号§4 × 15号§2 系数）
└── AdAction 3: adjust_bid（降 Bid，幅度按 19号§3 × 15号§1.2 系数）
```

必须携带 `demoted_at`（降级日期），`32号§2.4` 的严重回落判定依赖它。

## 4. 动作生命周期（C-04）

v3.3.0 的 `01号` 与 `12号§三` 都写「仅允许 PROPOSED 或 BLOCKED」，与代码的 11 态生命周期不一致。
v3.4.0 统一为 11 态，并明确**谁能写哪一态**。

| # | 状态 | 含义 | 写入方 |
| --- | --- | --- | --- |
| 1 | `proposed` | Agent 已生成提案 | **Agent** |
| 2 | `blocked` | Agent 自检或护栏不通过，不生成可执行动作 | **Agent** / `OntologyValidator` |
| 3 | `validated` | 通过 Ontology 校验与安全护栏 | `OntologyValidator` |
| 4 | `human_approved` | 运营在 ERP 确认执行 | ERP（人工） |
| 5 | `erp_accepted` | ERP 护栏校验通过并受理 | ERP |
| 6 | `executing` | ERP 已提交异步任务，未收到终态 | ERP |
| 7 | `executed` | 收到终态且执行成功 | ERP |
| 8 | `rejected` | ERP 护栏明确拒绝 | ERP |
| 9 | `failed` | 系统性失败 | ERP |
| 10 | `observing` | 执行后进入观察窗（1/3/7/14 天） | 系统 |
| 11 | `evaluated` | 观察窗结束，已产出复盘结论 | 系统 |

```text
proposed → validated → human_approved → erp_accepted → executing
                                                          ├→ executed → observing → evaluated
                                                          ├→ rejected（不重试）
                                                          └→ failed（仅契约标记可重试者允许重试）
blocked（终态，不进入流转）
```

**硬规则**：

- Agent 只能产出 `proposed` 与 `blocked` 两态，不得自行写入其他状态。
- ERP 异步任务提交后只能标 `executing`；**收到终态结果前不得写成 `executed`**。
- `rejected` 不自动重试。只有契约标记为可重试的系统性 `failed` 才允许重试。
- `ActionBundle` 允许部分成功：同一 bundle 内不同 `AdAction` 可处于不同状态，但 §3 的复合动作必须同批。

## 0. 核心结论

广泛、自动、词组广告的职责是**挖词和提供流量来源**，不承担精准主推。

四条原则：

1. 有效 Search Term 先进入**精准测试组**，不直接进入精准主力组（`23号§3.4` → `32号§3`）。
2. **明显不相关**才否词；**相关但暂时无转化**走低 Bid 或受控预算观察，不否词。
3. 产品定位决定探索强度与预算档位；经营模式决定当前允许哪些动作。
4. 目标 ACOS、父 ASIN 日预算和安全护栏决定调整边界的硬上限。

## 1. 三类广告的职责边界

| 广告类型 | 承担 | 不承担 |
| --- | --- | --- |
| 广泛广告 `broad_keyword` | 打开词池、探索搜索词、挖掘词根、获取长尾流量 | 精准主推；广告位调整 |
| 词组广告 `phrase_keyword` | 比广泛更收窄地探索相关搜索词，为精准测试提供词源 | 不单独建立主推逻辑；按广泛策略处理 |
| 自动广告 `auto_discovery` | 发现 Close Match / Loose Match / Substitutes / Complements 及相关 Search Term | 不因 Auto 整体 ACOS 高就批量提高全部 Auto Bid；缺 Target 契约时不调 Target Bid |

依据：`18号§1`、`07号§0`、`ontology/budget_groups.yaml` group_types、`ROUTE-001`。

## 2. 产品定位下的探索强度（四档，按 02号§1）

### 2.1 P0 战略级 / P1 重点产品

精准侧负责抢核心词、推自然排名、承接已验证词；广泛/自动/词组负责挖新词、扩长尾、提供精准测试词源。

- 标题词、后台 Search Term 词、核心卖点词、自然排名相关词，**不因短期无订单直接否词**（`ONT-RUNTIME-004`）。
- 有效 Search Term 先进精准测试组，完成 `23号§3.5` 验证后才进精准主力组。
- 关键词转入精准后，原广泛/自动/词组活动**默认不自动否词**（见 §12）。
- 探索预算档位按 `15号§2.1` 的 P0 / P1 列。
- **P0 专属**：核心词 Bid 每次降幅 ≤5% 且不得连续两次下调同一关键词（`15号§1.3`）；P1 不适用此项。

### 2.2 P2 常规产品

精准侧负责稳定转化和盈利；广泛/自动/词组负责补充流量、挖少量新词、发现可升级 Search Term。

- 探索预算低于 P0/P1（按 `15号§2.1` 的 P2 列）。
- 对高花费无转化词更敏感：进入 §5 的强优化档所需的花费门槛按 `03号§7` 取值，不额外放宽。
- 明显不相关词及时否词；相关但无转化词先判断数据是否充分（§4）。
- 不长期保护大量未验证词。

### 2.3 P3 长尾产品

**P3 不要求建立大量精准主推词。** 广泛/自动/词组可以承担主要流量来源，精准侧只承接少量已验证或高价值词。

- 优先低 Bid 或固定 Bid；预算采用固定或受控预算，避免频繁大幅波动。
- 高相关但暂时无转化的词继续观察；样本不足时观察窗延长至 14 天（`18号§3`）。
- 明显不相关词否词；稳定转化后升级为精准测试。
- **关联说明**：精准主力组当前仍执行固定 $5 门槛（`23号§3.5`）。
  P3 长尾升组困难是已知待验证问题，不能以未经确认的比例参数自动放宽。

## 3. 经营模式下的动作权限

| 经营模式 | 广泛/自动/词组 允许动作 | 限制 |
| --- | --- | --- |
| `积极推进` 积极推进 | 扩词、增加探索预算、适度提高 Bid、有效词送入精准测试 | 不得突破父 ASIN 预算；不做广告位调整 |
| `稳定经营` 稳定经营 | 保持活动、低幅度扩词、小幅 Bid/预算调整 | 不大规模新增和扩量 |
| `限时修复` 有限修复 | 否词、降 Bid、降预算、Listing 诊断 | 停止激进扩词和大规模新建；阶段 ACOS 正加值归零（`09号§3`） |
| `控制清货` 控制清货 | 低 Bid 保留有订单或高价值流量，逐步收缩 | 原则上停止大规模扩词（`28号§3.2` 清仓行） |
| `获取利润` 获取利润 | 减少探索，保留高效 Search Term，预算优先给精准高效词 | 不积极扩展新词；阶段 ACOS 正加值归零（`09号§3`） |
| `立即退出` 立即退出 | 无。确定性执行 `stop_campaign` | 不进入 LLM 判断；禁止新建；见 `18号§0` |

## 4. 相关性优先于效率：四档分支（本文核心）

**判定顺序：先判相关性，再判数据是否达到动作阈值。** 顺序不可颠倒。

相关性档位沿用 `28号§2` 的 `R1 精确相关 / R2 扩展相关 / R3 试探相关 / R4 风险相关`。

| 档 | 场景 | 相关性 | 数据条件 | 动作 | 是否否词 |
| :-: | --- | --- | --- | --- | :-: |
| 1 | 数据不足 | 任意 | 活动上线 <3 天；或 7 天点击 <10 **且** 7 天花费 < 无单花费门槛（`03号§7`） | 不做大幅调整，低 Bid 或原 Bid 观察；P3/长尾词观察窗延长至 14 天 | 否 |
| 2 | 相关但暂时无转化 | R1 / R2 | 7 天点击 ≥10 **或** 7 天花费 ≥ 无单花费门槛，且无订单 | Bid 下降一档（`19号§3` 小降，经 `15号§1.2` 系数修正）；预算保持或小幅下降；观察 7 天 | **否** |
| 3 | 相关且已达强优化档 | R1 / R2 | 7 天点击 ≥20 **或** 7 天花费 ≥ 强优化花费门槛（`03号§7`），仍无订单 | Bid 下降两档（`19号§3` 大降）；预算下降一档；进入人工复评 | 通常不否 R1 词 |
| 4 | 明显不相关 | R3 / R4 或语义冲突 | 无数据门槛 —— 相关性判定即可触发 | 添加精确否定词，记录相关性判定依据与证据 | **是** |

**补充规则：**

- 档 3 命中 R1 词时，若该词属 `29号` 的核心词（`is_core_keyword = true`）或 `ONT-RUNTIME-004` 的四类保护词，**不得否词**，只允许降 Bid / 降预算 / 转 Listing 诊断。
- 「高花费低相关」是档 3 与档 4 的叠加：7 天花费 ≥ 强优化门槛 **且** 相关性为 R3/R4 → 先否词，再降 Bid/预算，必要时 `stop_campaign`。
- 相关性证据不足时，**不得把「无订单」直接等同于「不相关」**（`19号§8` 末句，本节将其规则化）。
- 档 2 与档 3 的点击阈值 `≥10` / `≥20` 与 `22号§3.3` 一致（预警 / 强优化两档制）。`19号§8` 已同步修订为两档制。

## 5. Bid 调整规则

基础幅度按 `19号§3`，系数修正按 `15号§1.2`，硬上下限按 `03号§8`。本节只定义**触发条件与档位映射**。

| 表现 | 触发信号 | Bid 档位 | 复评窗 |
| --- | --- | --- | --- |
| 曝光不足 | 高度相关（R1）、预算未花满、点击不足 | 小涨；单次幅度上限 15%（`22号§3.2`） | 1–3 天 |
| 轻度偏高 | 有订单，ACOS > 目标 但 ≤ 有效容忍上限（`15号§4`） | **不降**（未超容忍上限不触发降 Bid） | 7 天 |
| 超出容忍上限 | ACOS > 有效容忍上限，有订单 | 小降 | 7 天 |
| 相关但无转化 | §4 档 2 | 小降，同时检查是否应先否词（`22号§3.2`） | 7 天 |
| 已达强优化档 | §4 档 3 | 大降；必要时降预算或 `stop_campaign` | 7 天 |
| 核心保护词 | `is_core_keyword = true` 且仍有自然位价值 | 小降或维持低 Bid，**不得归零**；P0 额外受 `15号§1.3` 的 ≤5% 约束 | 7–14 天 |

## 6. 预算调整规则

| 场景 | 数据条件 | 动作 |
| --- | --- | --- |
| 预算花不满 | 预算利用率连续 3 天 <50% | **先按 `23号§4.3` 做瓶颈判断**；确认瓶颈在活动层后，走 `28号§5` 四档填补（① 回流被压制的有效词 → ② 提现有有效词 Bid/预算 → ③ 精准测试组提词升组 → ④ 才扩新词）；四档都无法消化才降预算 |
| 表现好且预算不足 | 7 天 ACOS ≤ 目标、订单有效、预算利用率 ≥70%、库存天数 ≥30 天 | `积极推进` 可增加一档（`19号§4` 小涨/大涨，经 `15号§2` 系数修正）；P2 小幅；P3 优先固定或受控预算 |
| 花满且 ACOS 超容忍上限 | 预算利用率高、ACOS > 有效容忍上限、Search Term 质量差 | 先否不相关词（§4 档 4），再降 Bid 和预算；**不做广告位调整** |

| 主力预算保护 | 精准主力组 7 天花费 ≥$5 且有出单 | 广泛自动组不得扩张挤占主力组；预算紧时精准测试组优先压缩、广泛自动组次之（`GROUP-BUDGET-004`） |

## 10. Search Term 进入精准测试组

准入条件以 `23号§3.4` 为唯一权威，本节只做引用与广泛侧补充说明。

| 通道 | 条件 | 审核等级 |
| --- | --- | --- |
| 通道一：订单通道 | 近 7 天有效订单 ≥3 单 **且** 近 7 天 ACOS ≤ 目标 ACOS **且** 无对应精准活动 | MANUAL_REVIEW |
| 通道二：词根通道 | 同词根合计 7 天订单 ≥3 单 **或** 合计 ACOS ≤ 目标 ACOS；且无精准活动承接该词根 | MANUAL_REVIEW |
| 通道三：CVR 通道 | CVR > 品类均值 × 0.8 **且** 7 天花费 ≥ 无单花费门槛（`03号§7`）**且** 无对应精准活动 | **HIGH_RISK_REVIEW**（强制人工） |

**共同约束：**

- 候选词必须存在于本轮输入数据，**禁止 LLM 生成输入外的词**（`28号§1` 词保真，违反 → BLOCKED）。
- 新建单关键词 Exact 活动，初始预算按 `16号§2`，归属 `exact_testing_group`。
- **不得从广泛/自动/词组直接进入精准主力组**，必须先完成 `23号§3.5` 的验证。
- 相关性必须达 R1（`28号§2`）。

## 11. 保护型精准测试（v3.4.0 新形态）

战略核心词可以被保护，但保护**不是**「只要相关就进」，也**不是**直接进精准主力组。

### 11.1 字段定义

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `protected_testing` | boolean | 是否处于保护型测试状态 |
| `protection_expires_at` | date | 保护到期日 = 进入日 + 保护期（§11.2） |
| `protection_basis` | array | 进入依据（产品定位 / 相关性档 / 数据证据 / 运营指定） |

### 11.2 进入条件（四条同时满足）

| 条件 | 要求 |
| --- | --- |
| 产品定位 | P0 或 P1；或运营显式确认该词为战略词 |
| 相关性 | 达 `R1 精确相关`（`28号§2`）；或 `29号` 判定 `semantic_core = true` |
| 最低数据 | 近 7 天点击 ≥5 **或** 花费 ≥ `03号§7` 的保护型测试最低数据门槛 |
| 验证结果 | 尚未达到 `23号§3.5` 的精准主力组准入条件 |

### 11.3 保护期内的行为

- 观察 7–14 天（具体值见 `03号§7`，标 `needs_review`）。
- **不自动否词**；不进入 `21号` 淘汰评估；不进入 `32号§2` 的降级判定。
- 允许低 Bid 或受控预算；允许降 Bid / 降预算。
- 必须同步检查 Listing、价格、库存、评价与转化承接（`14号§15` 页面承接排查）。

### 11.4 保护边界（防止无限花费）

- 到达 §4 档 3（强优化档）后，**保护不豁免降 Bid / 降预算**，只豁免否词与淘汰。
- `protection_expires_at` 到期后强制回归常规评估，`protected_testing` 自动置 `false`，
  并输出一条 MANUAL_REVIEW 说明保护期结论。
- 保护期不可由 Agent 自行续期；续期需运营显式操作。

## 12. Search Term 转入精准后，原活动如何处理

按运营共识：Search Term 转入精准测试或精准主力后，原广泛/自动/词组活动**默认不自动否词**。

| 阶段 | 原活动处理 | 原因 |
| --- | --- | --- |
| 该词进入精准测试组 | 继续保留，不自动否词 | 观察精准测试与原探索活动的流量与转化差异 |
| 精准测试稳定 / 已升主力组 | 默认仍不自动否词，除非运营另行确认 | 保留探索功能，避免过早切断长尾来源（切断会直接触发 `28号` TRG-3 词池萎缩） |
| 该 Search Term 被判定明显不相关 | 可以否词 | 否词针对的是**相关性错误**，不是「词已转精准」 |
| 出现明显重复抢量 | 进入人工复评 | 不自动把所有重复流量否掉 |

## 13. 停止投放与低价捡漏组

**广泛、词组、自动活动不得迁入低价捡漏组**（`ONT-016`、`ONT-RUNTIME-002`）。
低价捡漏组只收 EXACT，预算固定 $1，Bid = `min(current_bid, 0.20)`（`ONT-014`）。

广泛类的退出动作是 `stop_campaign`（`30号§2`），**不是** `pause`，也**不是** `eliminate_to_low_bid_pool`。

| 情况 | 处理 |
| --- | --- |
| 数据不足或活动上线 <3 天 | 不能关闭，只观察曝光、点击、花费 |
| 相关但无转化（§4 档 2/3） | 低 Bid、受控预算、Listing 诊断；不关闭 |
| 明显不相关（§4 档 4） | Search Term 否词 |
| 高花费无单且低相关 | 否词 → 降 Bid → 降预算；仍无改善 → `stop_campaign` |
| 整体活动持续长期低效 | `stop_campaign`（HIGH_RISK_REVIEW，必须人工确认） |
| `立即退出` 模式 | 确定性 `stop_campaign`，不进入 LLM 判断（`18号§0`） |

**停止投放前必须走完 `21号§3` 的广泛类诊断路径**：高点击无单 → 先否词 → 仍无改善降 Bid/降预算 → 仍无改善才评估停止投放。不得跳过否词直接停止投放。

**停止投放触发预算回算**：释放金额 = `current_daily_budget`，计入 `other_campaign_budget_decrease`（`23号§5`）。

## 14. 扩词

扩词决策以 `28号` 为唯一权威（触发动因 TRG-1~5 × 产品阶段矩阵、来源码、相关性档位、配额公式）。
本节只列广泛侧的接口要点：

- 扩词是 `28号§5` 预算缺口填补的**第 4 档兜底**，前三档消化不完才扩。
- 数量按 `28号§3` 公式动态计算（可分配扩词预算 ÷ 单词最低验证预算），受每日新词上限封顶（`03号§7`，作用域为**每父 ASIN 每日**）。
- 缺 `search_term_report` 时，`SRC_CONVERTED / SRC_AUTO_CLICKED / SRC_BROAD_DERIVED / SRC_AUTO_BROAD_TERM` 全部不可用，扩词降级为「仅人工提案」（`28号§1`）。
- 清仓期（`清货期`）禁止扩词（`28号§3.2`）。

## 5. 返回结果（LLM 应产出）结构

- `reason/evidence` 经 `_sanitize_ops_text` + `humanize_ops_text` 脱敏清洗。
