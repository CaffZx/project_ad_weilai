# 文本治理与影子知识库 SkillOpt 实施方案

> 版本：v1.0  
> 日期：2026-07-17  
> 状态：设计确认稿  
> 目标：建立一套以真实、合法样本为底座的文本治理系统，使复盘记忆、知识库、记忆注入模板和指定提示词片段能够被安全地迭代；唯一业务判断标准是广告 Agent 推荐建议是否更准确、更安全。

## 1. 结论与边界

SkillOpt 的作用不是修改数据或业务规则，而是治理和迭代 Agent 会读取的文本对象。它可以自动生成一份影子知识库，并让该候选参与离线和影子推荐评测；它不能直接覆盖线上知识库，也不能绕过人工发布和回滚。

复盘记忆与知识库不是两套彼此独立的数据工程：两者共用“分析快照 → 实际执行 → Amazon 生效 → T+3 → 干扰检查 → 合法案例”的数据底座；差异在于产物和使用方式：

- 复盘记忆：从单个历史决策中提炼出的、带父 ASIN/活动身份和适用条件的经验。
- 知识库：跨产品、跨场景的业务解释、规则组织、案例归纳与知识缺口补全。
- 注入模板/提示词：决定 Agent 如何筛选、理解和使用上述文本。

所有候选都必须通过同一个推荐建议 benchmark。不能因为知识库更完整、记忆更像人工、提示词更长，就视为优化成功。

## 2. 不可修改区与可优化区

### 2.1 永久不可由 SkillOpt 修改

以下内容是确定性业务约束，只能由业务/研发走人工变更流程维护：

- 数值阈值、预算上限、目标 ACOS 上下限；
- 安全红线、执行 guardrail、风险拦截条件；
- 指标定义与计算公式；
- 数据关联、ASIN/活动/关键词身份规则；
- 样本合法性判定与干扰排除规则；
- train/validation/final test 的分区规则；
- scorer 的硬门槛；
- MCP 调用权限、实际执行参数构造与幂等规则。

这些内容需在知识库中以“锁定块（locked block）”显式标记，并同时保存在版本清单中。候选生成或合并时一旦改动锁定块，静态校验必须直接失败。

### 2.2 允许自动生成影子候选的内容

SkillOpt 可以生成、删除、重排或改写下列非锁定内容，但每次运行仅开放一个明确范围：

| 对象 | 允许的变化 | 不允许的变化 |
|---|---|---|
| 知识库内容组织 | 章节层级、索引、术语导航、调用点切片说明 | 改变锁定规则含义 |
| 解释规则 | 已有规则的解释、边界说明、反例、常见误解 | 新造阈值或把经验写成硬规则 |
| 适用条件 | 产品阶段、淡旺季、广告目的、流量前提、例外条件 | 无证据扩大适用范围 |
| 案例归纳 | 从已审核、合法复盘案例中提炼的模式 | 引用未执行、被排除或数据不足案例作为正向结论 |
| 知识缺口补全 | 对 benchmark 反复出现而当前 KB 未覆盖的问题增加“待审核解释模块” | 以模型猜测填充业务事实 |
| 记忆注入模板 | 选择、排序、冲突处理、压缩与引用方式 | 绕过记忆状态和适用条件 |
| 提示词指定片段 | 如何要求 Agent 阅读证据、处理冲突和表达不确定性 | 删除 guardrail 或改变输出契约 |

## 3. 统一治理底座

### 3.1 事实链路

所有可用文本经验必须回到以下事实链路：

```text
决策时分析快照
  + 产品策略上下文、知识库/提示词版本、卡片与建议
        ↓
运营同意范围 + 执行 MCP + ERP 执行结果
        ↓
Amazon 最终生效时间
        ↓
完整 T+3 产品级/活动级数据
        ↓
干扰检查、数据充分性检查、确定性证据计算
        ↓
合法 review_case
        ↓
人工审核后的记忆 / 可用于归纳的案例事实
```

`decision_id` 是这条链路的主线。长期治理必须确保执行主表和 campaign、keyword、placement 三张执行子表可通过 `decision_id` 回到决策、快照和实际动作。

### 3.2 合法案例门槛

只有同时满足以下条件的案例才可进入记忆生成、知识库案例归纳或 benchmark 素材库：

1. 决策快照、产品上下文和当时文本版本可定位；
2. 运营同意范围可定位；
3. 实际成功动作、Amazon 最终生效时间可定位；
4. 自生效起具备完整、口径一致的 T+3 数据；
5. 改价、人工二次调整、库存/断货等干扰已检查；
6. 流量和转化数据达到预定义充分性门槛；
7. 关键词、活动、产品身份不存在冲突或串位；
8. 可解释本次案例为什么属于 `eligible`、`INSUFFICIENT_DATA` 或 `EXCLUDED`。

`INSUFFICIENT_DATA` 与 `EXCLUDED` 案例必须保留用于审计和风险学习，但默认不得写成正向记忆或知识库经验。

### 3.3 统一版本账本

使用 `t_advert_agent_text_artifact_version` 作为所有文本对象的版本账本。每一行至少记录：

- `artifact_id`、`artifact_type`、`artifact_version`、`content_hash`；
- `base_artifact_version`：候选从哪个已发布版本派生；
- `storage_uri`：真实文件/目录位置；
- `scope_manifest_json`：允许变更的文件、章节、锁定块、调用点；
- `source_run_id`：对应 SkillOpt 运行；
- `status`：`DRAFT`、`SHADOW`、`APPROVED`、`ACTIVE`、`REJECTED`、`RETIRED`；
- `created_by`、`approved_by`、时间戳与发布/回滚原因。

`artifact_type` 最少覆盖：`REVIEW_MEMORY`、`MEMORY_INJECTION_TEMPLATE`、`AGENT_PROMPT_FRAGMENT`、`KNOWLEDGE_BASE`、`KNOWLEDGE_BASE_MODULE`。

## 4. 影子知识库的形态与生成规则

### 4.1 目录与版本关系

线上知识库当前由 `docs/knowledge_base/` 中的 Markdown 和 ontology 配置组成，并由 `app/llm/kb_loader.py` 按调用点切片。影子知识库不能直接改写该目录；每次候选运行必须创建独立版本目录，例如：

```text
knowledge_artifacts/
├── active/<active_kb_version>/
│   ├── knowledge_base/             # 当前线上等价副本
│   └── manifest.json
└── shadow/<run_id>/<candidate_id>/
    ├── knowledge_base/             # 完整候选副本
    ├── manifest.json                # base 版本、hash、可改范围、锁定块清单
    ├── change_set.json              # 逐文件/逐章节结构化 diff
    ├── evidence_refs.json           # 每项改动对应的合法案例或 benchmark 缺口
    ├── static_check_report.json
    └── evaluation_report.json
```

影子评测时，运行时加载器应接受 `KB_ROOT` 或同等显式参数，令同一份 Agent 代码可以读取 active 或 shadow 目录。评测调用必须记录实际加载的 `artifact_version` 和 `content_hash`。

### 4.2 候选输入

一次知识库候选生成只允许使用以下冻结输入：

- 当前 active 知识库版本与其锁定块清单；
- 允许编辑的模块列表和最大改动预算；
- train 分区内、已审核且合法的复盘记忆/案例归纳；
- train 分区内 benchmark 暴露出的错误类别、失败建议和人工标注；
- 知识库 ontology、调用点映射和文本长度预算；
- 当前 scorer、模型、随机种子和运行配置。

禁止把 validation/final test 的案例、人工答案、后验 T+3 结果或失败分析交给候选生成器。

### 4.3 候选输出

候选不是“直接改一堆 Markdown”，而是一个完整、可审计的变更包：

```json
{
  "candidate_id": "kb-shadow-...",
  "base_artifact_version": "kb-active-...",
  "editable_scope": ["02-...md", "campaign/..."] ,
  "locked_block_hashes": {"03-...md#guardrails": "..."},
  "changes": [
    {
      "file": "...",
      "section": "...",
      "change_type": "ADD|REWRITE|MOVE|DELETE",
      "rationale": "解决某类推荐错误或补齐明确缺口",
      "evidence_refs": ["review_case_id", "benchmark_case_id"],
      "before_hash": "...",
      "after_hash": "..."
    }
  ]
}
```

候选输出必须包含：变更前后 diff、每处改动的证据引用、影响调用点、预计 token 增减和明确的回滚目标。没有证据引用的“经验补充”不得进入影子知识库。

### 4.4 静态检查与人工检查

候选进入 Agent 回放前，先执行：

1. Markdown/YAML/ontology 语法检查；
2. `kb_loader` 调用点切片检查，确认所有必需模块仍可加载；
3. 锁定块哈希校验；
4. 禁止词/禁止字段检查，防止出现未授权阈值、执行指令或泄漏标签；
5. 链接、目录、重复规则和冲突规则检查；
6. 候选长度与单调用点 prompt token 预算检查；
7. 变更包中的每处 `evidence_refs` 存在性与样本合法性检查。

静态检查通过只是“可评测”，不是“可发布”。人工审核关注候选是否误解业务、是否将偶然案例泛化为规则、是否引入隐蔽冲突或过度冗长。

## 5. 唯一业务 benchmark：推荐建议回放

### 5.1 推荐案例

一个 `recommendation_case` 固定在真实的分析时点 `analysis_at`，并保存：

- 当时 Agent 可见的产品/活动数据和策略上下文；
- 当时允许使用的 active 文本版本；
- `analysis_at` 之前已完成 T+3、审核通过且应当可检索的历史记忆；
- 对应的历史建议、运营同意/拒绝、实际执行与 T+3；
- 人工标注的合理推荐方向、必须避免的风险和关键证据。

评测中，只有候选文本对象替换 active 版本；数据、案例、Agent 代码、模型设置、记忆检索规则和 scorer 全部冻结。

### 5.2 不泄漏规则

- 一个 `decision_id` 的 T+3 结果或由它生成的记忆，不得用于评分该 `decision_id` 决策时的推荐。
- 较早、已审核的案例记忆可以用于较晚的推荐案例，前提是其复盘完成时间早于该案例 `analysis_at`。
- 一个父 ASIN 的全部快照、决策、复盘案例、记忆和推荐案例只能位于 train、validation、final test 的其中一个分区。
- validation/final test 的运营结果、实际执行、T+3 与人工答案只供 scorer 使用，不得出现在 Agent 输入或候选生成上下文。

### 5.3 数据切分

| 分区 | 切分单位 | 用途 | 是否允许 SkillOpt 读取 |
|---|---|---|---|
| train | 约 80% 父 ASIN | 生成候选、反思、训练侧评分 | 是 |
| held-out validation | 约 20% 父 ASIN | 选择候选版本、拒绝退化候选 | 否 |
| final test | 后续新增父 ASIN 或未来新增案例 | 发布前和发布后独立审计 | 否 |

样本量不足时只建立 train/held-out validation，20% 不能称作 final test。任何分区都需以父 ASIN 为整体；不得随机把同一产品的相邻决策拆开。

### 5.4 scorer

硬门槛必须先于质量评分执行：不使用未来信息、不越过预算/ACOS/业务 guardrail、不虚构动作或事实、不错误关联活动/关键词、不将排除/数据不足记忆当正向经验。

质量评分由人工标注校准，至少覆盖：

- 推荐方向与产品阶段、目标和当前证据的一致性；
- Bid、预算、广告位、否词等动作的合理性；
- 风险识别和数据不足时的克制；
- 对记忆/知识库规则的正确使用，避免错误泛化；
- 建议是否清晰、可执行；
- 在具有真实后验的案例上，与人工判断、实际执行和 T+3 的一致程度。

LLM Judge 可辅助批量评分，但需以人工标注持续校准，不能成为唯一裁判。

## 6. SkillOpt 运行策略

### 6.1 每次只优化一个对象

为了知道提升来自哪里，一次 SkillOpt run 只能选择一个 `artifact_type`：

1. `MEMORY_INJECTION_TEMPLATE`：首先验证怎样检索、排序、压缩和呈现审核记忆；
2. `AGENT_PROMPT_FRAGMENT`：优化 Agent 如何使用文本证据与处理冲突；
3. `KNOWLEDGE_BASE_MODULE`：优化一个明确调用点的知识模块；
4. `KNOWLEDGE_BASE`：只有模块级治理、回滚和 token 预算成熟后才允许全库结构优化；
5. `REVIEW_MEMORY`：只优化已审核记忆的表达模板，不修改其事实、适用范围或审核结论。

不能在同一 run 同时改知识库、提示词和记忆注入模板。

### 6.2 一次运行的输入与输出

输入：当前文本版本、可编辑范围、锁定块、train/validation 清单与哈希、推荐案例、scorer 版本、模型版本、成本/时间预算。  
输出：候选 artifact、逐项 diff、静态检查报告、train/validation 分数、硬错误列表、逐案例建议差异、token/成本、人工审核结论和回滚版本。

SkillOpt 的 train 侧可产生候选，但只能用 held-out validation 选择是否比当前 active 版本更好。final test 仅在版本选择完成后运行一次。

## 7. 发布与回滚

### 7.1 影子评测

影子知识库/文本版本在相同的推荐案例上与 active 版本并行回放。必须同时保存：同一输入、两个文本版本、两个输出、逐项 scorer 结果、命中的记忆/KB 片段、模型调用成本和运行时间。

候选进入影子运行的最低门槛：静态检查通过、锁定块零变化、train 侧无硬错误、held-out validation 优于或至少不低于 active、人工初审通过。

### 7.2 小范围启用

影子版本持续稳定后，按店铺/父 ASIN/调用点小范围启用。每次生产推荐记录实际 `artifact_version`、`content_hash`、命中的文本片段与决策结果。发生高风险建议、硬门槛违规或业务指标明显回退时立即切回上一 active 版本。

### 7.3 人工发布责任

业务人员审批知识含义与案例泛化是否合理；研发审批静态检查、调用点兼容性、成本与回滚；产品审批实验范围和上线阈值。SkillOpt 只能提交候选和证据，不拥有发布权。

## 8. 落地顺序

### 阶段 0：定义治理合同

冻结 `decision_id` 链路、快照结构、样本合法性、锁定块格式、文本对象类型、推荐案例结构、父 ASIN 切分和 scorer 硬门槛。

验收：业务、产品、研发、ERP 维护方明确各字段的写入方、版本责任和发布责任。

### 阶段 1：先完成长期事实治理

1. 执行 MCP 向 ERP 传递并落库统一 `decision_id`；
2. 执行主表和三张子表可回溯到决策；
3. 分析完成时异步冻结数据和文本版本；
4. Amazon 最终生效后创建幂等 T+3 任务；
5. 自动形成 `review_case` 和合法性判定。

验收：随机一条真实执行能恢复决策时输入、实际动作、T+3 结果和干扰结论。

### 阶段 2：跑通审核记忆与文本版本链路

1. 从 `eligible=true` 案例生成统一记忆 JSON；
2. 拆分、落库、人工审核、启停和审计；
3. 将 active 知识库纳入版本账本，识别锁定块和可编辑模块；
4. 先人工制作一个影子知识库副本，验证加载器可切换根目录和记录版本。

验收：记忆和影子知识库均可被独立加载、可回溯、可停用，不影响线上 active 版本。

### 阶段 3：建立推荐建议 benchmark

1. 按父 ASIN 切分 train/held-out validation；
2. 按每个 `analysis_at` 截断可见数据和记忆；
3. 完成人工标注、硬门槛和质量 scorer；
4. 跑无记忆/当前 active 文本基线；
5. 校验 validation 没有样本和未来信息泄漏。

验收：每条评分可完整回放，并能解释候选为何得分或失败。

### 阶段 4：先优化低风险文本对象

先运行记忆注入模板或指定提示词片段的 SkillOpt 实验；一次只改一个对象，记录 candidate、diff、分数、成本和人工结论。

验收：held-out validation 提升、硬错误为零、人工确认没有通过“更保守但失去可用性”刷分。

### 阶段 5：自动生成影子知识库候选

1. 先限定一个调用点和一个可编辑知识模块；
2. 基于 train 中合法案例和失败类别生成影子候选；
3. 跑静态检查、推荐回放和人工审核；
4. 验证通过后扩大到相邻模块；
5. 最后才考虑全库结构治理。

验收：候选可解释、锁定块零变化、validation 不回退、可以精确回滚到基础版本。

### 阶段 6：影子运行、小范围发布与 final test

候选先在影子流量中并行记录建议差异；满足阈值后小范围启用。使用从未参与候选生成或选择的 final test 做独立审计，并持续监控真实业务风险。

## 9. 最终验收标准

系统完成不以“生成了候选知识库”为标准，而至少满足：

- 每条可用经验可追溯到合法事实链路；
- active、shadow、候选和已废弃文本版本均可定位、比较和回滚；
- 锁定业务规则从未被候选改写；
- 同一父 ASIN 和未来后验信息未跨 benchmark 分区泄漏；
- 推荐 benchmark 的 held-out validation 对 active 版本有稳定提升或至少无风险回退；
- 人工能理解每处知识库改动的证据来源和影响调用点；
- 影子及小范围发布没有新增高风险推荐；
- SkillOpt 运行的样本、模型、文本、评分和成本均可复现。
